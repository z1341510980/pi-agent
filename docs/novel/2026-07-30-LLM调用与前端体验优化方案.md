### P1-1 后续：已定位两个真实成因（诊断之外的实际修复）

诊断上线后回看链路，发现命中率低不是"分层设计没生效"，而是有两处实现把命中**主动打掉**了。两者都已修复：

**成因 1：缓存路由键每次都是随机值**（主因）

`createSession` 每次都用 `plugin:${name}:${randomUUID()}` 作 threadId → 新 Pi Session → 新 `sessionId`，而 pi-ai 把 `sessionId` 直接当 OpenAI 的 `prompt_cache_key`（`providers/openai-completions.js` 的 `buildParams`）。这个字段是**路由提示**：相同 key 的请求才会被尽量导到同一台机器，从而命中那台机器上的前缀缓存。

于是同一章的 Director / Writer / Reviewer 各拿一个随机 key，明明共享 system + shared 前缀，却被路由到三台不同机器 —— 前缀建了但谁也用不上。这解释了为什么 Writer 的 `cache_read` 只有 6.1k 而 shared 段本身 14.2k 字符。

修复：`PluginSessionOptions` 加 `promptCacheScope`，orchestrator 传 `novel:${projectId}:${chapterNumber}` —— 正是「共享同一段前缀的那组调用」的粒度。

**成因 2：对不认这套协议的 provider 强打 `cache_control`**

`applyCacheBreakpoints` 无条件把消息 `content` 从字符串改写成 `[{type:'text', text, cache_control}]` 数组。但只有 Anthropic 系认这个字段；DeepSeek / OpenAI 用的是**自动前缀缓存**，要求前缀逐字节稳定，改写序列化形态反而把本来能命中的自动缓存打掉 —— 我们以为在提升命中率，实际在破坏它。这也与实测里那条 `400 Failed to deserialize the JSON body：missing field 'messages'` 吻合。

修复：新增 `core/plugin/cache-control-support.ts`，口径与 pi-ai 的 `detectCompat` 对齐（仅 Anthropic 原生 + OpenRouter 转发 `anthropic/*`），其余保持字符串原样，把命中交回服务端。21 个用例覆盖两项判定 + 键生成。

> 待验证：两处修复都需要接真实 Provider 跑一章才能确认 `cache_read` 是否真的上来。诊断面板已能直接给出前后对比。

### P0-2 剩余：Writer 增量重写 —— 已完成

新建 `core/writer-rewrite-plan.ts`。**关键判断是「上一稿可不可用」**，按 Guard 命中原因分两类：

| Guard 原因 | 上一稿 | 策略 |
|---|---|---|
| 模型未输出正文 / 模型退化检测命中 | 只有计划说明 / 复读截断，不是有效正文 | **全量重写**（带上去只会让模型顺着垃圾继续复读，比全量更糟） |
| 字数严重不足 / 超标 / 未完整执行矩阵编排 | 有效正文 | 定向扩写 / 压缩 / 补入 |

每条定向指令都写清「改哪里、怎么改、不要动什么」——只说原因（旧行为）会让模型把整章重写一遍，定向修改就退化成了全量重写。上一稿超长时保留首尾、省略中间（首尾承接最关键）。19 个用例。

没让 Reviser 做这件事：Reviser 的输入是 Reviewer 的结构化审稿报告（语义问题），而 Guard 命中的是确定性问题（字数、姓名缺失），此时 Reviewer 还没跑。Writer 自己做定向修改能省掉一次 Reviewer + 一次 Reviser 往返。

### P0-3 群聊同场角色合并调用 —— 纯函数与数据通路已完成

新建 `core/agent/discussion-actor-batching.ts`：认知指纹分组、合并提示词构建、按角色名解析分发。`DiscussionMember` 加 `knowledge` 字段，`novel-discussion-runner` 用 `collectCharacterKnowledge` 填充。31 个用例。

**合并的前提是信息对称，不能凭"同场"就合并。** 角色可见上下文按人裁剪（`informationLayers` 决定谁知道什么），把知情者和不知情者合进一次调用等于把秘密泄露给不该知道的角色，后续会出现「他明明不知道却提到了那件事」。所以只合并对每一条信息层 knows/suspects/misunderstands 都相同的角色，且归一化口径必须与 `buildCharacterVisibleContext` 的 if-else 链一致（那里命中一个就 continue）。

成组上限 4：一次要产出 N 段台词，N 太大时模型会压缩后面的段落（前几个角色演得完整，后面草草收尾），反而不如拆两次。

> **引擎已接线**：`ModeratorDecision.invite` 加可选 `agentIds`，主持人提示词说明「信息完全相同的角色可一次点名 2-4 人，不确定时宁可分开」；引擎 `handleMergedInvite` 按认知指纹分组 → 按规模上限切批 → 合并调用 → 按角色名解析分发。<br>三处回落保证不丢发言：分组后全是单人组 → 回落单角色路径；合并输出缺某人分段 → 单独调用该角色；单人组成员 → 补一次单独发言。`agentIds` 里的非法 id（不存在/非角色/规划阶段）被丢弃而非抛错 —— 退回单角色仍是正确行为，为一个可选优化字段触发重试不值得。Moderator 侧 8 个用例。

### P1-3 Memory 的上下文注入是反的 —— 已完成

memory 的 `chapter_context` 平均只有 347 字符，却有 20.2k input —— 靠 systemPrompt + 正文全文工作。

**一处对原判断的修正**：核查后「拿不到本章编排实体」不成立 —— `getCurrentEntityState` 早已按 `arrangedEntities` 过滤，编排实体的 currentState/currentGoal/currentPressure 都注入了。真正缺的只有**账本**一侧：

1. 前几章的变化 delta（只看到"当前值"，看不到它是第几章、因为什么变成这样）
2. 本章的 `plannedChanges`（编排阶段已声明要推进哪些维度，Memory 看不到，无法回答"计划的推进发生了没有"）

新增 `core/memory-ledger-handoff.ts` 补上这两段 + 账本自身的连续性告警（那些往往正是 Memory 上一次写错造成的）。措辞从「判断现在是什么状态」改成「找出哪些条目发生了变化 / 逐条核对计划、没发生就不要凭计划补写」。

没复用 prompt-builder 的 `formatStoryLedgerContext`：那个版本服务 Writer，含未来承诺、活跃线程、批注等，对状态提取无用，注入进去只会把 20.2k input 推更高。两者取舍方向相反，共用会让两边都妥协。19 个用例。

### P2 及待查

- `400 tool_calls must be followed by tool messages`：分类器已识别为 `malformed_session` 并快速失败（不静默重试，避免把缺陷掩盖成偶发抖动），但**根因未修**。指向 `pi-session` 在工具调用中断后没清理半截的 tool_calls，下一轮请求带着不成对的消息发出去。正确修法是在 session 侧丢弃未配对的 tool_calls 后重建请求。

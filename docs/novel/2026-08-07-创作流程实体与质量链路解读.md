# 小说创作全流程：剧情实体与质量链路解读

> 面向产品/非熟悉代码的读者。目标是把「编排 → 创作 → 审稿 → 修订/重写 → 记忆提取 → 落库 → 下一章」这条链路上，**剧情（冲突/伏笔/线索/事件）从生成、读取到回写的完整路径**讲清楚，并回答四个常见疑问。所有结论都对应到真实代码（文件 + 行号），标注「能做 / 不能做 / 注意点」。

---

## 0. 一分钟看懂整条链路

```
                ┌────────────────────────────────────────────────────────────┐
                │                         创作流程                           │
  矩阵编排        │  Director  →  检查点1  →  Writer  →  PostWriteGuard         │
  (ai-arrange)   │                    │              │(字数/退化/矩阵角色)       │
      │          │                    │              ▼                        │
      │ 生成/复用  │             ←─ Writer推回  重写(≤2次)/接受/转Reviser         │
      ▼          │                    │              │                        │
 冲突/伏笔/线索    │                    ▼              ▼                        │
 角色/势力/地点    │               Reviewer(盲审+验收) ──质量门仲裁──► 必须修订？   │
      │          │                    │            │                          │
      │          │                    ▼            ▼                          │
      │          │            验收检查点2    approve──► Memory ──► 落库章节      │
      │          │            approve/修订/重写    │                            │
      └─────────►│                 │              └► 修订(≤2轮)─►复检─► Memory  │
                 │                 └─► 重写(预算闸门)                            │
                 └────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
                    记忆提取：正文 diff → 冲突/伏笔/线索/角色状态更新
                                        │
                                        ▼
                    syncChapterDimensions + 快照 + 版本存档 → 下一章继续读
```

一句话：**编排阶段决定「本章哪些剧情实体登场」，创作阶段把实体喂给 AI 写正文，记忆阶段把正文的变化 diff 回写到实体，形成「读 → 写 → 再读」的闭环。**

## 1. 新加的剧情实体，在 ai-arrange 里如何生成？冲突/伏笔/线索能正确区分吗？

### 1.1 流程：两阶段生成

入口是 `POST /projects/:projectId/chapters/:chapterNumber/ai-arrange`（`routes/creation-flow-routes.ts:788`），调用 `entityGenerator.generateAndArrange`（`:853`）：

1. **规划阶段** `planEntitiesFromOutline`（`core/novel-entity-generator.ts:1602`）：LLM 单次调用、强制 JSON 输出（`:1849`），产出 `EntityPlan`——列出本章要出场的角色/冲突/伏笔/势力/地点/物品清单。
2. **生成阶段** `generatePlanInBatches → generateEntityBatch`（`:2009 / :2133`）：按 kind 分批调用 LLM，每类用**独立的 JSON 解析器 + 枚举校验**，最后落库。

编排能生成的实体类型只有 7 种（`:191`）：
`character 角色 / conflict 冲突 / foreshadow 伏笔 / faction 势力 / location 地点 / item 物品 / world_element 世界元素`。

### 1.2 冲突、伏笔、线索是怎么区分的？（核心）

| 实体 | 判定方式 | 关键校验（代码） |
|---|---|---|
| **冲突** | Prompt 写入「冲突编排准入」规则：**迫使角色做出选择的核心对抗**，一章 ≤ 2 条、同一事件只算一条（`:1801-1804`） | `parseConflict`（`:2613`）枚举校验：`type/intensity/stage/tier/participants/climaxChapter/climaxType/stakes/twistPotential/plotFunction/progressionMode` |
| **伏笔** | Prompt 强制返回 `importance/narrativeRole/hiddenQuestion/plannedPayoff/chapterAction`，缺项直接过滤（`:1791`、`:251`） | `parseForeshadow`（`:2687`）校验 `category`（8 类：物品/言语/事件/身份/秘密/预言/承诺/台词）、`status`（7 态）、`plantMethod/recoverMethod` |
| **线索** | **不经过 LLM 生成**：直接 `store.listClues()` 按 `chapterSpans` 覆盖本章过滤复用（`:625-629`） | 无生成校验（因为它压根不生成） |

**结论：**
- ✅ **冲突、伏笔能正确区分**——靠「结构性 prompt 规则 + 逐项枚举校验」双保险，不是让 AI 自由发挥。二者语义边界在 prompt 里写死：冲突是「对抗/选择」，伏笔是「埋设/回收」。
- ⚠️ **线索刻意「只复用、不新生成」**：线索是证据性事实（有 `pointsTo/progress/isMisleading` 字段，`packages/shared/src/novel/index.ts:702`），需要严格因果与验证动作。如果让 AI 每章随手造线索，会产生无法兑现的伪线索，污染推理链——所以设计上由正文自然产生，或人工标记。
- ⚠️ **剧情单元（NovelStoryEvent）不在编排范围**：它不是「生成」出来的，而是记忆阶段对正文做 diff 自动产生的账本记录（见第 3 节）。

落库调用：`createConflict`（`:916`）/`createForeshadow`（`:1011`）/`createCharacter`（`:1560`）等，冲突、伏笔、势力等会写入 `chapterSpans`（本章出场区间），供后续章节判断「这实体是否在本章可见」。

### 1.3 编排结果如何交给创作流程？

`arrangedEntities` 是唯一传输契约（`routes/arranged-entities-contract.ts:37`，zod schema 含 `clueIds`），create-flow 启动时校验实体归属（`findForeignArrangedEntities`）后传给 Writer；`novel-engine.ts:71-77` 再用 Set 过滤，防止伪造 ID。

## 2. create-flow / create-discussion 是否正确读到了剧情、冲突、伏笔、线索？

**能，而且是同一条读取管线。** 两条链路复用同一个 `buildChapterContextShared`（create-flow 在 `novel-orchestrator.ts:2235`，群聊在 `novel-discussion-runner.ts:119`），注入给各 Agent 的「共享章节上下文」按顺序包含：

| 注入段落 | 内容 | 数据来源 |
|---|---|---|
| 章节信息 + 章纲 | 本章基本信息与用户章纲 | `formatChapterInfo` |
| 创作约束 | 字数/节奏/冲突目标/悬念钩子 | `formatConstraints` |
| **本章出场要素**（有编排时） | 角色/冲突/伏笔/线索/势力/地点/物品/信息层 8 类 + 角色「本章功能位」中文映射 + 冲突推进模式 + 伏笔 category 映射，标题注明「**必须真正参与事件**」 | `formatArrangedEntities`（`prompt-builder.ts:1613`） |
| **当前故事状态**（无编排兜底） | 只注入「活着的」实体：未解决的冲突（排除 resolved/transformed）、未回收的伏笔（排除 recovered/abandoned）、未完成线索（progress<100） | `formatStoryState` → `toStoryState`（`:3372`） |
| 账本承接 | 上一章状态变更摘要 | `formatStoryLedgerContext`（`:2854`） |
| 实体关联 | 角色↔冲突↔伏笔的边 | `formatEdges`（`:2471`） |
| 信息差 | 各角色知道/不知道什么 | `formatInfoLayers` |
| 摘要/结尾/钩子 | 最近章节摘要、上一章结尾、**待兑现钩子**、文风指纹 | `collectChapterAnchorSections`（`:1027`） |

**各 Agent 的专属后缀**（`buildChapterContextSuffix`，`:1217`）：Director 注入节奏建议 + 上轮审稿反馈；Writer 注入创作指令模板；Reviewer 注入验收标准。

**群聊模式**（`novel-discussion-runner.ts`）：`buildMembers`（`:499`）= 4 个工种 Agent + 本章出场角色。角色成员**不读全知共享上下文**，只读 `buildCharacterVisibleContext` 裁剪过的「自己知道的部分」——这符合"角色只能依据已知信息行动"的设定。

**结论：**
- ✅ 剧情、冲突、伏笔、线索都在 Writer/Reviewer 的上下文里，且明确要求「出现不等于交差，必须真正参与事件」（`formatArrangedEntities` 标题即此意）。
- ✅ 有编排时以「本章出场要素」为准（精确到本章），无编排时以「当前故事状态」兜底（防止 AI 全知或遗漏）。
- ⚠️ 注意：实体「被读取」≠「被正确使用」。PostWriteGuard 会做确定性校验（矩阵角色姓名必须出现，`novel-orchestrator.ts` 的 `runPostWriteGuard`），但「是否真正参与事件」这类语义问题只能靠 Reviewer + 质量门把关（见第 4 节）。

## 3. 提取记忆时是如何操作的？

### 3.1 输入：刻意「轻装上阵」

记忆 Agent 的输入（`novel-memory-generator.ts:669` `buildUserPrompt`）是：

```
本章叙事任务 + 章纲 → 章节正文 → 账本承接 → 当前实体状态（仅本章相关）→ 待兑现钩子
```

**刻意不复用创作阶段的共享上下文**（代码注释 `:424-430` 明说省约 1 万字符）——记忆不需要知道全知故事状态，它要的是「读正文 → 对照已有状态 → 找变化」的差分，而不是重新判断。

### 3.2 输出：结构化 JSON 变更

LLM 输出 `MemoryUpdatePayload`（`:252`），包含：`characterUpdates / relationshipUpdates / foreshadowUpdates / clueUpdates / conflictUpdates / hookUpdates / characterArcUpdates`。

`applyChanges`（`:1065`）逐项落库：
- 角色：`updateCharacter` / 必要时 `createCharacter`
- 伏笔：`updateForeshadow`（状态、回收）+ `createEdge` 关联角色
- 线索：`updateClue`（推进 step / 标记误导）+ 关联伏笔
- 冲突：`updateConflict`（阶段、强度）
- 钩子：标记 `fulfilled`
- 角色弧光：`createCharacterArc`

### 3.3 故事事件（StoryEvent）怎么来的？

**不是记忆 Agent 直接 create 的。** 正文落库时 `chapter-finalizer.ts:930` 的 `recordMemoryEvents` 用「落库前 vs 落库后实体快照 diff」自动生成 `character_change / conflict_change / foreshadow_change` 等账本事件（`memoryStore.recordEvent`）。这样保证事件是"可验证的变化"，而不是 LLM 的自我声明。

### 3.4 落库顺序与事务边界

`finalize`（`chapter-finalizer.ts:176`）按序执行：

```
Memory(applyChanges) → syncChapterDimensions → 章节快照 → updateChapter(正文+版本来源)
```

- `syncChapterDimensions`（`:1527`）：回填角色出场史 `characterHistory`、冲突 `chapterSpans`、伏笔埋设事件——把"本章正文发生的事"落到实体时间线上，供下一章读取。
- 版本存档：`updateChapter` 透传 `versionSource`（writer_initial / reviser_final 等），正文每版都有来源可查。
- **历史重写保护**：如果重写的是"后面章节已完成"的中间章，只存正文、**跳过实体写入**，避免污染已有时间线。

### 3.5 诚实说明：事务边界

- 方案文档曾写「Memory 确认与正文提交使用事务」，但**当前实现是顺序执行、无回滚**：`applyChanges` 内逐条 store 调用，中途失败不会回滚前面已应用的条目；Memory 整体失败则返回 error、不写正文。
- 这通常可接受（幂等更新），但不是原子提交——如果对一致性要求高，这是一个已知的改进点。

## 4. 修订、重写等逻辑是否正确？

### 4.1 两条"后悔药"的边界

| 动作 | 触发点 | 代价/上限 | 是否丢成果 |
|---|---|---|---|
| **重写 Writer**（原地） | PostWriteGuard 命中（模型退化/字数严重偏离 <75% 或 >130%/矩阵角色缺失），弹检查点后选「重写」 | 自动上限 **2 次**（`MAX_GUARD_REWRITE`），超过降级交给 Reviewer 人工判断 | 不丢——`bestWriterCandidate` 保底，最后一次退化成更差草稿会**自动恢复此前最佳稿**（`novel-orchestrator.ts`） |
| **整章重写**（全流程） | 验收检查点选「重写」或 Guard 达上限选「从头重写」 | 走**预算闸门**（`tryRecordFullChapterRewrite`），超出本章重写额度后不再允许 | 递归调用 `createChapterWithFlow`，从 Director 重新规划 |
| **修订**（局部） | 验收检查点选「修订」或质量门强制 | 自动 **2 轮**（`MAX_AUTO_REVISION_ROUNDS`）：首轮按审稿意见全量修订 + 第 2 轮只针对未通过项定向修补 | 不丢——失败保留修订稿 + 结构化失败信息，可再次定向修订（`re-revise`） |

### 4.2 质量门为什么"拦得住"？

五套检测统一交给 `arbitrateQuality` 仲裁（`core/quality-policy.ts`），关键设计：

- **确定性门有执行力**：AI 腔句式 / 正文形态 / 角色声音命中 error 时，仲裁结果是 `revise`，**验收检查点直接移除「接受」按钮**，后端还有硬门兜底（`:1063` 把强传的 approve 转成 revise）——用户不能静默让有问题的正文落库。
- **权限分级**：只有确定性门能触发整章重写；LLM 判断（Reviewer 结论）最多到 `revise`，不会因为一个模型意见就推翻整章（`GATE_REGISTRY` + `QUALITY_POLICY_INVARIANTS` 单测守住阈值一致性）。
- **修订是"工具化"的**：Reviser 必须调用 `novel_apply_revision` 工具（`novel-tools.ts:2043`）做精确字符串替换，彻底绕开"LLM 输出修改意见文本、正则解析失败、把修改意见当正文落库"的历史事故。

### 4.3 修订失败也不浪费（本轮的改动）

上一轮刚完成的优化（`novel-orchestrator.ts` 的 `runTargetedRevisionLoop`）：

- 失败结果**携带当前修订稿**（`content`）、具体未通过项（`failedItems`）、修订记录（`revisionRounds`），前端展示结构化失败卡；
- 提供「再次修订（只跑修订、不重跑生成）/ 手动编辑 / 保留草稿 / 取消」四个出口；
- 修订前检查点会先告知「预计几轮、几次调用、大概多少 token」。

### 4.4 结论与注意点

- ✅ 修订/重写链路是**有界的**：重写 ≤2 次 + 预算闸门、修订 ≤2 轮，不会无限重试烧钱。
- ✅ 质量门有执行力（强制修订时不能直接接受），失败有保底（恢复最佳稿 / 保留修订稿）。
- ⚠️ 一处行为变化：非强制修订且 Reviser 一轮都没改到内容时，旧逻辑会"保留原正文继续落库"，新逻辑改为结构化失败、让用户决定——更安全，但如果你依赖旧的静默行为需知晓。
- ⚠️ 已知小问题（工作区既有，非本次改动）：`prompt-protocol.test.ts` 有一条断言文案与 `role-writer.md` 当前内容不一致（提示词加了"一条修辞红线"），测试未同步，全量跑会红这一条。

## 5. 风险与边界清单（诚实版）

1. **线索不自动生成**：ai-arrange 只复用已有线索。如果期望"AI 从章纲自动埋新线索"，当前不支持（设计如此，防止伪线索）。
2. **剧情单元（StoryEvent）不直接生成**：由正文 diff 自动产生，不能被编排/记忆直接指定。
3. **记忆落库非事务**：applyChanges 逐条更新、失败不回滚；整体失败则不落正文。
4. **实体"被读取"不等于"被用好"**：语义级参与度靠 Reviewer + 质量门，确定性门只查"姓名出现"。
5. **全流程重写成本高**：整章重写会从 Director 重来（token 消耗最大），有预算闸门但不阻止你多次手动触发。
6. **中间章重写保护**：只存正文、不改实体时间线，是刻意的（防止污染已完成章节）。

# 小说生成逻辑整理与作家视角改造方案

> 日期：2026-08-22
> 性质：生成质量专项复盘（现状整理 → 作家视角诊断 → 改造方案 → 复盘修正）
> 依据：ARCHITECTURE.md、novel-orchestrator.ts、prompting/、quality/、lengdu/ 源码阅读，以及 `novel/output/第01章_掌纹里的门.md`、`stories/开局上交异界，我的背后是国家/chapters/第5章.md` 两份样章的实际阅读。
> 一句话结论：**这个系统不缺质量门，缺的是"戏剧大脑"。它像一群严格的校对围着一张事件清单工作，而不是一个懂得蓄势、代价与读者情绪的作家在写书。**

---

## 一、现状：小说生成的几个重要逻辑

### 1.1 主链：五段式多 Agent 流水线（`core/novel-orchestrator.ts`）

```
章纲 → [AI编排实体矩阵 ai-arrange] → Director（场景契约）→ Writer（正文）
     → PostWriteGuard + 文体评估器（确定性门）→ 盲审文字编辑
     → Reviewer（十维评分 + verdict）→ Reviser（局部补丁）→ Memory Generator（JSON 提取）
```

重试预算都很紧：

| 预算 | 值 | 位置 |
|---|---|---|
| Writer 推回 Director | `MAX_PUSHBACK = 1` | novel-orchestrator.ts:780 |
| Guard 触发整章重写 | `MAX_GUARD_REWRITE = 2` | novel-orchestrator.ts:227 |
| 自动修订轮次 | `MAX_AUTO_REVISION_ROUNDS = 2` | novel-orchestrator.ts:233 |
| Director 工具未提交重试 | `MAX_DIRECTOR_TOOL_MISS = 2` | novel-orchestrator.ts:550 |

### 1.2 上下文层：三层缓存 + Chunk 化注入

STATIC（世界规则/风格指南/Agent 身份）/ SEMI（本章出场角色全量定义 + 故事状态 + 锚点）/ DYNAMIC（工具调用）。SEMI 层锚点已很细（`core/prompting/context-chunk.ts`、prompt-builder.ts）：

- 最近章节摘要（默认覆盖最近 3-5 章）
- 上一章结尾 200-400 字硬锚点（prompt-builder.ts:3164）
- 未兑现钩子清单（上一章钩子必须完整承接）
- 叙事声音锚点、下一章开头锚点、文风指纹
- diff 模式：全局 Top-N 关键事实 + 上一章变化 delta 替代全量故事状态

### 1.3 质量层：确定性扫描 + LLM 审查双轨

确定性指标（`core/quality/prose-quality-evaluator.ts`、cliche-scanner.ts、quality-policy.ts）：

| 检查 | 阈值 |
|---|---|
| 碎段率（单句段占比） | ≥0.40 warn / ≥0.55 error |
| 短段占比（≤18 字） | ≥0.25 warn / ≥0.35 error |
| 解释腔 | ≥3 warn / ≥6 error |
| 泛化"像"字比喻 | 每千字 ≥2 warn / ≥3.5 error |
| 角色声音坍缩 | 句长 CV<0.35、完整句 ≥90% 等 |
| AI 腔正则（破折号/突然/然而/于是/内心深处等） | 各自独立阈值 |
| 字数门 | <75% 或 >130% 触发整章重写（`WORD_COUNT_LIMITS`） |

LLM 审查：Reviewer 十维评分（consistency/style 等）+ S1-S4 严重度 + verdict(accept/revise/reject)；盲审 prose-editor 只审文字形态不审规划。

### 1.4 文风层、记忆层与读感闭环

- **文风档案**：声明式参数 + 用户贴正向样本 ≤1200 字×2 + 反样本 ≤500 字×2（`writing-style-prompt-factory.ts:101-103`），注入 writer/reviser/reviewer；v2 风格专家卡从参考小说 LLM 蒸馏技法卡（六维，stage 3 部分 完成）。
- **Memory Generator**：单次输出 JSON 提取十类轨道（角色/剧情/冲突/线索/伏笔/钩子/弧光/势力地点物品/关系/故事线推进），名字匹配落库。
- **lengdu 读感闭环**：独立校准者 + 独立 Reader 冷读（`core/lengdu/lengdu-workflow.ts`），`MAX_READER_REVISIONS = 1`。

## 二、诊断：为什么不理想（资深作家视角）

工程机制已经过剩，叙事学机制不足。样章单章质量尚可（《掌纹里的门》感官、钩子合格），问题在更上层。

### 诊断 1：只有"章级大脑"，没有卷级戏剧结构（最核心）

Director 每次规划是孤立的一章，14 种任务类型是事件分类学而非戏剧结构学。卷纲到章纲之间缺一层**节拍表（Beat Sheet）**。后果：

- 每章都"成立"，但连续读平淡——没有跨章蓄势与释放曲线
- 爽文的爽点间隔、压制-爆发节奏无人设计（RhythmController 只输出节奏标签建议，不管情绪债务累积）
- 中段必然塌陷：40-60% 进度处没有"中点假胜利/假失败"这类结构性支点

### 诊断 2：人物是档案卡，不是欲望主体

`currentState/currentGoal/currentPressure` 是标签字段。Writer 拿到的是人物简历，不是"这个人此刻想从对面那个人身上拿到什么"。对手戏张力来自关系字符串 `currentStage`，而非双方欲望碰撞。所以对话容易滑回"提问→完整回答→下一个问题"——Reviewer 在检查这个，但生成侧没有强机制。

### 诊断 3：反 AI 味全靠负面清单

破折号禁令、解释腔计数、碎段率……这些是防下限手段。正向输入只有约 2400 字样本，且与本章题材无关时迁移很差。LLM 写作遵循的是"见过的最好文本"，不是"避开的坏模式"。

### 诊断 4：字数是一级目标，事件密度才是

75%-130% 区间管理让 Writer 把字数当任务。好章节的字数应由"这场戏演完需要多少字"决定。字数门会系统性产出注水段或赶戏段。

### 诊断 5：审稿者与写作者同源

Reviewer 与 Writer 默认共用项目级模型，审美相关性极高——它觉得"可以"的标准就是 Writer 的默认输出标准。十维评分没有一项对应"普通读者是否想往下翻"。（lengdu Reader 方向正确且已在主链，但修订上限仅 1 轮、其 verdict 不阻断发布。）

### 诊断 6：修订预算与问题类型错配

Reviser 的局部补丁只能修 S3 表面问题；S2 结构性问题（因果链缺失、人物失真）需要重写场景而非补丁。而 rewrite 是整章推倒，成本高且常"越改越平"。

## 三、修改方案（按投入产出排序）

### P0-1 加一层「卷级节拍规划器」（收益最大）

在 Director 之前新增 **Beat Planner** Agent：输入卷纲 + 已发布章节的事件账本，输出**未来 5-8 章的节拍表**，每个节拍声明：

- 戏剧功能（铺垫/递进/中点反转/假胜利/低谷/爆发/余波）
- 情绪债务（上一章欠读者的什么）
- 爽点类型与间隔
- 本章在卷弧光中的位置

Director 的输入从"章纲+状态"改为"章纲+状态+当前节拍"，14 种任务类型由节拍的戏剧功能推导，而不是自由选择。

落点：`chapters/` 下新增 beat-plan 模块与存储表；`novel-orchestrator.ts` Phase 1 前注入；复用现有 checkpoint 让用户确认节拍表。解决"每章都成立但全书平淡"和"中段塌陷"。做成**每卷一次批量规划 5-8 章**，避免每章多一次调用。

### P0-2 把「字数门」降级为「事件密度门」

- `computeChapterTargetWords` 只对 Writer 输出参考区间，不再触发 rewrite
- PostWriteGuard 改为检查**场景契约兑现度**：Director 契约里的 N 个"选择→后果"是否都在正文中有对应段落（轻量 LLM 对齐或关键词锚点），缺失才重写
- 字数异常只在 Reviewer 报告里作为 S4 提示

落点：`quality-policy.ts` 的 `WORD_COUNT_LIMITS` 从 gate 降为 advisory；PostWriteGuard 增加 contract-coverage 检查。

### P1-1 对手戏欲望碰撞卡（生成侧修对话问题）

`formatArrangedEntities` 为同场角色追加自动生成的「欲望碰撞」：A 想从 B 身上拿到什么 / B 实际能给什么 / 双方各自隐藏什么。数据来源已有——currentGoal/currentPressure + 关系 currentStage + 信息差表，规则模板拼装即可，无需新 LLM 调用。Writer 提示词里标为"本场对话的潜台词引擎"。

### P1-2 正向文风样本扩容 + 章节级风格检索

- 正向样本从 1200×2 扩到 ≥6000 字总量，按场景类型（对话场/动作场/静场）分桶，Writer 按本章主导场景类型注入对应桶
- 用本项目已发布且通过 lengdu 验收的章节作为动态正样本池（"本书最好的三章"），比外部参考迁移更准

落点：`writing-style-prompt-factory.ts` 的 `POSITIVE_SAMPLE_MAX_LENGTH` 与分桶逻辑；样本池复用 chapter-finalizer 的验收结果。

### P1-3 修订预算按严重度分配

- S2 结构性问题 → 不走 Reviser，走**场景级重写**：只重写出问题的场景，前后各留 200 字衔接上下文（ScenePlan V2 已有场景边界数据）
- S3 表面问题 → 维持局部补丁，轮次保持 2
- 整章 rewrite 仅留给 S1

落点：novel-orchestrator.ts 修订分支按 `issues[].severity` 路由；新增 scene-level rewrite 路径（ADR-0007 已有 scene-layering 基础）。

### P1-4 Memory 提取加校验回路

Memory Generator 输出 JSON 后加廉价确定性核对：正文中的矩阵实体名出现次数 > 0 但提取结果无任何对应 track 变更时，发一次定向补提取（只问该实体）。防止"漏提取→下一章状态陈旧"的单点故障。

### P2（值得做但不急）

- **Reader 门与发布联动**：lengdu `needs_attention` 时阻止 publish；`MAX_READER_REVISIONS` 从 1 提到 2；降级（自审）路径加强可观测性
- **审稿异源**：系统已支持按 Agent 配模型（见复盘第 3 条），先改配置把 Reviewer/盲审切到与 Writer 不同的模型档位验证；十维评分砍到四问——想不想往下翻 / 哪一段想跳过 / 谁的声音混了 / 本章改变了什么
- **风格专家卡 v2 收尾**：补齐文档标注缺失的"确定性指标差异报告"，让每次修订能对比 L1 形态指标

| 优先级 | 改动 | 解决的问题 | 主要落点 |
|---|---|---|---|
| P0-1 | 卷级节拍规划器 | 全书平淡、中段塌陷 | chapters/beat-plan + orchestrator |

## 五、复盘（2026-08-22 二次核查）

方案初稿完成后，对关键论断逐条回到代码核实，发现两处事实误差、两个新盲点，并补充风险清单与验证方法。

### 5.1 修正一：lengdu 已经在主链上，初稿表述有误

初稿称 lengdu Reader "不在主链上"、P2 要"进主链"。**核实结果：错误。** `novel-orchestrator.ts:1139-1248` 显示：Writer 输出通过 Guard 后即执行 `LengduWorkflow.run()`，且 `writerResult = lengduResult.content` 直接替换正文后才进入常规审稿。因此：

- 诊断 5 的表述已改为"已在主链，但修订仅 1 轮、verdict 不阻断发布"
- P2 措辞从"Reader 门进主链"改为"**needs_attention 与 publish 门联动 + 修订轮提到 2 + 自审降级的可观测性**"

### 5.2 修正二："完全没有卷级结构"论断过强，收窄为"缺节拍规划层"

`core/chapters/rhythm-controller.ts:21-24` 显示节奏模型已参考三幕剧+网文节奏理论，按章节位置映射小高潮/大高潮标签并给出情绪强度文本建议；伏笔实体也已有 `beats` 离散事件链字段（chapter-projection-fields.ts:67）。但这些是"位置→标签"的机械映射和出场章节数组，**不是带戏剧功能、情绪债务、爽点间隔的规划层**，也不消费事件账本。P0-1 论点成立但应收窄表述：Beat Planner 应**消费并取代** RhythmController 的标签建议作为 Director 输入，而不是与之并存造成双重节奏信号。

### 5.3 新盲点一：审稿异源的落地成本比预想低

`novel-orchestrator.ts:3032` 的模型解析链为 `run.perCallModelId ?? options.modelId ?? projectModelRef ?? agentConfig?.model`，即**按 Agent 配置不同模型的能力已存在**（`agentConfig?.model`，chapter-chat-runner.ts:387 亦同）。默认全用项目模型只是配置缺省，不是能力缺失。P2 的"审稿异源"可以先零代码改配置验证收益，再决定是否动评分体系。

### 5.4 新盲点二：上游输入质量无门（garbage in, garbage out）

`chapter-outline-generator.ts:364` 对空卷纲只 push warning 不阻断，卷纲仍会被截断 3500 字符注入章纲生成。若卷纲缺失或过薄，Beat Planner 会继承垃圾输入放大问题。因此 Beat Planner 应同时充当**卷纲质量门**：卷纲缺失/低于最低信息密度时拒绝规划并提示补纲，这比事后修章节便宜得多。

### 5.5 论证强化：样章证据与问题层级吻合

两份样章共同特征是"单场戏内张力成立、句子层面合格，但跨章递进无从判断"——《掌纹里的门》第 1 章感官与钩子均在水准之上，《第5章》玉佩通讯场潜台词自然。这恰好印证：瓶颈不在句子层（现有质量门有效），而在结构层（无人负责卷内曲线），支持"P0-1 优先于一切句子层优化"的排序。

### 5.6 风险清单

1. **流程变长**：Beat Planner 若每章一次会显著增加调用与人工 checkpoint，必须做成每卷一次批量规划。
2. **超短章风险**：字数门放松后可能出 2000 字以下的章，事件密度门的兜底实现必须先行或同步上线。
3. **场景级重写依赖 ScenePlan V2 数据质量**：该能力目前部分处于影子写阶段，场景边界覆盖率未审计，P1-3 动工前先审计 `scene_plans` 数据完整度。
4. **双重节奏信号冲突**：RhythmController 标签与节拍表并存时 Director 可能收到矛盾指令（见 5.2），需明确单一事实来源。

### 5.7 验证方法（A/B 对照）

同一卷纲 + 同一实体矩阵，旧链 vs 加节拍层各生成第 N~N+2 章，交给 lengdu Reader 盲评（不告知来源），对比三项指标：想继续读 / 跳读段数 / 人物声音可区分度。样本至少两组题材（都市异能、玄幻）以排除题材偶然性。

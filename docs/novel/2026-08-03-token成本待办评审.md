## B1. 第一阶段：处理 `novel_ask_story`

### 当前功能与真实白名单

- 工具定义：`core/novel-tools.ts` 的 `AskStoryParams` 与 `createNovelAskStoryTool()`。参数为 `projectId/question/chapterNumber?`；按关键词返回上一章、角色、冲突、伏笔、线索、风格、大纲或世界设定。传章号时优先通过 `ChapterBoundaryProvider.getChapterBoundaryContext()` 使用与注入相同的章前快照。
- 注册：`plugins/novel-plugin/novel-services.ts` 将 promptBuilder 注入 `createNovelTools()`，因而工具与注入路径共享章前边界语义。
- 实际白名单：`core/novel-agents.ts:66,92,107,125`。Director、Writer、Reviser、Reviewer 均挂一个 `novel_ask_story`。Reviser 另有每调用动态注入的 `novel_apply_revision`；Reviewer 另有 `novel_submit_review`；Director 另有 `novel_submit_narrative_task`。
- `runAgentOnce()` 会以 `NOVEL_AGENT_CONFIGS[agentType].tools` 过滤全局工具后再附加闭包工具，见 `core/novel-orchestrator.ts:1544-1554`，所以该白名单是实际生效配置，不是死代码。

### SEMI 层覆盖度与风险结论

SEMI 并非“工具返回的所有信息均已注入”。`buildChapterContextShared()` 确实注入章节信息、约束、已编排实体完整短卡、账本承接、边、信息差、最近摘要和锚点；Writer/Reviewer 的 Director 方案在 suffix 中注入，见 `core/novel-orchestrator.ts:1495-1537` 与 `prompt-builder.ts` 的 `buildChapterContextShared/buildChapterContextSuffix`。

但在已编排模式，`prompt-builder.ts` 明确不再调用 `formatStoryState()`，未编排实体被隔离，只剩当前章编排实体的完整字段。`novel_ask_story` 仍能返回全书大纲、风格指南、世界/势力/地点和不在本章的角色、冲突、伏笔、线索详情；其工具描述也就是这些能力。因此：

| Agent | 是否可先移除 | 依据与补救 |
|---|---|---|
| Director | 可以，P0 | 规划所需本章实体、约束、账本、摘要、信息差都已固定注入；若 Director 对未编排实体查询是业务需求，应让 arranger 在规划前产出候选关联，而不是让 Director 工具循环。保留 `novel_submit_narrative_task`。 |
| Reviewer | 可以，P0 | 正文、盲审意见、质量报告、Director 方案、shared/suffix 均已进入 prompt；验收不应临时检索全局故事。保留 `novel_submit_review`。 |
| Writer | 暂不建议无条件删除 | 当前章完整实体与锚点齐备，但未编排人物/世界设定、全书大纲和完整风格指南存在缺口。补法：由 Director 的结构化 task 增加 `requiredReferences`（只含必要实体 ID/名称），在 Writer 前由服务器确定性展开并作为 suffix 注入；无引用即 0 额外内容。 |
| Reviser | 暂不建议无条件删除 | `editor` context 模式会跳过 shared，虽带原文、结构化审稿报告和文风身份，但不保证带角色/世界/账本事实。优先在 Reviser 输入中加入由 Reviewer 问题位置导出的最小事实包，或在修订任务中显式传入 `requiredReferences`。保留 `novel_apply_revision`。 |

### 实施与灰度

1. 先删 Director、Reviewer 的 `novel_ask_story`；同步移除 prompt-builder 的“可调用该工具”引导，避免模型请求不可见工具。Writer/Reviser 暂维持。
2. 采集可审计基线：每角色 `payload_tool_count`、`llm_round_trips`、`payload_total_chars`、`input_tokens`，并从 session event/agent log 记录 `toolNames`；按项目/章节/模型分组对比。
3. 加一个仅开发或项目级 feature flag：`novelAskStoryPolicy = legacy | directorReviewerOff | allOffWithReferences`。不允许全局静默切换。
4. `directorReviewerOff` 连续至少 10 章或同项目 30 次调用：Director/Reviewer 工具数应分别仅保留闭包提交工具、round trips 的 P50/P95 不上升，章节完成率、review 结构化提交率、人工接受/修订比例不劣于基线。
5. Writer/Reviser 的 `allOffWithReferences` 先做 5 章受控样本，验证未编排事实错误、修订 patch 成功率、需要人工重写率；未达标退回 `directorReviewerOff`。回滚条件：任一角色完成率下降超过 5 个百分点、P95 输入 token 上升、事实一致性人工抽检明显退化、闭包工具提交率下降。

## B2. 第二阶段：arranger 与 memory payload 计量

### 可复用链路

`PluginSessionOptions.onPayloadStats` 已经是通用 Session API，`PluginManager` 在最终 provider payload 处调用，故不应复制 `measurePayload()`。在任意 `context.createSession({ ..., onPayloadStats })` 中本地累加即可。

- arranger：`NovelEntityGenerator.generateAndArrange()` 调 `planEntitiesFromOutline()`，再调 `generatePlanInBatches()`，其中可再有单项生成、批次重试。每处 `context.createSession()` 均应封装为 `runMeasuredSession()` 或接收 `PayloadStatsAccumulator`，在 `onPayloadStats` 累加。现有 usage 已按 `EntityPlanLogContext.usage`、`BatchGenerationRun.usage` 聚合，payload 采用完全同构的累加模式。
- memory：`NovelMemoryGenerator.generate()` 和 `runFullCalibration()` 各创建独立 session。给 `MemoryGenerationResult.logContext` 增加 payload aggregate，`ChapterFinalizer.runMemoryAgent()` 将其写入 `novel_agent_logs`。`retryStructuredMemory()` 也须返回完整测量结果，而不是只返回 summary；否则重试成本仍不可见。

### 日志粒度与 sessionId

推荐“双层日志”，不要只填现有一条 arranger 聚合行。

1. 保留现有 `agent_type='arranger'` 聚合行：其五列写所有调用累计值，`llm_round_trips` 为 provider 请求总数，`payload_tool_count` 为各调用最大工具数。这样原有面板和章节合计保持兼容。
2. 新增每个 LLM 子调用的明细行或子表，建议加 `parent_log_id` 与 `operation`（`plan/batch/retry/unbatched/fallback`）。每行都有自己的 payload、usage、sessionId、时序；聚合行可由这些明细求和。仅一条 59k token 日志无法说明是哪批次或重试造成成本。
3. sessionId 不应再留空：`PluginSessionHandle` 已公开 `sessionId`；在 `planEntitiesFromOutline/generateEntityBatch/generate` 返回上下文中携带并写明细。对已无法获取 sessionId 的旧单项路径，禁用不安全的“仅时间窗”归属；时间窗查询会在并发编排时串账。当前 `NovelEntityGenerator.readUsageFromLedgerWindow()` 不以 session 过滤，需作为同一阶段风险修正。
4. 077 五列足够记录聚合和明细的 payload 数值，不需再迁移；为了父子关联及操作名需要单独新增列/表。若本阶段只要求“补盲区总量”，可以不迁移，复用五列先落聚合值；若要求诊断/优化，必须做明细模型。

### 验收

- 结构化 memory 成功、瞬时重试成功、工具 fallback、每 10 章 calibration 都至少有可检索日志，且 payload 不再全部 0。
- arranger 聚合行的 `llmRoundTrips` 与其明细 provider 请求数一致；聚合 payload chars 等于明细求和；工具数为 max，不是求和。
- 用固定 mock provider 生成 1 次 plan、2 个 batch、1 次 retry，断言每层记录；并发两次 arrange 时 usage/session 不串账。

## B3. 第三阶段：重写闸门与 `chapter_budget`

### 当前缺陷复核

- Guard 自动重写：已改善。`core/novel-orchestrator.ts:482-773` 在同一 Writer while 循环中递增 `writerGuardRewriteCount`，不再从 Director 重跑。
- 用户整章重写：仍无独立次数约束。`guard_degraded` 的 `rewrite` 在约 `755-763` 调用 `createChapterWithFlow()` 时不传 `guardRewriteCount`；review 的 `rewrite` 分支也递归调用。因为已有 AsyncLocalStorage，上层 `budget` 实例会延续，总 LLM calls/token/耗时并不清零；但用户可以无限次确认重开，且 `MAX_GUARD_REWRITE` 被重置。
- `chapter_budget`：`enforceChapterBudget()` 仅对 `reject` 抛错，其他值统一 `acknowledged=true`，见约 `1337-1382`；`revise` 的“尽快收尾”当前无分支处理，属于空操作。

### 推荐设计

采用“总预算 + 分类计数”，而非只选其一。

- 保留既有全章总量：`llmCalls/inputTokens/wallClock` 是成本底线，且已经跨递归延续。
- 加类别计数：`fullChapterRewrites`（用户从 review 或 guard_degraded 明确要求整章重开）、`guardWriterRewrites`、`reviserRuns`、`reviewerRuns`；在预算检查点展示来源。分类使产品能区分质量保障的局部 Writer 重写与用户主动高成本重开。
- 新增 `maxFullChapterRewrites`，默认建议 1 或 2。达到上限时不再提供整章 rewrite，只允许“接受当前版”“Reviser 局部修订”“停止”。用户主动 rewrite 和 Guard 自动 rewrite 不共享同一配额：触发原因不同，分别计数；但共同受总 token/call/time 上限。
- 运行期状态用 `CreationRunContext`/`AsyncLocalStorage` 即可，递归调用天然延续，且本请求生命周期内没有恢复执行的状态一致性需求；不要为此先引入 DB。若未来支持进程重启后恢复 workflow run，再把 budget snapshot 持久化到 run 表。
- `chapter_budget` 的 revise 必须二选一：
  - 实现：设置 `run.budget.finishSoon = true`，跳过可选或高成本分支（Writer pushback 的再规划、Guard 重写、Review→Reviser、标题候选/recap、十章 calibration），保留当前 draft、一次必要审稿和必要 memory/persist；UI 文案改为“保存当前稿并跳过后续优化”。
  - 移除：若产品不愿定义上述精确语义，应删除 `revise` 选项与“尽快收尾”文案，保留继续/停止，不能展示无效承诺。

### 测试范围

1. chapter-budget 纯函数测试：分类累加、总量阈值、全章 rewrite 上限、`finishSoon` 决策。
2. orchestrator 流程测试：review rewrite 与 guard_degraded rewrite 连续触发后被拒绝重开但保留局部修订路径；总 budget 不因递归丢失。
3. finishSoon 集成测试：确定跳过哪些节点，最终正文/持久化/memory 仍完成；若选择移除则断言路由不接受该动作。
4. 回归：Guard 自动 Writer 重写仍最多两次，失败 retry 不占质量重写额度，chapter budget 的 reject 仍取消。

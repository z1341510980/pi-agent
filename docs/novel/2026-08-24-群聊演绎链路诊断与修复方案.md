## 1. 结论摘要

用户反馈"群聊没有演绎"。经代码走读 + 真实运行库（`~/.pi/wenlang-agent.db` 的 `novel_discussion_runs` / `novel_agent_logs` / `novel_agent_log_payloads`）取证，确认：

1. **第 4 章 2026-08-23 那次 completed 运行（runId `b616f15f`），`scenes` 字段为空数组，整场演出被静默跳过，正文是 Writer 盲写的。** 直接原因是 Director 输出格式（中文数字 `### 场景一：` + Markdown 表格字段）不匹配解析正则。
2. 即使演出成功执行，**Writer 也被提示词明确解除复用台词的义务**；实测台词正文复用率仅 44%（ch11）/ 15%（ch1）。
3. 演出格式校验过严且归一化具有破坏性：一次真实运行中 **62 次角色调用里 30 次是格式重试（48%）**，重试产出显著缩水。

核心判断：**问题不是缺一条链路，而是三个软契约（Markdown 解析、prompt 约束、轮数参数）在关键节点全部失守，且失守时静默降级。**

## 3. 根因清单（代码级）

按对症状的解释力排序。

### R1（首要）Director 场景拆分是唯一入口的脆弱文本契约

- 契约定义：`core/prompts/role-director-discussion.md:34-58`，第 58 行明说六字段是解析契约；
- 解析实现：`team-discussion-engine.ts:1637-1697`（`parseScenes`）、`:1710-1714`（`extractField` 要求行首 `-`）;
- 失败处置：只有 `logger.warn`（`:1676-1679`），无检查点、无 SSE 告警、无重试；
- V2 ScenePlan 是**事后影子写**（`novel-discussion-runner.ts:386-387`、`:516-550`），本次运行不读它；
- 结构化工具已存在但未用于群聊拆场：`novel-tools.ts:2198` `createNovelSubmitNarrativeTaskTool` 只有章节级约束，无逐场字段。

对应 `docs/novel/2026-08-05-剧情推进模型重构方案.md:59` 已记录的结构风险："△ Markdown 协议脆弱，运行快照同时承担业务计划"。

### R2 Writer 提示词明确解除复用义务，且无确定性校验兜底

- `role-writer-discussion.md:9`：「角色演出是现场素材，**不是必须逐条复述的提纲**」；
- `:27`：「角色演出是素材，**不是逐条复述的台词稿**……不能因为编织方便，把所有演出整理成完整、准确、轮流发言的对话」；
- 引擎侧编织要求同样没有正向强制（`team-discussion-engine.ts:1453-1461`，`:1457` 只写"补全"）；
- `runDiscussionPostWriteGuard`（`:1234-1322`）只查过短/拒答/复读/字数/角色名字符串出现，不查台词复用；
- Reviser prompt 不含 transcript（`:1577-1591`），修订阶段会二次抹平角色声音。

### R3 演出格式校验过严 + 归一化破坏性

### R6 续跑丢失临时角色

- `resumeSceneActing`（`team-discussion-engine.ts:443-464`）不调用 `resolveSceneCharacters`；

### R7 可观测性缺失（放大一切）

- acting 被映射成 `writing`（`novel-discussion-runner.ts:224`）：状态栏显示"写作创作中"，用户无法分辨"角色在对戏"和"Writer 在盲写"；

## 4. dsh-chaos 借鉴与取舍

dsh-chaos 是软件协作场景（channel/thread/task/kanban + Rust napi core），直接套用会走偏。值得搬的是工程手段，不是产品形态。

### 4.1 值得搬

| # | dsh-chaos 机制 | 证据 | 映射到 pi-agent |
| --- | --- | --- | --- |
| 1 | 四阶段 delivery 状态机 committed → notified → checked → model_seen，"未读"定义为 `model_seen_at_ms IS NULL` | `delivery/store.rs:272-273`、`index.ts:211-216` | 角色发言的生命周期应为可查询四态：已产出 → 已入 transcript → 已进 weave prompt → **已在正文中被复用**。现在"入了 history 就算完"，F1/F2/F3 全部不可见 |
| 2 | 结构化提交取代自由文本：Task 状态变更必须传 `expectedVersion` 做 CAS | `tools.ts:512-542`、`task/store.rs:200-217` | Director 用工具提交场景计划（对应已有的 `novel_submit_narrative_task` 模式），废除正则解析 |
| 3 | level-triggered 水位而非计数器：`pending_seq = MAX(...)`，自愈、幂等 | `delivery/store.rs:513-520` | "场景演出是否充分"不应由固定轮数决定，而应由义务清单（每个在场角色至少 1 次发言）清空与否决定 |
| 4 | 单事务原子提交 message + delivery + wake + change | `message/mod.rs:40-148` | 快照保存应与关键状态变更绑定；现状下证据 B 那种 62 次调用的运行可以毫无痕迹地消失 |
| 5 | generation 围栏：旧 Session 不能代新 Session 确认或写入 | `runtime.rs:227-251` | 续跑语义：已提交的演出不重演，只消费未读投递 |
| 6 | live projection prompt：身份 thunk + 版本单调守卫 | `agent-prompt.ts:38-42` | 我们的 `buildIdentityPrompt` 工厂已对齐，保持即可 |
| 7 | mention 精确 token 边界匹配（6 个反例单测）+ thread follow 门收窄扇出 | `delivery/store.rs:86-108`、`thread/mod.rs` | 在场角色集合应是显式的 cast 名单（present/focus/functional 分层，ChapterScenePlan 已建模），而非"全员兜底" |

### 4.2 不能搬（反面教材）

dsh-chaos 的 channel 唤醒**不看 @mention**：频道内任何发言唤醒所有 Agent 成员（`delivery/store.rs:408-425` 排除作者但不筛提及对象）。且全库无 maxTurns / token 预算 / 冷却 / 回环检测 —— `deliveries.attempt_count / next_retry_at_ms / last_error` 三列是从未被递增读取的空壳（只在 `delivery/store.rs:211-213` 被重置一次）。两个 Agent 在 channel 里互相回复会无限循环，README 也未声称解决了此问题。

小说共创比软件协作更容易失控（"继续写"永远是合理动作）。**pi-agent 的 Moderator 中心化调度比它安全，不要往"Agent 自主互相唤醒"方向改。**

## 5. 改造方案

### P0 止血：让演出不再静默丢失（1–2 天）

#### P0-1 Director 用工具提交场景计划，废除 Markdown 正则主路径

- 新建 `createNovelSubmitScenePlanTool(draft)`（放 `core/novel-tools.ts`，模式照抄 `createNovelSubmitNarrativeTaskTool:2198`）；
- schema 直接复用 `ChapterScenePlanScene`（`chapter-scene-plan.ts:38-53`：sceneKey/order/title/goal/locationText/timeText/povMode/povCharacterId/focusCharacterIds/presentCharacterIds/functionalCast/targetWords），校验复用 `validateChapterScenePlan`；
- **presentCharacterIds 直接是角色 id**，一次性消除名字匹配（R6）与临时角色 voice 缺失两个衍生缺陷；
- 引擎 planning 阶段经 `ctx.extraTools` 注入（通路已有：`invokeMember :1008` `tools: ctx.extraTools ?? []`）；
- `converge(scope='chapter')` 时读 `draft.plan`，`parseScenes` 降级为兼容回退，且回退路径必须 emit 显式警告事件；
- `shadowWriteDiscussionPlan` 从影子写升级为正式写（计划先落库再开演，scene plan V2 成为运行输入而非事后记录）。

#### P0-2 加"演出产出闸门"，禁止静默盲写

在 `runSceneLoop` 结束后、`weaveChapter` 之前检查：**每个场景至少 1 条 `type==='member' && fromId.startsWith('char-')` 的消息**。

三档处置：
1. 场景计划为空 / 全部场景零演出 → 抛检查点让用户选择"重新规划 / 转标准工作流 / 中止"，删除 `:1417` 的静默 fallbackPrompt 主路径；
2. 部分场景无发言 → emit 显式警告事件 + 向 history 写入 system 记录，让 Writer 明确知道"这场没演完"；
3. `hasAnyScript`（`:1412`）从"切换 prompt 的开关"升级为"必须上报的状态"。

#### P0-3 修 Moderator 降级硬编码

- `Moderator` 构造函数接受 `limits`，`:234` 的 `3` 改为 `limits.maxRoundsPerScene`；
- 降级轮转改为"未发言者优先"，保证在场角色各至少发言 1 次后才允许 converge；
- 降级产生的 converge 在 transcript 打标记，与正常收敛可区分。

#### P0-4 放宽演出格式校验，停止销毁内容

- 行数上限 6 → 12；
- 动作括号允许嵌套 `]`；
- `normalizeCharacterSpeech` 保留全部引号内容（去掉 `slice(0, 3)`），动作保留原文可提取部分；罐头兜底句仅在完全无引号时使用并记审计日志。

### P1 让演出真正进入正文（3–5 天）

#### P1-1 反转 Writer 提示词默认义务

- `role-writer-discussion.md` 改为正向硬约束："每个场景至少将本场推演中的 2 处台词或动作写入正文（句式可改写，语义不可丢弃）"；

#### P1-2 台词复用率闸门（对应 dsh-chaos model_seen 语义）

- `runDiscussionPostWriteGuard` 新增检测项：transcript 引号台词指纹（去标点 8 字窗口，见 §2.2 证据 C 算法）在正文中的命中率 < 40% 时，触发一次定向重写，重写 prompt 附上被丢弃台词清单；

#### P1-3 Reviser 可见 transcript

Reviser prompt（`:1577-1591`）注入各场景推演摘要，避免修订二次抹平角色声音。

#### P1-4 场景契约常驻化

- 当前场景契约作为固定段拼进角色 `buildContextPrompt`，不参与 10 条滑动窗口；
- 本场景关联的冲突无条件可见（其余仍按 participants 过滤），修 `buildCharacterVisibleContext:170-189`。

### P2 可观测与可控（1 周）

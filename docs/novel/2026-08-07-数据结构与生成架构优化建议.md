# 小说创作 Agent：数据结构与生成架构优化建议

> **已被《2026-08-07-数据结构与生成架构统一方案.md》取代，本文仅作诊断参考。**
> 本文的价值保留在：问题清单（冗余点 1-7）与方案草图；执行节奏与迁移安全以统一方案为准。

> 本文基于真实代码诊断（53 张表、工作流 4 角色生成管线），给出**具体可落地**的重构建议。
> 结论先行：你的两个判断都成立 —— 数据层确实存在 6 处可治理的冗余；生成层"角色区分 vs 上下文重复"的矛盾**已被 prompt 缓存机制部分缓解，但仍有 4 个结构性浪费点**值得优化。

---

## 一、现状概览（先说清"我们站在哪"）

**数据层**：`novel-migrations.ts` 共 53 张表。实体分型存储（角色/冲突/伏笔/线索/势力/地点/物品各一张表），另有一组 plan/scene 版本链（V2 影子写）和 story/memory 双账本。

**生成层**（`novel-orchestrator.ts` 工作流管线）：

```
Director → [检查点1] → Writer → PostWriteGuard → Reviewer → [质量门] → Reviser → Memory → 落库
```

每次 Agent 调用，`runAgentOnce` 组装四层上下文（`prompt-builder.ts`）：

| 层 | 内容 | 跨角色复用？ |
|---|---|---|
| STATIC | `buildSystemPrompt(projectId, agentType)` 世界规则+风格+角色定义 | 按角色不同，末尾打 cache breakpoint |
| SEMI-shared | `buildChapterContextShared` 章节信息/故事状态/实体档案/摘要 | **跨角色完全一致**，共享缓存块 |
| SEMI-identity | `buildAgentIdentity` 角色身份 | 按角色不同 |
| SEMI-suffix | `buildChapterContextSuffix` 角色专属指令 | 按角色不同 |
| DYNAMIC | 本轮任务指令 | 每次不同 |

关键机制：`prefixUserMessage` 顺序为 shared → identity → suffix，`promptCacheScope: novel:{projectId}:{chapterNumber}` 让同章所有角色走同一缓存路由，shared 前缀打 `cache_control` breakpoint 后**跨角色命中 prompt cache**；`semiLayerSharedCache` 再做单章内存级缓存。

> 结论：**"每个角色重复输入大量上下文"的问题，架构上已通过 shared 前缀 + prompt cache 化解了大半**（重复的是 bill 便宜的 cache-read，不是全价 input）。真正剩余的结构性浪费见第三节。

## 二、问题一：数据结构冗余点（6 处）与重构建议

### 冗余点 1：`chapter_spans` 在 6 张实体表重复（高优先级）

**现状**：`novel_conflicts`(:558) / `novel_factions`(:559) / `novel_foreshadowing`(:659) / `novel_clues`(:846) / `novel_items`(:868) / `novel_narratives`(:1365) 都有一列同构 JSON `chapter_spans: [[start,end],...]`，连语义都相同（"这个实体在哪几章出场"）。

**问题**：实体类型新增就要再抄一列；查询"第 N 章所有出场实体"要 union 6 张表；出场区间与实体主数据耦合，版本/重写时难以独立追踪。

**重构建议**：抽成关联表，主表只留实体自身事实：

```sql
-- 目标态：实体出场区间统一
CREATE TABLE novel_entity_appearances (
  entity_type TEXT NOT NULL,        -- 'conflict'|'foreshadow'|'clue'|'faction'|'location'|'item'|'narrative'
  entity_id   TEXT NOT NULL,
  chapter_no  INTEGER NOT NULL,     -- 摊平成单章一行，替代 JSON 区间
  PRIMARY KEY (entity_type, entity_id, chapter_no)
);
CREATE INDEX idx_appearances_chapter ON novel_entity_appearances(chapter_no, entity_type);
```

- 摊平单章一行比 JSON 区间更好：可建索引、"本章出场"变一次索引查询，无需解析 JSON。
- 查询第 N 章全部出场实体：`SELECT * FROM novel_entity_appearances WHERE chapter_no = ?`，一次搞定。
- 后端对应抽一个 `EntityAppearanceStore`，`syncChapterDimensions`（`chapter-finalizer.ts:1527` 现在逐表回填 chapterSpans）改为批量写关联表。

**迁移**：新增表 + 数据搬运脚本 + 读路径切换 + 保留旧列一个版本（或直接删，因为写路径只有 `syncChapterDimensions` 和 `createXxx` 两处）。

### 冗余点 2：已废弃列未清理（低成本，顺手做）

**现状**：`novel_conflicts`(:465-466) 和 `novel_factions`(:472-473) 的 `first_chapter`/`last_chapter` 列，代码注释明确"保留为兼容字段，不再读写"(:556)；`novel_locations`(:378) 的同名列还在读写。

**建议**：写路径不再使用后直接 `DROP COLUMN`（SQLite 3.35+ 支持），把"兼容"写死成"已清理"，避免下一个人继续猜。

### 冗余点 3：双版本链并存（高优先级）

**现状**：`novel_chapter_versions`(:820) 与 `novel_chapter_content_revisions`(:1173) 列几乎全同（content/word_count/phase/agent_type/trigger + 版本号），迁移注释自述"迁移期双写"(:1170)，但**两个表都还在写**——同一正文在 `novel_chapters.content` + 两张版本表 = **至少 3 份全文**。

**建议**：确认 V2 版本链（`content_revisions` + `current_content_revision_id`）为唯一事实源，`novel_chapter_versions` 冻结为只读归档，写入路径摘除，下一个大版本删表。同时给 `content_revisions` 增加 `retention` 策略（默认保留最近 N 版全文，更早的存 hash + 摘要）。

### 冗余点 4：scene 三张角色关联表同构（低成本）

**现状**：`novel_scene_focus`(:1262) 与 `novel_scene_presence`(:1268) 两表结构完全一致（仅 `scene_revision_id`+`character_id` 复合主键，语义 focus/present 不同），`novel_scene_functions`(:1274) 只是多两列。

**建议**：合并为一张带 role 的关联表：

```sql
CREATE TABLE novel_scene_cast (
  scene_revision_id TEXT NOT NULL,
  character_id      TEXT NOT NULL,
  role              TEXT NOT NULL,   -- 'focus' | 'present' | 'functional'
  function          TEXT,            -- 仅 functional 时
  prominence        REAL,
  note              TEXT,
  PRIMARY KEY (scene_revision_id, character_id, role)
);
```

同时 `novel_scene_revisions` 里的 `chapter_id`/`project_id` 可由 `scene_id` 推出（调研确认 :1235），一并去掉，层级从 plan→scene→revision→cast 四层收敛为三层。

### 冗余点 5：`novel_agent_logs` 巨型全文行（中优先级）

**现状**：`system_prompt` / `chapter_context` / `user_message` / `task_input` / `user_instructions` / `result` / `error` 全是 TEXT 全文（:433-456），一行可达数万字符；同时 `display_agent_type/display_agent_name` 是 `agent_type` 的副本，`result_length`/`payload_*_chars` 是派生值。

**建议**（日志是审计不是运行时数据，值得单独设计）：
- 大文本**外置**：`novel_agent_logs` 只留元数据（agent/session/耗时/token/状态/长度），正文存 blob 表或文件，按需读取（AgentLog 面板本来就是低频查看）。
- 或者至少**压缩**：超过阈值的 prompt/result 存 `gzip` 后的 BLOB，读取时解压。
- 副本列（display_agent_type）删除，派生值（result_length）改为查询时计算。

### 冗余点 6：story_events 与 memory_events 双账本（需产品决策）

**现状**：`novel_story_events`(:894，自引用树 parent_event_id) 与 `novel_memory_events`(:311，后扩展出 story_event_id/scene_order/target_entity_type 等列，:931-937) 职责高度重叠——同一"章节里发生了什么"被记了两套账。

**建议**：二选一，明确职责：
- 方案 A（推荐）：`novel_story_events` 为唯一"故事事件"账本（含实体关联表 `novel_story_event_entities`），`memory_events` 降级为"记忆 Agent 操作日志"（只记 applyChanges 的原始操作），不再承载语义事件。
- 方案 B：反过来，保留 memory_events 并删除 story_events。取决于哪个先被页面消费。

### 冗余点 7（附带）：派生值 / 冗余标识

`word_count` 在 chapters / versions / content_revisions 三处存派生值 → 只保留主表 + 查询时 `length()` 计算；`project_id + chapter_number` 双标识大量出现 → 统一经 `chapter_id` join（已走 chapter_id 的表不动，只清理仍用双标识写的新代码）。

### 分表 vs 超类型表：为什么建议"保留分表 + 抽公共列"

各实体字段差异大（冲突有 intensity/stage/participants，伏笔有 category/plantMethod/beats，线索有 pointsTo/progress）。合并成一张超类型表会引入大量 NULL 列，查询要按类型分支，得不偿失。**正确的做法是保留分型表，只把"跨类型公共的横切面"（出场区间、版本链、审计、名称索引）抽出来共用**——出场区间正是第一个要抽的。

## 三、问题二：工作流模式 vs 上下文利用

### 3.1 现状机制盘点（已经在解决的）

| 机制 | 代码位置 | 作用 |
|---|---|---|
| shared 前缀跨角色复用 + cache breakpoint | `runAgentOnce` / `prompt-builder.ts:896-900` | 同章 4 个角色的"章节信息+故事状态+实体档案"只按全价算一次，后续都是 cache-read |
| `promptCacheScope: novel:{p}:{ch}` | `novel-orchestrator.ts:2041` | 同章所有角色同一缓存路由键 |
| `semiLayerSharedCache` | `novel-orchestrator.ts:1880` | 单章内存级 shared 字符串缓存 |
| contextMode 裁剪 | `runAgentOnce`（full/editor/identity_only） | Reviser 用 editor（不带全书共享）、盲审用 identity_only，省掉大段 shared |

### 3.2 剩余的结构性浪费（4 个，按收益排序）

1. **实体档案全量注入**：`formatArrangedEntities`（`prompt-builder.ts:1613`）把本章所有出场实体的**完整档案**（含大段中文映射、plotRole 定义、每个实体的 description）一次性拼进 shared。角色只有一句话作用也带上全文。→ 上下文分块可解决（方案 A）。
2. **跨章零复用**：`semiLayerSharedCache` 只在单章运行内有效；下一章从零重建 shared（虽然命中 prompt cache 的 shared 部分，但**新章缓存未写入的部分仍全价**——模型切换/Provider 分布式缓存失效时尤其明显）。→ 跨章增量可解决（方案 C）。
3. **角色区分靠"上下文差异"而非"身份差异"**：`buildSystemPrompt(projectId, agentType)` 按角色组装，世界规则/风格模板在每个角色 system 里各存一份（依赖缓存合并）。角色应该只有**薄身份 + 工具白名单**，共享部分彻底放 shared。→ 方案 B。
4. **Writer 全章一次性生成**：19k input 长上下文中，真正驱动本章的实体/事件只占小部分；V2 `ChapterScenePlan`（scene 拆分）已就绪但影子写阶段未切换 Writer 输入。→ 方案 D。

### 3.3 优化方案（按可实现性排序，均可独立落地）

#### 方案 A：上下文分块 + 引用式注入（Context Chunk 协议）

把 shared 拆成命名的、可独立缓存/命中的 chunk，注入时用"**摘要 + 指针**"代替全量，Agent 需要细节时通过既有只读工具（`novel_ask_story` 已存在）按需拉取：

```ts
// 伪代码：Context Chunk Registry
interface ContextChunk {
  id: string                       // 'chapter-info' | 'story-state' | 'arranged-entities' | 'ledger' | 'hooks' | 'style-fingerprint'
  versionKey: string               // 缓存键的一部分，如 `entities:v3:ch4`（hash(实体快照)）
  build: (ctx) => string           // 惰性构建
  /** 注入模式：full = 全量；summary = 只给摘要+指针 */
  mode: 'full' | 'summary'
}

// shared 组装时：
const storyStateChunk = chunks.get('story-state')
const shouldFull = storyStateChunk.entitiesCount <= 8   // 小章全量
shared = join(
  shouldFull
    ? storyStateChunk.build(ctx)
    : `${storyStateChunk.summary(ctx)}\n\n> 需要某实体的完整档案时，调用 novel_ask_story 按名称/ID 查询。`,
  ...
)
```

- 收益：实体多的章节（>8 个出场实体）shared 体积可砍 30-50%。
- 前置条件：`novel_ask_story` 工具已存在（`resolveNovelAgentToolNames` 按角色白名单发放），只需保证被摘要的 Agent（Writer/Reviewer）都带该工具。

#### 方案 B：角色薄身化 —— 区分"身份"与"知识"

```ts
// 现状：每个角色 system 都带全套世界规则 + 风格模板（角色间重复）
system = worldRules + styleGuide + roleDefinition(agentType)

// 目标：世界规则/风格进 shared（全角色一份），system 只剩角色身份
system = roleIdentity(agentType)          // 很薄：你是谁、你的职责、工具白名单
shared = worldRules + styleGuide + chapterContext   // 一份，全角色缓存命中
```

`buildAgentIdentity` 已经做了"身份从 system 移到 DYNAMIC 层"的迁移（`prompt-builder.ts:835` 注释），说明方向已被验证；把世界规则/风格也并入 shared 即可。**缓存键不变**（`promptCacheScope` 按章），迁移成本低。

#### 方案 C：跨章增量共享缓存

```ts
// 伪代码：跨章 shared diff
const prevShared = chapterCache.get(projectId, chapterNumber - 1)
const currShared = buildChapterContextShared(...)
if (prevShared) {
  // 只把"变化的部分"作为新 shared：上一章摘要 + 本章实体/钩子 delta
  const delta = diffShared(prevShared, currShared)
  shared = prevSharedFingerprint + delta
}
// 失效策略：实体/冲突/伏笔任何一次 memory applyChanges 后，失效该章缓存
invalidateOn('entity-change', (p, ch) => chapterCache.delete(p, ch))
```

- 注意：prompt cache 本身会缓存 shared 文本，跨章 diff 的收益在于**减小每次请求的传输体积 + 未命中时的重建成本**，不是替代 prompt cache。
- 失效点很明确：`applyChanges`（`novel-memory-generator.ts:1065`）与 `syncChapterDimensions` 是仅有的实体变更入口。

#### 方案 D：场景级生成（复用已有 V2 ScenePlan）

`ChapterScenePlan` / `ChapterScene`（`packages/shared/src/novel/index.ts:2630/2647`）与 `novel_scenes` 系列表已就绪，目前是影子写（`shadowWriteDirectorPlan`，不改生成行为）。下一步把 Writer 从"整章一次生成"切为"逐场景生成"：

```ts
// 伪代码：per-scene 生成（writer 输入按场景裁剪）
for (const scene of plan.scenes) {
  writerInput = buildScenePrompt({
    scene,
    // 只带本场景 POV 角色 + focus/present cast + 场景地点/时间/目标
    cast: sceneCastOf(scene.id),        // 来自 novel_scene_cast（合并后）
    // 章级 shared 只带摘要 + 全局事实，不重复整章实体档案
    shared: summarizeChapter(plan),
  })
}
```

- 收益：单次调用上下文从 19k 降到场景级（3-5k），且**每场景只注入本场景实体**，token 与 cache 命中都更好。
- 与方案 A 叠加：场景 cast 本来就从 `novel_scene_cast` 读，天然是"按需注入"。

#### 方案 E（补充）：检索式故事状态

把 `formatStoryState` 的全量注入改为"**索引 + 按需查询**"：shared 只放实体 ID + 一句话摘要（50 字内），完整状态靠 `novel_ask_story` 工具在生成中按需拉取。适合故事中后期实体数量大的章节；前期小章保留全量（避免工具调用往返）。

## 四、目标态架构（一图流）

```
数据层（目标态）                                  生成层（目标态）
┌──────────────────────────┐          ┌──────────────────────────────┐
│ 实体分型表（保留，瘦身）      │          │ STATIC   角色薄身份（按角色缓存）     │
│  - 只存自身事实            │          │ SEMI     世界规则+风格+章节 shared     │
│  + novel_entity_appearances│◄────────►│           （全角色一份，缓存命中）     │
│    （出场区间统一）          │ 读-写-再读  │  SEMI     角色专属 suffix（薄）      │
│  + novel_scene_cast(role)  │          │ DYNAMIC  任务指令（每次不同）          │
│  + 单一版本链 content_revs  │          │  注入 = 分块摘要 + 指针 + 按需拉取      │
│  + story_events 唯一账本    │          └──────────────────────────────┘
│  + agent_logs 大文本外置    │                    ▲
└──────────────────────────┘            promptCacheScope 按章 + 跨章 diff
```

### 迁移路径（建议分三期，每期独立可回滚）

| 期 | 内容 | 风险 | 收益 |
|---|---|---|---|
| P1（低风险） | 删废弃列；scene_cast 三表合并；`novel_chapter_versions` 冻结只读 | 低（写路径只有 2-3 处） | 表数量 53→48，消除双版本链 |
| P2（中风险） | 出场区间抽 `novel_entity_appearances`；agent_logs 大文本外置 | 中（查询路径多） | 查询变简单，日志表瘦身 90%+ |
| P3（架构级） | 上下文分块（方案 A）+ 角色薄身化（B）+ 场景级生成（D） | 高（改生成行为） | token 成本下降 30-50% |

## 五、风险与取舍（诚实清单）

1. **分块注入的召回风险**：Agent 需要细节时如果忘了调 `novel_ask_story`，会写出与实体档案不符的内容。缓解：摘要里明确提示"需要完整档案时调用工具"，且 PostWriteGuard 的矩阵角色缺失检查兜底。
2. **跨章 diff 的复杂度**：diff 算法本身要维护；如果共享段大部分相同，收益有限。建议先量化"相邻章 shared 重复率"再决定投入。
3. **场景级生成会改变落库粒度**：Writer 逐场景输出后，正文合并与质量门（prose-shape 全局扫描）需要按章整体复检，验收逻辑要适配。
4. **版本链合并涉及数据迁移**：P1 的冻结不等于删除，归档期要保留回滚出口；`novel_chapter_versions` 有页面消费（`chapter-version-panel.tsx`）的话要先切换读源。
5. **prompt cache 不是银弹**：它只省"重复读取"的账单，不省首轮全价；模型/Provider 切换、缓存淘汰都会让 19k 上下文重新全价——这正是方案 A/C/D 值得做的原因。

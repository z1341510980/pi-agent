## 3. 过程中做的取舍（为什么这么做）

1. **双写只做两个收口点，而非逐表插桩**：
   - ai-arrange 的 `generateAndArrange` 返回前统一写 6 类 → 覆盖"编排出场"
   - `syncChapterDimensions` 结尾统一写 5 类 → 覆盖"正文确认 + Memory 新建 + 复用实体"
   - **Memory 不再单独插桩**：它创建的实体在正文确认时被 sync 兜底（`before/after` diff 已把它算进 involved）。省掉 applyChanges 里 6+ 处插桩，且不遗漏。
   - 代价：Memory 阶段到正文确认之间的窗口期，appearance 还没写（对账/读切在这窗口读到旧数据）——可接受，最终一致。

2. **读切用"返回 null 回退"而非强制双路径**：
   - `listChapterAppearanceIds` 在 Read 关闭时返回 `null`，调用方走原 `chapterSpans` 过滤。
   - 好处：零行为变化（Flag 关=现状），读切可独立灰度、可回滚。
   - 读切只接入 2 个高价值点（生成路径 conflictTargets + 编排 clue 复用）；`entity-admission-policy` 的 `isActiveInChapter` 是**无 store 的纯函数**，接入需改签名牵连调用方，暂保持原逻辑——正确性不受影响（appearance 与 chapter_spans 数据等价）。

3. **角色出场不进 appearance**：角色出场事实在 `character_history`（历史账本），P2 只统一"有 chapter_spans 的实体"（conflict/foreshadow/clue/faction/location/item/narrative）。避免两套出场事实源打架。

## 4. 发现的问题与风险

1. **chapter_id 依赖**：appearance 以 chapter_id 为主键维度，双写时需 `getChapter` 解析；**旧数据/反推流程若章节未落库会写不进去**（`recordAppearancesIfEnabled` 已对无法解析 chapterId 的情况静默跳过）。真实库对账时需注意历史章节的覆盖。
2. **climaxChapter 语义**：读切后 novel-engine 的冲突判定保留 `isClimaxChapter || noSpans` 兜底——**appearance 缺失（未双写的老数据）仍能靠 climaxChapter 命中**，不会因读切丢冲突。
3. **一致性的最终收敛**：双写是"先写 chapter_spans、后写 appearance"（sync 内顺序）；若中途异常，appearance 可能少写 → 由对账 CLI 兜底发现。
4. **narrative 类型**：表结构与对账 CLI 支持 narrative，但**双写入口未接入 narrative**（编排不生成 narrative，Memory 的 narrativeCreates 未被 sync 收口）——narrative 的 appearance 暂为空，对账会报 mismatch。**待补**或从对账白名单排除。

### 7.2 过程中发现并修复的 CLI 缺陷

1. **chapter 映射语义错误**：`chapterIdByNumber` 存的是 `chapter_number → chapter_id`，却用 `chapter_id` 反查 → appearance 侧恒为空，对账永远全 mismatch。修复为 `chapter_id → chapter_number` 正查。
2. **location 盲区**：`appear_chapters` 是数字数组 `[1,2,3]`，`expandSpans` 的区间解构展开得空集 → location 8 行从未被检查。回填脚本单独用 `expandChapterList` 处理。
3. **未落库引用口径**：spans 指向未落库章节（E2E 测试项目 `[[2,4]]` 只落库 1 章；真实小说 faction 规划第 14 章但正文只写到 11 章）是**合法规划**而非数据缺失——新增 `unpersistedRefs` 单独统计，不阻塞 `acceptable`。

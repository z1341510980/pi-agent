# 对话化交互形态设计规格（create-flow 与群聊）

> 日期：2026-08-15
> 方案：对话为壳、工作流为核（方案 A）
> 实施范围：`apps/agent-server` 后端与 `apps/desktop` 桌面端
> 前置：缓存与监控一体化（迁移 100 已落地，本方案不得破坏其调用序列确定性）

## 1. 背景与目标

当前 create-flow 是纯工作流（9 阶段状态机 + 6 类检查点门），群聊是编排器驱动的多智能体剧本（Moderator 决定发言）。共同问题：**缺少人工反馈通道**——流程进行中用户无法插入修改意见，意见只能通过检查点决策的 comment 字段，或等流程结束后复盘。

本方案目标：

1. **create-flow 中途插话**：流程任意阶段，用户消息注入下一个 Agent 的上下文。
2. **群聊中途插话**：用户消息进入讨论 history，Moderator 下一轮感知并可改变讨论走向。
3. **对话流触发工作流**：对话输入框用确定性命令启动/恢复/重写 flow。
4. **检查点对话化**：阻塞式检查点改为对话内嵌卡片，等待期间输入框保持可用。

## 2. 非目标

- 不拆状态机：9 阶段流转、事务、断点恢复、预算控制、阶段门全部保留。
- 不引入 LLM 意图识别触发命令（误触发成本高，命令先用确定性前缀语法）。
- 不改 chapter-chat：它已是对话形态，作为「无运行中 flow 时」的默认对话后端。
- 不改缓存遥测链路：调用序列仍由 orchestrator/engine 确定，cacheKey 分域不变。

## 3. 设计

### 3.1 统一插话通道（后端核心）

新增端点：

```text
POST /api/plugins/novel/projects/:projectId/flows/:flowId/messages
Content-Type: application/json
{ "content": "打斗戏改用棍", "targetAgent": "writer" }
```

- `content`：必填，非空，长度 ≤ 4000 字符。
- `targetAgent`：工作流可选（director/writer/reviewer/reviser/memory）。缺省注入「下一个将被调用的 Agent」；群聊不接受该字段，由 Moderator 自主分发。
- `flowId`：create-flow 的 flow 实例 ID 或 discussion run ID。运行中才接受插话；无运行中 flow 返回 409。

行为分两条路径：

**create-flow**：orchestrator 现有 `setUserMessages` 是「覆盖」语义，插话另设**队列 append** 通道。每次 `runAgentOnce` 前 drain 队列：无 `targetAgent` 的消息注入下一个 Agent；定向 director/writer/reviewer/reviser 的消息等对应 Agent 被调用时注入。注入时在 Agent 上下文中以「用户中途反馈」显式区块呈现（区别于任务指令），Agent 能感知这是流程进行中的人工修改意见。

**Memory 定向契约**：`targetAgent=memory` 只在 Finalizer 进入结构化 Memory 分析时消费，作为本轮“提取关注点”核对已定稿正文。该文本被标记为不可信数据，不是故事事实或写库指令，不能覆盖正文、当前实体状态或 JSON 输出协议；正文无明确证据时必须忽略。最终变更继续经过既有结构化解析、`applyAnalysis` 校验和短事务提交，禁止把自由文本直接转换为数据库操作。

**群聊**：`TeamDiscussionEngine` 的 history 增加「pending 用户消息」队列。Moderator 下一轮 `decide` 前先把队列消息以 user 角色写入 history（携带 `injected: true` 元数据），Moderator 决策时可围绕它调整点名与议题。消息不重排已有 history，只追加。

**即时回显**：插话成功即写 `chapterChatStore`（三模式共用持久层，flowMode 标签区分）并推 SSE 事件 `novel:user-message`（携带 flowId、content、targetAgent、状态 `queued`）。消息被实际注入后再推 `injected` 状态更新（create-flow 在 `runAgentOnce` drain 时，Memory 在 Finalizer 接收关注点时，群聊在 Moderator 感知时）。

### 3.2 检查点对话化（前端呈现层）

- 检查点从「锁面板的模态」改为对话流内嵌卡片：正文 + 确认/否决按钮 + 修改意见输入框。
- 卡片内修改意见映射到既有 `POST /checkpoint/:id/decision` 的 comment 字段，后端协议零改动。
- 等待检查点期间输入框**保持可用**：用户可先插话（进 §3.1 队列）再确认检查点，二者不互斥、不竞态（队列与检查点决策是两个独立通道）。

### 3.3 对话流触发工作流

输入框命令语法（确定性前缀，不做模糊匹配）：

| 命令 | 行为 |
| --- | --- |
| `/写 N` 或 `/write N` | 启动第 N 章 create-flow |
| `/继续` 或 `/resume` | 恢复最近一次可续跑流程。优先使用当前结果中的群聊或 workflow runId；工作流结果丢失时以 `latest` 查询最近快照。群聊恢复已保存的 transcript/scenes，workflow 恢复已完成阶段产物 |
| `/重写 N` 或 `/rewrite N` | 触发第 N 章 rewrite 路径（章节须已存在） |
| `/群聊 N` 或 `/discuss N` | 启动第 N 章群聊（章节须已存在） |

- 命令解析在前端（输入框拦截），命中即调对应既有启动端点（不新增后端触发逻辑）。
- 未命中命令的普通文本：有运行中 flow → 走插话端点；无 → 走 chapter-chat。
- 工作流运行中，输入区“反馈给”选择器可选下一位 Agent 或五类定向 Agent；群聊不显示定向选择器。
- flow 各阶段产出继续以消息卡片进流（SSE 已有，前端把「阶段进度」升级为「消息」语义）。

## 4. 错误与兼容

- 插话落库失败仍返回 201（消息已排队，落库仅影响历史回放，失败仅记服务日志），端点级异常返回 5xx。
- flow 结束时队列中未注入的消息：随 flow 结束清空，chapterChatStore 中该消息标记 `dropped`（用户可见未被采纳，不静默丢失）。
- `flowId` 使用 `RUN_STARTED.runId`，后端按当前项目活动任务反查章节；客户端也可附带 `chapterNumber` 加速定位，但两者不一致时必须返回 409，禁止旧运行向同章新运行注入。
- 旧版本客户端无插话调用，端点纯增量，无兼容负担。
- 断点恢复：插话队列不进快照（恢复后从空队列开始），已落 chapterChatStore 的消息作为历史可见。

## 5. 测试与验收

后端：

- 插话端点：参数校验（空 content/超长/非法 targetAgent/无运行中 flow 409）。
- orchestrator 队列：append 不覆盖、drain 注入下一个 Agent、targetAgent 定向注入、Memory 只读关注点、flow 结束清空。
- engine 队列：Moderator 感知插话、history 追加不重排、injected 状态推送。
- 既有 create-flow/群聊/检查点测试零回归；缓存遥测测试零回归。

桌面端：

- 插话发送 → 「已排队/已注入」状态流转展示。
- 工作流定向选择器透传 targetAgent；群聊不显示定向选择器。
- 检查点卡片：确认/否决 + 修改意见提交走既有 decision 端点。
- 输入框常开：等待检查点时可发插话。
- 命令解析四条 + 普通文本分流。

验收：

1. create-flow 运行中插话，下一个 Agent 的日志（novel_agent_logs）userInstructions 或 metadata 中可见该消息。
2. 群聊运行中插话，Moderator 下一轮决策输入包含该消息。
3. 检查点等待期间可插话且互不干扰。
4. `/写 11` 从对话框直接启动第 11 章流程。
5. 定向给 Memory 的插话在日志中显示为不可信提取关注点，正文无证据时不产生状态变更。
6. 全量回归绿（agent-server + desktop tsc 与 vitest）。

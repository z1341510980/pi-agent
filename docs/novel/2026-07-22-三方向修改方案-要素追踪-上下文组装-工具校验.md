# 小说创作系统三方向修改方案

日期：2026-07-22
状态：决策点已全部确认（见第 5 章），可按 PR1 → PR4 实施
范围：要素变化追踪与 AI 辅助生成 / 创作时上下文组装 / Tool 调用行为校验

***

## 0. 现状总结论

代码核查结论：三套能力约 80% 已落地（novel-plugin + ChapterFinalizer + 故事矩阵），三个需求各自的核心差距是：

| 需求             | 已有                                                     | 核心差距                                                   |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 1. 要素追踪 + 回退重生 | 8 类要素表、统一事件账本、每章全量快照、正文版本回滚                            | **要素状态没有"按章回退"能力**：重新生成最新一章时读不到 N-1 快照，且上次生成的状态变更已污染活库 |
| 2. 上下文组装       | 三层缓存 prompt-builder、arrangedEntities 精准注入、按 Agent 差异注入 | **查询工具没有"章节时点"语义**，历史章节重写时工具结果与快照上下文互相矛盾；上下文对作者不透明     |
| 3. Tool 调用校验   | 工具权限白名单、writer maxToolCalls=2、agent\_logs              | **没有工具调用序列的观测手段**，"AI 是否主动循环调工具"无法验证                   |

## 1. 需求一：要素变化追踪与 AI 辅助生成

### 1.1 数据模型现状与多对多关联

8 类要素 + 关系 + 世界观要素均有独立表（迁移 013-026）。多对多关联目前有两套并存：

| 机制              | 位置                                                                                            | 问题                                 |
| --------------- | --------------------------------------------------------------------------------------------- | ---------------------------------- |
| 实体上的 JSON 数组字段  | `linkedCharacters` / `linkedClues` / `participants` / `allies` / `enemies` / `appearChapters` | 无法反向查询、无法级联、与 edges 可能不一致          |
| `novel_edges` 表 | sourceType/targetType/edgeType（15 种）/auto                                                     | 删除实体时已能级联清理（`deleteEdgesByEntity`） |

**建议**：以 `novel_edges` 为多对多关联的唯一事实源，实体 JSON 字段降级为读缓存（写路径先写 edges 再同步 JSON）。当前不新增关联表；若后续出现高频反向查询再评估抽 `novel_entity_relations`。

### 1.2 变化追踪现状

- **统一账本** `novel_memory_events`：ChapterFinalizer 30+ 处 `recordEvent`，8 类 `*_change` 事件全覆盖。
- **dimension 集中推断**：`novel-memory-store.ts` `inferDimension()` 按 eventType + 变更字段名回填 dimension/valueType，供矩阵子轨道消费。
- **每章全量快照** `novel_memory_snapshots`：`chapter-finalizer.ts saveChapterSnapshot()`。
- **角色字段级历史** `novel_character_history`：5 个动态字段逐章 oldValue/newValue/reason。

### 1.3 子轨道分类核对（请逐条确认）

**我发现的 7 个问题点**：

1. **faction.activity 是死规则**：`matchFields: []`（第 381 行），任何 faction\_change 事件按字段名都匹配不上，只能靠 fallback 兜底命中，语义模糊。且势力真正值得追踪的是 **strength（实力消长，4 级）**，目前缺失。建议：删 activity，新增 `faction.strength`（level）。
2. **character.pressure 类型错误**：`currentPressure` 是自由文本（"当前压力"），却标为 level（等级数值轨道），子轨道会按数值渲染 sparkline/色档，语义错乱。建议改为 text。
3. **foreshadow\.payoff\_chapter 命名误导**：matchFields 是 `lastChapter`（最后出现章），不是 `recoverByChapter`（计划回收章）。回收计划才是创作关心的维度。建议 matchFields 改为 `recoverByChapter`，或改名 `last_chapter`。
4. **信息差缺核心轨道**：信息差的本质是"哪些角色知道"，现在只有读者视角（reader\_knows/revealed）。建议新增 `info_layer.knowledge_spread`（set：知情角色集合变化，matchFields `characterKnowledge`）。
5. **item.function 是静态属性**（创建时确定的功能定位），作为变化轨道全是噪音。建议仅 created 时记录，移除独立轨道。
6. **relationship.updated / hint 是元数据**：`lastUpdatedChapter` 每章必变、无信息量；建议移除 updated 轨道，hint 视使用情况保留或移除。
7. **location.appear / item.appear 是单调累积数组**：每出场一章数字徽标 +1，作为"变化"轨道信息量低。出场更适合用区间带（appearance band，折叠态已有类似渲染），建议从子轨道移除或改渲染语义。

### 1.4 关键差距：重新生成不满足"基于上一章快照"

**代码实证**：

1. `prompt-builder.ts:2332 getStoryState()` 只有在"重写历史章节"（`latestKnownChapter > chapterNumber`）时才读 N-1 章快照。**重新生成最新一章时该条件不成立**（3 > 3 为 false），直接读活库——即上次生成已被 Memory Agent 污染的状态。
2. Memory Agent 的 17 个写工具直接写活库，没有按章撤销能力（无 `deleteEventsByChapter`、无状态 restore）。
3. 快照写入侧漏了两类要素：`saveChapterSnapshot` 只存 characters/conflicts/foreshadowing/clues/factions/locations/relationships，**缺 items 和 info\_layers**（读侧 `prompt-builder.ts:2352` 已对 items 做缺失兼容，属于"读侧先写了，写侧没跟上"）。
4. 章节正文有版本回滚（`chapter_versions` + `rollbackToVersion`），要素状态没有对应物。

**修改方案（后端）**：

A. **快照补全**：`saveChapterSnapshot` 增加 `items` + `infoLayers` 两个字段。

B. **新增状态恢复服务** `restoreStateFromSnapshot(projectId, chapterNumber)`（建议放 `core/state-rollback.ts`）：

- 读第 N 章 full 快照；
- 单事务内对 9 张实体表做"快照级恢复"（以快照为准 upsert，快照中不存在但活库存在的实体删除——它们是 N 章之后才创建的）；
- 清理 `chapter_number > N` 的 memory\_events、character\_history、agent\_logs、旧快照；
- 返回恢复报告（恢复实体数、清理事件数、删除实体清单），供前端展示。

C. **重新生成入口**：`create-flow` 增加 `rebase?: boolean`，或新增 `POST /projects/:id/chapters/:chapterNumber/regenerate`：

- `rebase=true` → 先 `restoreStateFromSnapshot(N-1)` → 再走正常 `createChapterWithFlow`；
- 同时修正 `getStoryState` 条件为 `latestKnownChapter >= chapterNumber` 即读快照（防御性，双保险）。
- **边界约束**：仅允许对"最新已写章节"执行 rebase；若存在更后面章节，恢复 N-1 快照会使 N+1..M 章成为"未来残留"，需级联提示用户后续章节全部失效（或禁止并提供"删到第 N 章再重生"选项）。

**方案选型对比**：

| 方案                 | 原理                    | 成本                                                | 风险                |
| ------------------ | --------------------- | ------------------------------------------------- | ----------------- |
| **A. 恢复快照到活库（推荐）** | 生成前把活库倒回 N-1          | 低：工具链零改造（query/写工具/SEMI 注入都读活库）                   | 有未来章节时会倒灌，靠边界约束规避 |
| B. 写隔离暂存区          | 生成过程写 staging 表，确认后合并 | 高：17 个写工具 + query 工具 + prompt-builder 全部要加"读暂存"分支 | 改动面大，缓存键也要区分      |

推荐 A：语义就是"时间倒流"，与现有架构零冲突。

**修改方案（前端）**：

- 章节操作区"重新生成"按钮 → 确认弹窗（明确列出：将回滚 8 类要素到第 N-1 章快照、清除第 N 章变更记录与 Agent 日志、正文旧版本保留在版本历史）→ 确认后走 regenerate SSE；
- SSE 完成后复用现有 `dataChanged` 推送刷新矩阵/画布；
- 恢复报告以 toast + 章节版本面板（`chapter-version-panel.tsx` 扩展一个"状态回退记录"区块）展示。

涉及前端文件：`novel-workspace.tsx`（入口按钮）、`api/novel-client.ts`（regenerate 接口）、`hooks/use-novel-creation-flow.ts`（rebase 参数透传）、`chapter-version-panel.tsx`（回退记录）。

### 1.5 AI 辅助生成：要素创建已有，状态变更缺"人工干预点"

现状：`ai-arrange`（按章纲 AI 编排）与 `entities/ai-generate`（单实体生成）已存在且有失败回滚；但**章节内的要素状态变化**完全由 Memory Agent 事后提取并直接落库，用户没有任何预览/干预机会——这正是"第 3 章角色升级结果不满意"的来源。

**建议（可选增强，决策点 3）**：Memory 阶段产出"状态变更草案"检查点：

- Memory Agent 的写工具正常执行，但每个写操作同时记录 inverse patch（旧值）；
- SSE 推送 `novel:checkpoint{type:'state_changes'}`，前端展示变更清单（实体 / 字段 / 旧值 → 新值 / 理由，可复用子轨道气泡卡片的 diff 样式）；
- 用户逐条接受 / 拒绝 / 编辑后提交；拒绝的条目按 inverse patch 回滚。

成本提醒：多一次人工确认会打断"一键成章"流程；可做成项目级开关（默认关，精修模式开）。

## 2. 需求二：创作时的上下文组装

### 2.1 现状（已完整，不需要重构）

三层缓存（STATIC 世界规则+风格+Agent 身份 / SEMI 章节上下文 / DYNAMIC 对话）+ arrangedEntities 精准注入 + 按 agentType 差异注入（chapter-instruction 仅 Writer）。缓存诊断接口（hash）已有。

各 Agent 的 SEMI 层差异现状（供核对）：

| Agent    | 章节信息 | 约束 | arrangedEntities | 故事状态 | 信息差 | 摘要/因果链   | 创作指令  |
| -------- | ---- | -- | ---------------- | ---- | --- | -------- | ----- |
| director | 有    | 有  | 有                | 有    | 有   | 有        | 无     |
| writer   | 有    | 有  | 有                | 有    | 有   | 有        | **有** |
| reviewer | 有    | 有  | 有                | 有    | 有   | 有 + 盲审后缀 | 无     |
| memory   | 有    | 有  | 有                | 有    | 有   | 有        | 无     |

### 2.2 差距 1：查询工具没有"章节时点"（asOf）语义

`novel_query_state` / `novel_ask_story` 永远读活库最新状态。重写历史章节时，SEMI 层注入的是 N-1 快照，而 AI 若调工具查询，拿到的是活库最新值——**同一轮对话里两个互相矛盾的事实源**，这比不查更危险。

**修改方案**：

- 利用 orchestrator 已有的 AsyncLocalStorage run 隔离，给工具执行上下文注入当前 `chapterNumber`；
- `novel_query_state` / `novel_ask_story` 增加可选参数 `asOfChapter`：显式指定或缺省取"当前创作章 - 1"；命中该分支时改读快照（`getSnapshot(asOf)`）或账本重放（`listChangeRecords` 按章过滤后折叠），而非活库；
- 工具描述里写明规则："查询历史状态时必传 asOfChapter；查询当前最新状态不传"。

### 2.3 差距 2：上下文对作者不透明

`cache-diagnostics` 只返回 hash，作者无法确认"这次生成到底塞了什么"。

**修改方案**：

- 后端新增 `GET /projects/:id/context-preview?chapterNumber=N&agentType=writer`：复用 `buildSystemPrompt` / `buildChapterContext` 返回三层全文 + 分段 token 估算 + 各段缓存层级标记；
- 前端新增"上下文预览"抽屉（从章节操作区打开）：三层分段折叠展示、每段 token 条、arrangedEntities 清单高亮；生成前可核对，生成后可与 agent\_logs 的实际 prompt 对照。

涉及文件：`novel-routes.ts`（新端点）、`prompt-builder.ts`（导出分段构建结果）、`novel-workspace.tsx` + 新增 `context-preview-drawer.tsx`、`api/novel-client.ts`。

## 3. 需求三：Tool 调用行为校验

### 3.1 现状策略（从代码注释还原的演进史）

`novel-agents.ts` 的注释记录了一次完整试错：Director/Writer/Reviewer 曾配全量 query 工具，结果是"LLM 在干活前先调用工具重复查询已知状态，3 次工具调用 = 3 倍 system\_prompt token"，于是全部移除；后来以"A+B"折中给 4 个 Agent 只开语义化查询工具 `novel_ask_story`（writer `maxToolCalls=2`），Memory 保留全部 17 个工具。

**结论**：当前设计是"刻意压制工具循环"，所以校验重点不是"会不会疯狂循环调用"，而是 **"该调的时候会不会调、调得对不对"**。

### 3.2 差距：没有观测手段

`novel_agent_logs` 记录三层 prompt + 结果 + 耗时，但**不记录工具调用序列**。无法回答"Writer 这章调了几次 ask\_story、查了什么、结果是否被用上"。

### 3.3 修改方案

**后端**：

1. **工具调用插桩**：`createNovelTools` 返回前对每个 `tool.execute` 包一层 `withToolCallLogger(ctx)`，写入新表 `novel_tool_call_logs`（迁移 027）：
   `id / run_id / project_id / chapter_number / agent_type / tool_name / params_digest / result_chars / duration_ms / created_at`；
   同时 `novel_agent_logs` 增加 `tool_call_count` 列。ctx（runId/chapterNumber/agentType）从 orchestrator 的 AsyncLocalStorage 取，零参数穿透。
2. **SSE 透传**：`runAgent` 内每次工具调用推 `CUSTOM(novel:tool-call)` 事件（复用 creation-flow SSE 通道与现有 toolCallId 机制），前端实时可见。
3. **行为测试套件**：`__tests__/tool-behavior.test.ts`，固定三个剧本各跑 N 次（mock 或真实小模型）：
   - 剧本 A（信息已注入）：本章出场角色定义已在 SEMI 层 → 断言 Writer **不应**调 ask\_story 查该角色；
   - 剧本 B（信息未注入）：叙事任务涉及未编排角色 → 断言 Writer **应**调 ask\_story，且查询词包含该角色；
   - 剧本 C（Memory 提取）：正文含明确状态变更 → 断言 Memory 必须出现对应 update 工具调用，缺失即提取失败。

**前端**：

1. 创作流水线面板（creation-flow 进度区）每个 Agent 阶段下挂"工具调用轨迹"chip 行：工具名 + 耗时 + 参数摘要，点击展开结果；
2. agent-logs 页面增加 `tool_call_count` 列与按工具名筛选。

**校验判定标准（建议固化到文档）**：

| Agent                        | 正常区间          | 异常信号        | 处置                  |
| ---------------------------- | ------------- | ----------- | ------------------- |
| writer / director / reviewer | 0-2 次/章       | >3 次        | SEMI 层注入缺失，检查上下文组装  |
| memory                       | ≥1 次写工具（有变更时） | 0 次但正文有明显变更 | 提取失败告警，重跑 memory 阶段 |

## 5. 决策点（2026-07-22 已全部确认，确认结果见各条末尾）

1. **子轨道分类**：1.3 节 7 个问题点的处理（全采纳 / 部分采纳 / 逐条讨论）。 全采纳
2. **回退方案选型**：A 恢复快照到活库（推荐）/ B 写隔离暂存区。 A
3. **状态变更草案检查点**：是否值得做（多一次人工确认 vs 打断一键成章）；可做项目级开关。做项目级开关
4. **实施顺序**：是否按 PR1 → PR4 推进，还是有优先级调整。按 PR1 → PR4 推进

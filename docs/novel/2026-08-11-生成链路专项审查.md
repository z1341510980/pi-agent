## 2. 生成链路修复明细

### 2.1 Writer pushback → Director 重规划

首次 Director 成功后，`scenePlanV2Write` 开启时会执行 ScenePlan V2 影子写；但 Writer pushback 后重跑 Director 的分支只更新 `run.directorTask`，没有重新影子写，导致数据库保留首次规划而非最终批准规划。

修复：pushback Director 工具提交成功后，使用与首次规划相同的 flag 和 `shadowWriteDirectorPlan` 路径重新写入计划。

证据：

- 首次写：`novel-orchestrator.ts:482`
- pushback 补写：`novel-orchestrator.ts:693`

### 2.2 顶层错误与取消收敛

`createChapterWithFlow` 顶层 catch 已具备：

- Abort signal → cancelled 事件与 `{ status: 'cancelled' }`；
- 其他异常 → error 事件与结构化 `{ status: 'error', error }`；
- finally 调试与锁清理路径可达。

未继续做无证据改动。该项核查结论为“现实现已完整”，不是“新增修复”。

## 3. P2 Appearance 收口

### 3.1 手工更新与 sync 双写

手工跨度编辑双写已覆盖 narrative/conflict/foreshadow/clue/faction/location/item。Character 本身没有 `chapterSpans`，不走手工 spans 差集；其出场由 character_history 与编排/同步入口记录。

`syncChapterDimensions` 原只双写 conflict/foreshadow/clue/faction/location，漏 item 与 narrative。本轮增加：

- item：`arranged.itemIds + before/after 新建差集`，补 `chapterSpans` 后以 `source='sync'` 写 Appearance；
- narrative：加入 `captureEntityState`，用 before/after 新建差集补 `chapterSpans` 并写 Appearance。

### 3.2 删除级联

`novel_entity_appearances` 没有指向实体或章节的数据库外键，因此必须由 Store 手工清理：

- 8 类投影实体删除均清理 Appearance；Character 是本轮补齐的高频缺口；
- `ChapterStore.deleteChapter` 在同一事务内先清 Appearance，再删除章节和重排引用；
- 项目移入回收站时清理进程级 ChunkCache。

## 4. P3 Context Chunk 与缓存

### 4.1 versionKey 失效维度

原 versionKey 设计包含项目、实体、Memory 和文风，但实际调用 `buildChunkVersionSource(this.store, ...)` 时，`NovelStore` 没有账本事件方法，导致 `latestMemoryEventId` 恒为 null。

修复：

- `NovelMemoryStore.getLatestStoryEventId` 使用单条 SQL 获取最新事件 ID；
- orchestrator 把 `memoryStore` 作为独立 eventSource 传入；
- 新增 `chapterVersion`：所有章节最大 `updatedAt`，覆盖正文、章纲和计划变化；
- 新增 `contextAnchorVersion`：Hooks 与 InformationLayers 最大 `updatedAt`；
- `NovelStore.getContextAnchorVersion` 统一提供锚点版本。

代码证据：

- `novel-memory-store.ts:871`
- `chunk-cache.ts:100-139`
- `novel-store.ts:576`

### 4.2 真正的先查后建

旧链路：

1. `buildChapterContextChunks` 全量读取 boundary、ledger、edges、anchors 并格式化；
2. 对已生成内容算 contentHash；
3. 再查询缓存。

因此命中只能复用字符串，无法省构建。旧逻辑还要求先得到 content 才能得到查找键，与“先查后建”冲突。

新链路：

1. `buildChapterContextChunkBuilders` 只创建惰性 `{ chunkId, scope, build }`；
2. `buildWithChunkCacheLazy` 先按 `projectId + chunkId + versionKey + scope` 查询；
3. 命中不执行 `build()`；
4. 未命中才读取数据并格式化；
5. `contentHash` 仍保存为真实内容 SHA-256 指纹，不再冒充 scope；
6. optional chunk 的 null 结果使用空哨兵缓存，避免重复探测。

`scope` 覆盖 chapterNumber、agentType、narrativeTask、constraints、arrangedEntities、summaryMode 和 askStoryEnabled；versionKey 覆盖数据库版本维度，两者共同防止串缓存。

代码证据：

- lazy cache：`chunk-cache.ts:292`
- lazy builders：`prompt-builder.ts:1160`
- 生成路径接入：`novel-orchestrator.ts:2304`

测试守门：

- 二次命中后 build 计数不增加；
- scope 变化强制 miss；
- null optional chunk 只构建一次；
- lazy builders 执行结果与 eager chunks 逐字节一致；
- Agent disabled 过滤结果一致。

### 4.3 缓存生命周期

- 默认上限 2000 条，超限按插入顺序淘汰最旧条目；
- stats 增加 `evictions`；
- 项目删除时调用 `clearProject`；
- lazy slot 使用 scopeKey，同一 version+scope 会覆盖，不再因 contentHash 变化无限新增槽位。

### 4.4 contextSummaryMode

原状态：flag 已定义，`chooseEntityChunkMode` 和 `buildStoryStateSummary` 已有测试，但 orchestrator 不传 `entitySummaryMode`，生产始终 full。

修复：

- `contextChunksEnabled && contextSummaryMode` 时执行 `chooseChapterEntitySummaryMode`；
- 无编排且实体总数 > 8 时进入 summary；小项目保持 full；
- 有 arrangedEntities 时保持 full，因为该路径本身不注入 story-state；
- shared cache key 区分 summary/full。

当前限制：模型 contextWindow 尚未统一暴露给 orchestrator，因此预算分支暂用 Infinity，只启用实体数量阈值，避免在预算未知时压缩小项目。这是保守接线，不等同于完整 T03-7 预算降级。

### 4.5 identity-contract

原状态：`validateAgentIdentity` 仅测试和看板使用，生产 8 个 `buildAgentIdentity` 消费方没有统一守卫。

修复：守卫下沉到 `buildAgentIdentity`，所有消费方自动覆盖。五个主 Agent 缺协议标记或身份超长时写 warn，不抛异常；其他工具 Agent markers 为空，仅校验字符上界。日志由 services 装配注入。

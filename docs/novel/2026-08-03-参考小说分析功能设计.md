# 参考小说分析功能设计

> 日期：2026-08-03  
> 状态：调研稿，待评审  
> 目标：从用户提供的参考小说中提取文风、文笔、笔力、故事要素和推进节奏，形成可审核、可编辑、可版本化的创作指导，并安全应用到当前小说项目。

## 一、功能定位

该功能暂定名为“参考小说分析”。

它不是把另一本小说反向导入当前项目，也不是让模型照搬原作，而是分析参考小说中相对稳定、可抽象的创作规律，包括：

- 作者以什么思想和态度观察人物与世界。
- 作品形成了怎样的叙述气质和个人特色。
- 作者怎样组织感官、视角、动作、情绪和语言。
- 作者怎样选择重点、分配详略并控制场面。
- 作者怎样建立期待、制造悬念、推进冲突和释放爽点。
- 章节、场景、人物关系、伏笔和信息差如何向前发展。

分析结果先作为独立草稿保存。用户逐项确认后，系统才将抽象规则应用到当前项目。参考小说中的人物、地点、专有名词、具体剧情和原文片段不得自动写入当前小说的故事实体、账本或生成 Prompt。

分析结果可以保存为跨项目复用的私人模板。项目绑定模板后，每次生成章节时仍由用户通过“采用参考模板”开关决定本次是否启用；关闭时不得向任何 Agent 注入该模板。

## 二、核心概念

参考小说分析必须区分文风、文笔、笔力和节奏，不能将句长、对话比例等语言统计统一归入“文风”。

| 概念 | 核心内涵 | 解决的问题 |
|---|---|---|
| 文风 | 思想、性格与语言气质结合后形成的个人风格 | 作者以什么态度看世界，作品整体给人什么感觉 |
| 文笔 | 将场景、感受、动作和情绪转化为文字的表达能力 | 文字是否准确、流畅、生动、有代入感 |
| 笔力 | 对重点、详略、信息、张力和场面的控制能力 | 能否把重要内容写透，把次要内容及时略过 |
| 节奏 | 期待、压力、信息、兑现和收束在时间上的安排 | 读者何时紧张、期待、满足、喘息并继续阅读 |

四者彼此关联，但不能互相替代。

以一个人物高光场面为例：

- 文风决定作者是热烈歌颂、冷静旁观、含蓄留白还是反讽解构。
- 文笔决定如何使用感官、动作、视角和句式呈现场面。
- 笔力决定哪些过程压缩、哪个瞬间展开、配角反馈写到什么程度。
- 节奏决定何时建立失败预期、何时揭示转机、何时兑现并展示后果。

## 三、文风分析

### 3.1 定义

文风是作者的思想、性格和语言气质共同作用后，在作品中形成的稳定表达倾向。

文风主要由“思想”和“文采”构成，同时受作者性格影响，最终形成具有个人感染力的“文气”。

### 3.2 思想内核

思想是文风的首要部分。系统需要分析作者如何理解和判断人物、关系、社会、权力与命运。

建议观察以下维度：

| 维度 | 可能倾向 |
|---|---|
| 人性观 | 偏善、偏恶、复杂、功利、理想主义 |
| 命运观 | 宿命、抗争、因果、机会主义、随机无常 |
| 成功观 | 个人能力、资源交换、关系网络、牺牲、运气 |
| 权力观 | 崇拜、警惕、解构、现实接受 |
| 道德观 | 原则优先、结果优先、关系优先、利益优先 |
| 情感观 | 克制、热烈、浪漫、悲观、交易化 |
| 冲突观 | 善恶对立、立场差异、利益冲突、制度冲突 |
| 成长观 | 苦难塑造、选择塑造、关系塑造、天赋决定 |
| 世界态度 | 严肃、戏谑、温柔、冷峻、悲悯、讽刺 |

系统还要判断思想通过什么方式进入作品：

- 旁白直接议论。
- 人物选择及其代价。
- 正反人物对照。
- 人物命运和行为后果。
- 反讽和叙事落差。
- 世界运行规则。
- 保留矛盾，不替读者下结论。

参考作品的思想结论不能自动覆盖当前项目。系统应优先提取“思想如何表达”，而不是要求当前小说接受相同价值判断。

例如，不能直接生成：

> 当前小说应采用参考作品的功利主义价值观。

可以转化为：

> 避免由旁白直接宣布道德结论，让人物的利益选择及其后果承担价值表达。

### 3.3 作者性格与文气

文气是作品在长篇阅读中形成的人格感。它不能由一两个句子判断，需要跨章节、跨场景观察。

建议分析：

- 冷静或热烈。
- 克制或外放。
- 严谨或松弛。
- 犀利或温和。
- 悲悯或冷酷。
- 庄重或戏谑。
- 坦率或含蓄。
- 豪放或婉约。
- 世故或天真。
- 现实或浪漫。
- 作者是否经常评价人物。
- 旁白是否具有强烈存在感。
- 面对悲剧时是沉痛、冷处理还是黑色幽默。
- 面对成功时是热烈释放、轻描淡写还是迅速引入代价。

分析结果不应只给形容词，还要说明这些倾向如何在正文中出现。例如：

```text
作者人格倾向：冷静、锋利、克制。

主要表现：
1. 很少直接抒情。
2. 人物陷入困境时，旁白不替人物解释。
3. 通过动作和选择暴露人物弱点。
4. 重大胜利后不长篇庆祝，而是迅速引入新的代价。
```

### 3.4 外在语言气质

文采和语言气质构成文风的表面形态，主要分析：

- 凝练或铺陈。
- 直接或曲折。
- 幽默或庄重。
- 含蓄或明快。
- 豪放或婉约。
- 冷峻或温暖。
- 口语化或书面化。
- 平铺直叙或千回百转。
- 旁白主导或人物视角主导。
- 是否喜欢讽刺、反讽和调侃。
- 是否喜欢留白。
- 是否经常总结和议论。
- 是否追求“一眼懂”的阅读体验。

### 3.5 网文语境

网络小说通常具有日更、篇幅长和设定开放的特点，文风更强调可持续阅读，而不只是单章文学效果。

分析时应额外考虑：

- 阅读门槛是否足够低。
- 句子是否倾向“一眼懂”。
- 信息和情绪是否容易快速获取。
- 爽点、悬念和新鲜要素的保鲜周期。
- 语言是否适合长期连载。
- 是否为了辞藻牺牲清晰度。
- 文风能否在高频更新中保持稳定。

## 四、文笔分析

文笔负责把场景、感受、动作和情绪转化为准确、流畅、生动且有代入感的文字。

### 4.1 选择性感官描写

写场景前，应先在脑中经过视觉、听觉、嗅觉、触觉、味觉和身体感觉，再选择真正有作用的感官。

系统不应鼓励机械地写满五感，而要判断感官描写是否承担以下功能：

- 定位环境。
- 提示危险。
- 触发记忆。
- 改变人物判断。
- 强化身体反应。
- 埋设伏笔。
- 显示人物经验和身份差异。

需要统计：

- 各类感官的使用比例。
- 每千字感官描写次数。
- 高压和低压场景的感官差异。
- 感官描写后是否跟随判断、动作或情绪。
- 是否存在静态罗列感官的问题。

### 4.2 主体化视角

普通描写不只说明“一个东西怎么样”，而要说明“它对当前视角人物意味着什么”。

例如，不只写房间冷，而要写寒冷怎样影响人物的伤口、动作、判断或耐心。

系统应分析：

- 客观镜头比例。
- 主角感知比例。
- 配角视角比例。
- 全知视角比例。
- 环境是否经过角色经验、欲望和风险判断过滤。
- 描写是否改变人物行动。
- 同一事物在不同人物眼中的差异。

视角切换还应按功能分析：

- 主角高光时，通过配角的震惊、误判或恐惧放大效果。
- 主角掌握信息优势时，通过配角视角保留未知感。
- 展示主配角信息差时，使用有限切换或全知视角。
- 展示主角无法察觉的变化时，通过旁观者观察呈现。

“80% 使用主角视角”可以作为经验参考，但系统不应固定写死，应根据参考小说和当前项目类型提取目标范围。

### 4.3 生理、情绪、认知递进链

生理反应类描写建议遵循以下自然顺序：

```text
底层生理反应
→ 模糊情绪
→ 对情绪的识别
→ 对自身状态的认知
→ 行动、压制或掩饰
```

例如：

```text
掌心开始出汗。
他握紧刀柄，才发现自己的呼吸已经乱了。
直到这一刻，他才承认自己是在害怕。
```

分析时需要判断：

- 生理反应是否先于情绪命名。
- 是否直接使用“他很害怕”等总结。
- 生理反应是否具体并符合场景。
- 角色是否延迟识别情绪。
- 角色是否压制、掩饰或误解自己的情绪。
- 情绪是否最终导致行动。

该机制适用于恐惧、疼痛、欲望、羞耻、愤怒、焦虑、疲惫和兴奋，但不能机械套用到每一个情绪场景。

### 4.4 紧张场面的感知领先

高压状态下，人的感觉往往先于完整意识。

建议顺序：

```text
刺激
→ 碎片化感觉
→ 身体反应
→ 不完整判断
→ 完整意识
→ 决策
```

系统应分析：

- 是否先解释结果，再写感受。
- 是否先呈现局部视觉、声音、触感或失衡感。
- 紧张场景句长是否缩短。
- 主语和完整解释是否减少。
- 动作是否早于原因说明。
- 角色意识是否存在合理延迟。

可应用规则：

> 高压瞬间不要先解释发生了什么，优先写角色能捕捉到的局部感觉，再让意识补上因果。

### 4.5 高代价冲突揭示人物底色

重要人物的性格不应主要依赖介绍，而应通过高代价选择暴露其真正的价值排序。

系统应分析：

- 人物平时怎样描述自己。
- 极端状态下首先想到什么。
- 危机中保护什么、放弃什么。
- 下意识行为是否与公开立场矛盾。
- 高代价选择是否推动人物弧光。
- 关键性格揭示是否出现在压力节点。

生死冲突是最强形式，但不是唯一方式。还可以使用：

- 名誉风险。
- 关系破裂。
- 利益损失。
- 身份暴露。
- 原则与目标冲突。
- 无法撤回的选择。

### 4.6 悬念后置

危机感不只来自时间锁和空间锁，还来自结果的延后确认。

典型结构：

```text
异常征兆
→ 可推测的模式
→ 逐步验证
→ 读者形成猜测
→ 人物接近答案
→ 最后确认或反转
```

系统应分析：

- 结果是先说还是后说。
- 前置线索数量和显著度。
- 读者比人物提前知道多少。
- 猜测到确认之间的距离。
- 是否使用错误解释或误导。
- 是否通过空间、物件和行为展示异常。
- 是否过早由旁白解释答案。

### 4.7 爽点的详略控制

网文节奏不是所有内容都快，而是压缩影响满足感的无效过程，展开满足发生和反馈的关键部分。

需要分析：

- 铺垫长度。
- 压抑长度。
- 期待建立时长。
- 爽点本体描写时长。
- 配角反馈时长。
- 后果展示时长。
- 爽点后是否过早切走。
- 重复性庆祝是否及时收束。

可应用规则：

> 通往满足的无效阻碍要快；满足发生的关键瞬间要慢；反馈和后果要充分；重复性的庆祝要及时收束。

### 4.8 期待先行

重要事件发生前，应先让读者知道自己在期待或担心什么。

高光场面适合使用反向期待：

- 展示困难。
- 展示双方差距。
- 展示失败代价。
- 让旁观者认为不可能。
- 让读者期待主角打破判断。

厄运场面适合使用正向期待：

- 给出不安征兆。
- 让人物猜测坏结果。
- 逐步验证猜测。
- 让读者担心猜测成真。

系统要记录期待建立点、兑现点、两者距离、使用视角、是否反转以及兑现后的反馈长度。

## 五、笔力分析

笔力决定作者能否抓住重点、分配详略、掌控场面并把关键内容写透。

### 5.1 重点选择

分析内容：

- 一章完整展开了几个核心事件。
- 是否围绕章节任务组织内容。
- 次要事件是否及时压缩。
- 重要事件是否得到足够篇幅。
- 是否存在大量有信息但无叙事作用的细节。
- 是否出现胡子眉毛一把抓的问题。

### 5.2 详略分配

分析铺垫、过程、高潮和反馈的篇幅分配：

- 关键选择是否被一笔带过。
- 无关移动和说明是否过长。
- 人物高光是否有旁观反馈。
- 反转后是否展示后果。
- 情绪场面是否只写结果，不写形成过程。
- 爽点和高潮是否得到适当减速。

### 5.3 描写穿透力

分析描写是否进入人物的身体、情绪、认知和选择，而不只停留在表面：

- 是否通过一个细节揭示人物。
- 是否用环境承载冲突。
- 是否通过人物反应表现力量差距。
- 是否把抽象情绪转化为可观察行为。
- 描写是否最终影响判断和行动。

### 5.4 场面掌控

分析：

- 场面内人物数量。
- 当前目标是否清楚。
- 空间关系是否清楚。
- 动作因果是否连续。
- 信息是否按需要释放。
- 视角是否混乱。
- 高潮是否具有明确焦点。
- 配角反应是否服务主事件。

### 5.5 信息密度

分析：

- 每个段落新增了什么。
- 是否重复相同信息。
- 解释是否早于读者需要。
- 背景说明是否打断行动。
- 世界设定是否嵌入风险、利益和冲突。
- 是否通过选择和后果传递设定。
- 是否存在大段静态说明。

### 5.6 情绪累积与释放

分析：

- 情绪是否有起因、积累和释放。
- 是否突然要求读者感动或愤怒。
- 释放前是否形成足够期待。
- 释放后是否改变行为、关系和后续选择。
- 情绪场面是否存在重复压抑而没有推进。

## 六、推进节奏分析

节奏不是单纯的快慢，而是期待、压力、信息、兑现和收束的安排。

基础结构：

```text
期待建立
→ 阻力增加
→ 信息延迟
→ 局部兑现
→ 反馈放大
→ 新问题出现
```

### 6.1 场景级节奏

每个场景建议提取：

- 场景开始、中段和结束时的张力。
- 冲突强度变化。
- 信息释放量。
- 人物可选行动空间是否收窄。
- 情绪变化。
- 对话、动作、反思和说明比例。
- 场景时间跨度。
- 是否产生不可逆后果。
- 场景进入和离开方式。

### 6.2 章节级节奏

将每章标准化为 0%-100% 的位置，生成：

- 张力曲线。
- 信息释放曲线。
- 情绪强度曲线。
- 动作密度曲线。
- 对话密度曲线。

不同章节功能应分别聚合，不能把高压、关系、说明和缓冲章节混在一起求一个平均曲线。

典型输出：

```text
高压章节通常在 65%-80% 位置达到局部峰值。
结尾平均保留 35%-55% 的未解决张力。
连续两个高压章节后，约 40% 概率进入关系或恢复章节。
重要揭示通常发生在章节后 1/3。
```

### 6.3 全书级节奏

分析：

- 期待建立到兑现的距离。
- 爽点前的压抑长度。
- 爽点本体的展开长度。
- 兑现后的反馈长度。
- 悬念后置距离。
- 高压和缓冲章节比例。
- 同类场景连续次数。
- 局部高潮和大高潮间隔。
- 信息揭示间隔。
- 伏笔种植到回收的章节距离。
- 每章结束时保留的未解决张力。
- 钩子类型分布和重复频率。
- 关系推进、情节推进和信息章节占比。

最终结果应保存范围和概率，不能保存参考小说的精确章节序列，避免逐章复刻。

## 七、故事要素分析

故事要素应按叙事功能抽象，不能保留参考小说的具体名称和独特组合。

### 7.1 功能角色

- 焦点人物。
- 目标持有者。
- 对手。
- 盟友。
- 导师。
- 催化者。
- 见证者。
- 阻碍者。
- 信息持有者。
- 欺骗者。
- 权威者。
- 关系对象。

### 7.2 叙事要素

- 目标。
- 障碍。
- 代价。
- 选择。
- 行动。
- 后果。
- 揭示。
- 秘密。
- 线索。
- 伏笔。
- 回收。
- 反转。
- 误解。
- 承诺。
- 悬念债务。
- 关系变化。
- 身份变化。
- 状态变化。
- 世界规则。
- 资源和期限。

### 7.3 抽象原则

不安全的结果：

> 被逐出宗门的剑修发现玉佩里藏着母亲的灵魂。

初步抽象：

> 主角通过熟悉物件发现与家族历史有关的隐藏信息。

可应用规则：

> 将关键揭示绑定到前文出现过的普通物件；揭示前安排低显著度提醒；揭示必须改变角色的即时选择。

如果某个模式只在参考小说中出现一次，而且组合高度独特，应标记为高风险，不建议应用。

## 八、分析处理流程

整本小说不能一次性发送给模型。建议采用本地统计与分层 Map-Reduce 相结合的方式。

### 8.1 导入和预处理

处理步骤：

1. 检测文件格式和编码。
2. 标准化换行和 Unicode。
3. 清除控制字符、重复页眉页脚、站点水印和广告。
4. 识别正文、目录、前言、后记和附录。
5. 识别章节边界。
6. 识别场景边界。
7. 保留标准化前后的稳定偏移。
8. 计算原文件和标准化文本哈希。
9. 生成导入质量报告。
10. 由用户确认章节划分和排除区域。

第一版建议支持：

- TXT。
- Markdown。
- 粘贴文本。
- UTF-8、UTF-8 BOM、GBK 和 GB18030。

EPUB、DOCX、HTML、PDF 和 OCR 放到后续阶段。

本地文件和粘贴文本是第一版并列支持的输入方式。无法可靠识别编码时，必须提示用户选择编码或重新导入，不能将乱码直接提交给模型。

### 8.2 输入大小、Token 与费用限制

语义分析必须通过 LLM 完成，可能消耗大量 Token 并产生较高费用。用户提交前必须显示明确提示：

> 参考小说分析需要将所选文本发送给当前模型，可能消耗大量 Token 并产生较高费用，请谨慎使用。

系统应读取所选模型的上下文窗口，并为系统 Prompt、分析指令、结构化输出和估算误差预留空间。文件或粘贴文本不得超过本次分析的有效输入预算。

```text
有效文本 Token 上限
= 模型上下文窗口
- 系统 Prompt Token
- 分析指令 Token
- 结构化输出预留 Token
- 安全余量
```

安全余量建议不低于上下文窗口的 10%，并设置固定最低值，避免不同 provider 或 tokenizer 的估算误差造成请求溢出。

提交确认页需要展示：

- 当前 provider、模型和上下文窗口。
- 文件或粘贴文本的字符数和估算 Token。
- Prompt、输出预留和安全余量。
- 预计输入、输出 Token 和调用次数。
- 能读取价格时展示预计费用区间。
- 是否超过限制，以及需要减少多少内容。

超过有效输入上限时必须阻止提交。第一版不静默截断，也不能只分析前半部分。用户可以缩小文本、选择部分章节或更换上下文窗口更大的模型。

输入通过总量校验后，内部仍可按场景和章节组织分析，以提高结构化结果质量；但所有调用量和费用必须在开始前统一估算并由用户确认。

### 8.3 本地确定性分析

不调用 LLM，覆盖全部文本：

- 句长和段落统计。
- 对话比例。
- 标点频率。
- 词汇分布。
- 感官词分布。
- 叙事人称迹象。
- 高频表达。
- 专有名词清单。
- 原文短语指纹。
- 章节长度。
- 开头和结尾形态。
- 套路句式和重复结构。

这部分提供可复现的量化基础，也用于检查 LLM 的分析结论是否有证据支持。

### 8.4 场景级 LLM 提取

每个场景或场景窗口提取：

- 场景目标和障碍。
- 人物选择和后果。
- 揭示、反转和关系变化。
- 感官与视角组织。
- 生理、情绪和认知顺序。
- 信息释放方式。
- 期待建立与兑现。
- 场景详略和重点。
- 张力进入、中段和离开值。

建议参数：

- 每块 1500-4000 tokens。
- 超长场景按段落切分。
- 10%-15% 重叠。
- JSON 输出。
- 温度 0-0.2。
- Zod 严格校验。
- 校验失败最多重试一次。

### 8.5 章节级汇总

章节汇总读取场景结构化记录，而不是再次读取整章原文，生成：

- 章节功能。
- 场景数量。
- 开场方式。
- 期待和冲突推进。
- 转折和高潮位置。
- 结尾钩子。
- 信息释放模式。
- 详略分配。
- 张力、情绪和信息曲线。

### 8.6 全书级汇总

最终模型只读取统计数据和章节分析结果，不读取原文，生成：

- 主要和次要文风模式。
- 思想表达机制。
- 作者人格与文气。
- 文笔技法。
- 笔力控制规律。
- 章节和全书节奏周期。
- 可复用规则。
- 反例和矛盾。
- 置信度和覆盖率。
- 不建议复用的独特模式。

## 九、置信度与证据

每项分析结果都必须包含证据和反例，不能由模型凭一两个片段给整本书下结论。

```ts
interface ReferenceFinding {
  key: string
  category: 'styleSpirit' | 'proseCraft' | 'narrativePower' | 'pacing'
  title: string
  observation: string
  applicableRule?: string

  supportCount: number
  counterexampleCount: number
  confidence: number
  chapterCoverage: number

  evidenceOffsets: Array<{
    sourceSectionId: string
    start: number
    end: number
  }>

  safety: {
    containsSourceSpecificContent: boolean
    abstractionRisk: 'low' | 'medium' | 'high'
  }

  decision: 'pending' | 'accepted' | 'edited' | 'rejected'
}
```

置信度至少分为：

- 测量置信度：统计样本是否足够。
- 分段置信度：章节和场景边界是否可靠。
- 语义置信度：LLM 判断是否稳定。
- 覆盖置信度：语义分析覆盖了多少章节和场景。
- 安全置信度：分析结果与原作表达保持了多大距离。

建议支持等级：

| 等级 | 建议条件 |
|---|---|
| 强支持 | 至少 8 个场景、4 个章节，且加权一致率不低于 70% |
| 中等支持 | 至少 4 个场景、3 个章节，且一致率不低于 55% |
| 暂定 | 样本较少或存在明显反例 |
| 不支持 | 只有单个例子、边界质量低或无法验证 |

## 十一、用户审核流程

### 11.1 导入确认

导入前展示：

- 文件格式和大小。
- 检测编码。
- 预计章节数。
- 是否会将文本发送给云端模型。
- 使用的 provider 和 model。
- 预计调用次数、token 和成本。
- 原文保留和删除方式。
- 用户对文件拥有相应使用权限的确认。
- 高 Token、高费用的明确警告。
- 所选模型的上下文窗口、有效输入预算和当前文本是否超限。

### 11.2 文本质量确认

LLM 分析前展示：

- 检测到的章节边界。
- 场景数量。
- 被排除的目录、广告和后记。
- 编码和乱码警告。
- 低置信度边界。
- 抽样正文预览。

用户可以调整章节边界或排除不需要分析的部分。

### 11.3 分析进度

通过 SSE 展示：

- 校验文件。
- 解析文本。
- 本地测量。
- 场景分析。
- 章节汇总。
- 全书汇总。
- 安全检查。
- 等待用户审核。
- 完成、失败或取消。

分析需要支持取消、失败重试和按 chunk 断点恢复。

### 11.4 结果审核

页面分为四个标签：

1. 文风精神。
2. 文笔技法。
3. 笔力控制。
4. 推进节奏。

每项结果支持：

- 接受。
- 拒绝。
- 编辑。
- 降为软规则。
- 提升为硬规则。
- 仅供参考，不进入 Prompt。
- 仅用于 Director、Writer、Reviser 或 Reviewer。
- 查看证据。
- 查看反例。

### 11.5 应用预览

应用前展示：

- 将修改哪些现有文风字段。
- 将新增哪些硬规则和软规则。
- 哪些规则进入 Director、Writer、Reviser 和 Reviewer。
- Prompt 增加多少字符和预计 token。
- 与当前项目规则是否冲突。
- 与当前项目已经形成的文风是否冲突。
- 是否包含疑似参考作品专有表达。

激活时创建不可变版本，并支持比较和回滚。

### 11.6 同场景示例生成与整改

分析结果通过相似度和安全检查后，还要使用“同场景示例生成”验证模板是否符合用户预期。

流程如下：

1. 用户选择一个场景类型，或输入一段与参考小说无关的原创场景设定。
2. 系统固定人物目标、冲突、场景事实和信息条件。
3. 生成一版未启用模板的基准示例。
4. 使用待审核模板生成同一场景的模板示例。
5. 展示两版正文，以及文风、文笔、笔力和节奏规则的命中情况。
6. 用户针对模板示例提出整改意见。
7. 系统根据意见修改模板规则，而不是只修改当前示例正文。
8. 使用相同场景事实重新生成，验证规则调整效果。
9. 用户明确同意后，才将当前版本保存为可复用模板。

测试场景必须是原创、通用或当前项目拥有的场景，不能复现参考小说的具体人物、地点、专有名词、独特物件或精确事件组合。

建议保存以下验收记录：

- 固定场景输入及版本。
- 基准输出和模板输出。
- 用户整改意见。
- 整改前后的模板差异。
- 重新生成结果。
- 用户最终接受或拒绝决定。
- 使用的 provider、model、Token 和费用。

### 11.7 模板保存与复用

通过同场景示例验收后，分析结果可以保存为私人可复用模板。

模板支持：

- 自定义名称和说明。
- 文风、文笔、笔力和节奏四类规则分别启用。
- 按章节类型保存不同规则。
- 指定规则应用于 Director、Writer、Reviser 或 Reviewer。
- 绑定到一个或多个小说项目。
- 创建新版本、比较版本和回滚。
- 复制模板后继续调整，不影响原模板。
- 删除参考原文后继续使用已确认的抽象模板。

## 十二、应用到 Agent

不同 Agent 只接收与其职责相关的规则，不能全部读取完整分析报告。

### 12.1 运行期开关

章节生成入口增加“采用参考模板”开关。

- 关闭：本次生成不注入参考模板，也不执行模板专属验收。
- 开启：使用当前项目绑定且用户选中的模板版本。
- 每次提交生成前明确显示当前开关和模板版本。
- 项目可以保存默认值，但不能在用户不可见的情况下静默启用。
- 日志记录是否启用、模板 ID、模板版本和 profile hash。
- 历史章节重写记录当时实际使用的模板版本，不受后续模板更新影响。

如果项目绑定多个模板，第一版要求用户在生成前选择其中一个模板版本，不在运行时临时混合多套模板。

### 12.2 Director

接收：

- 笔力规则。
- 章节重点和详略分配。
- 场景数量范围。
- 期待与兑现规律。
- 高潮和缓冲周期。
- 人物底色揭示时机。
- 信息释放方式。
- 钩子轮换建议。

不接收参考小说原文、专有名词和具体剧情。

### 12.3 Writer

接收：

- 用户确认的文风精神和叙述气质。
- 文笔规则。
- 感官选择方式。
- 主体化视角规则。
- 生理、情绪和认知递进链。
- 紧张场面的感知顺序。
- 句式、段落和对话范围。
- 当前章节类型下的节奏要求。

不接收参考小说原文样例。

### 12.4 Reviser

只接收当前正文实际偏离的规则：

- 文风目标。
- 文笔机制。
- 详略分配。
- 信息顺序。
- 场面重点。
- 当前修订 patch 所需的有限事实。

### 12.5 Reviewer

分别检查：

- 思想表达是否与当前项目主题一致。
- 文风是否稳定。
- 文笔是否准确并有代入感。
- 笔力是否突出重点。
- 节奏是否完成期待与兑现。
- 是否出现参考作品专有内容或过高相似度。

### 12.6 Memory

Memory Agent 不接收参考小说分析。它只负责当前项目的故事事实和状态变化。

### 12.7 按章节类型应用

模板允许针对不同章节类型保存不同规则。第一版复用现有三维分类，不新增含义重叠的 `chapterType`：

- `ChapterPositioning`：章节功能定位，回答“这一章主要怎么写”，现有六类为高压、推进、修炼、关系、低压和信息。
- `ChapterRhythm`：章节张力阶段，回答“这一章处于什么节奏”，如上升、高潮、舒缓、反转和悬念。
- `NarrativeTaskType`：本章必须完成的叙事动作，回答“这一章具体推进什么”，如推进主线、改变关系、释放信息和升级冲突。

页面仍可使用以下组合标签：

- 高压或高潮章节。
- 情节推进章节。
- 成长或修炼章节。
- 关系推进章节。
- 低压或缓冲章节。
- 信息揭示章节。
- 反转章节。
- 悬念章节。

同一条规则可以配置为全局适用、仅适用某类章节、在某类章节加强或在某类章节停用。

```text
全局：环境描写必须经过当前视角人物过滤。
高压章节：感觉先于意识，句子明显缩短。
关系章节：允许放慢节奏，增加动作间隙和未说出口的信息。
信息章节：悬念后置，先展示异常过程，再给出解释。
```

章节类型由 Director 的叙事任务、章节定位和节奏建议共同确定，用户可以在生成前使用相同的三维字段手动覆盖。比如“高压高潮推进章”表示 `positioning=high_pressure`、`rhythm=climax`，并带有 `advance_mainline` 或 `escalate_conflict` 等任务，而不是一个新的单值章节类型。

## 十三、Prompt 与 Token 控制

完整分析报告不能直接进入生成 Prompt。系统只编译用户已接受、与当前 Agent 相关的规则。

| Prompt 区域 | 建议最大字符数 |
|---|---:|
| 稳定文风规则 | 1500-2500 |
| 本章节奏指导 | 500-1000 |
| Agent 专属执行说明 | 300-700 |
| Reviewer 检查标准 | 600-1000 |

Writer 接收的参考规则总量建议不超过 3500 字符；Director 和 Reviewer 各自不超过 2000 字符。

规则应使用固定顺序、固定数字格式和 profile hash，避免破坏 provider Prompt Cache。

建议优先级：

1. 当前项目事实和连续性。
2. 用户对本章的明确要求。
3. 当前项目大纲和已编排实体。
4. 用户编写的硬规则。
5. 用户确认的参考分析硬规则。
6. 用户确认的参考分析软规则。
7. 当前项目正文形成的统计文风。
8. 通用默认规则。

## 十四、版权、隐私与安全边界

### 14.1 禁止行为

- 要求完全模仿某位作者。
- 保留原剧情，只替换人物名称。
- 逐章复刻原作节奏和事件序列。
- 将参考小说原文作为 Writer 正向样例。
- 将参考小说人物、地点和专有名词写入当前项目。
- 将完整章节放入生成 Prompt。
- 将上传小说形成可搜索的公共语料库。

### 14.2 原文保留

默认建议：

- 原文只在分析期间保存在本机。
- 分析完成并激活规则后默认删除原文。
- 保留抽象统计、分析结论、偏移和哈希。
- 证据只在用户主动展开时显示最短必要片段。
- 原文片段不得进入生成 Prompt。
- 参考分析日志不得记录完整原文和完整提取 Prompt。

用户可以删除原文，但系统保留不含原文的最小审计记录，包括来源名称、格式、大小、哈希、分析时间、模型、结果版本和删除状态。

原文删除后：

- 已确认的抽象模板可以继续使用。
- 原文证据查看功能不可用。
- 只能使用保留的不可逆短语指纹继续做精确重叠检查。
- UI 必须标明原文已删除，分析证据无法重新核验。

### 14.3 相似度检查

生成章节后可执行：

- 连续短语匹配。
- 8-12 字符 n-gram 匹配。
- 稀有短语重叠。
- 专有名词重叠。
- 最长公共子串。
- 章节节拍序列相似度。

用户删除原文后，可以保留 HMAC 短语指纹，用于精确重叠检测，但不能恢复原文。

### 14.4 分析安全检查

以下结果应阻止自动激活：

- 包含直接引用。
- 包含人物、地点和专有名词。
- 包含详细剧情摘要。
- 保留精确章节顺序。
- 只由一个高度独特场景支持。
- 将某位作者姓名编译进 Prompt。
- 安全检查失败或未完成。

## 十五、现有系统复用范围

### 15.1 可直接复用

- Electron 文件选择交互。
- Plugin Session 和模型选择。
- JSON 输出、重试和 payload 观测。
- SSE、取消和心跳机制。
- API 响应和 Zod 校验模式。
- 文风档案编辑器和 Prompt 预览交互。
- `ChapterRhythm`、`ChapterPositioning`、`NarrativeTask` 等分类词表。
- 现有句长、段落、对话和套路句式统计。

### 15.2 重构后复用

- `prompt-builder.ts` 内部的文风指纹算法，应抽成纯分析模块。
- Entity Generator 的 JSON 修复、Session 和进度处理可以抽取，但不能复用其写库逻辑。
- `prose-quality-evaluator.ts` 的统计可以复用，质量判断需要改成中性观察。
- `cliche-scanner.ts` 的模式频率可以复用，但不能把所有模式直接判为缺陷。

### 15.3 不可直接复用

- `generateAndArrange()` 的项目实体持久化。
- 当前项目角色、冲突、伏笔、地点和账本表。
- `ArrangedEntity` 作为参考小说的最终数据结构。
- 把参考小说存成当前项目章节。
- 把原文存入 Zustand 或 localStorage。
- 直接覆盖现有 `NovelWritingStyleProfile`。

## 十七、分阶段实施

### 阶段 0：概念和安全基础

目标：先确定产品边界，避免后续数据结构围绕“模仿”设计。

任务：

- 确认文风、文笔、笔力和节奏的分类标准。
- 确认分析词表和 JSON Schema。
- 定义用户权利确认和隐私提示。
- 定义禁止提取和禁止应用的内容。
- 建立公共领域、授权和自制测试文本。
- 确定相似度与安全阈值。

### 阶段 1：本地分析 MVP

支持 TXT、Markdown 和粘贴文本。

任务：

- 文件导入和编码检测。
- GBK/GB18030 中文 TXT 支持。
- 章节识别及手动调整。
- 文本清洗和哈希。
- 读取所选模型的上下文窗口并执行输入硬限制。
- 高 Token、高费用警告和费用预估。
- 全文本句长、段落、对话、感官、词汇和标点统计。
- 开头、结尾和章节长度统计。
- 文风语言气质的本地观察。
- 分析报告和数据质量报告。
- 手动选择后映射到现有文风档案。
- 不自动应用，不写入故事实体。

### 阶段 2：LLM 场景和章节分析

任务：

- 场景切分。
- 文风思想与作者人格分析。
- 文笔机制分析。
- 笔力和详略分析。
- 期待、悬念、爽点和节奏分析。
- 场景、章节和全书三级聚合。
- SSE 进度、取消和断点恢复。
- Token 和成本估算。
- 证据、反例、覆盖率和置信度。
- 用户逐项审核。

### 阶段 3：生成流程集成

任务：

- Director 机制规则编译。
- Writer 文风和文笔规则编译。
- Reviser 偏差修订规则。
- Reviewer 分维度验收。
- Prompt 差异和成本预览。
- profile hash、版本和回滚。
- 当前正文与规则的符合度检查。
- 生成章节与参考源的相似度检查。
- 章节生成入口的模板启用开关。
- 按章节类型选择规则。
- 同场景基准和模板示例生成。
- 用户整改、重新生成和确认入模板闭环。
- 可复用私人模板、版本和项目绑定。

### 阶段 4：丰富格式与隐私能力

任务：

- EPUB、DOCX 和 HTML。
- PDF 和 OCR 质量门槛。
- 本地加密文件库。
- 原文自动过期。
- 彻底删除和清除验证。
- 本地模型分析选项。

### 阶段 5：多参考小说融合

任务：

- 多本小说独立分析。
- 区分共同规律和单一来源规律。
- 每项规律设置来源和权重。
- 文风、文笔、笔力和节奏分别融合。
- 优先使用多来源共同支持的抽象规律。
- 降低过度贴近单一作品的风险。

## 十八、建议第一版范围

第一版建议实现：

> 导入本地 TXT/Markdown 或粘贴文本 → 检测 UTF-8/GBK/GB18030 编码 → 根据所选模型上下文窗口执行输入硬限制和高费用确认 → 自动分章 → 本地确定性统计 → LLM 分析文风、文笔、笔力和节奏 → 用户逐项审核 → 使用原创同场景生成基准和模板示例 → 用户整改并重新验证 → 确认后保存为可复用私人模板 → 生成时通过开关决定是否采用。

第一版暂不实现：

- PDF 和 OCR。
- 全书所有章节逐章调用 LLM。
- 自动导入人物和剧情。
- 将原文作为正向样例。
- 精确复刻章节节奏序列。
- 自动覆盖当前项目规则。
- 未经审核直接进入 Prompt。
- 多参考源自动融合。

第一版应支持：

- 本地文件和粘贴文本。
- GBK/GB18030 中文 TXT。
- 思想内核经用户确认后应用到当前项目。
- 用户将分析结果设置为硬规则。
- 针对不同章节类型保存不同规则。
- 删除原文但保留最小审计记录和已确认模板。
- 通过 LLM 完成语义分析。
- 明确提示高 Token、高费用并要求确认。
- 输入不得超过所选模型的有效上下文预算。
- 同场景示例生成、用户整改、重新生成和确认入模板。
- 模板跨项目复用。

## 十九、已确认产品决策

| 编号 | 决策 |
|---|---|
| 1 | 第一版同时支持本地文件和粘贴文本。 |
| 2 | 必须支持 GBK/GB18030 编码的中文 TXT。 |
| 3 | 章节生成时提供“采用参考模板”开关，由用户决定本次是否启用。 |
| 4 | 思想内核可以应用到当前项目，但必须经过用户审核确认。 |
| 5 | 用户可以将某项参考规律设置为硬规则。 |
| 6 | 支持针对不同章节类型保存不同文风、文笔、笔力和节奏规则。 |
| 7 | 用户可以删除原文；删除后保留不含原文的最小审计记录和已确认模板。 |
| 8 | 语义分析调用 LLM；提交前必须提示 Token 消耗大、费用高，并限制文件或文本不超过所选模型的有效上下文窗口。 |
| 9 | 除相似度检查外，使用原创的同一场景生成基准和模板示例；用户提出整改意见并确认后才能保存为模板。 |
| 10 | 分析结果可以保存为跨项目复用的私人模板。 |

## 二十、仍需细化的问题

1. “采用参考模板”开关的项目默认值是默认关闭，还是沿用用户上一次选择？
2. 同场景示例默认由系统生成测试场景，还是必须由用户提供场景？
3. 思想内核设置为硬规则时，如何检测它与当前项目主题、大纲和人物设定的冲突？
4. 上下文窗口和价格信息无法从 provider 准确读取时，采用哪个保守默认值？
5. 原文删除后，模板是否允许导出；导出时是否附来源删除和版权风险说明？

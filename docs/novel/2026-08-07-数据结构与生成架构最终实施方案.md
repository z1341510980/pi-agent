## 1. 文档目的与最终判断

当前系统并不是“完全错误”，而是经历了多轮兼容迁移后形成了三类技术债：

1. **迁移期双轨长期并存**：旧正文版本表与 V2 内容修订表同时写入，造成同一正文保存多份。
2. **跨领域公共关系分散在实体表中**：`chapter_spans` 在多张实体表重复，导致本章出场查询和重写同步逻辑分散。
3. **生成上下文已经做了缓存，但仍以全文注入为主**：同章角色间 shared 已复用，然而首轮输入、实体档案、工具往返和跨章重建仍然偏重。

本方案不追求“表越少越好”或“上下文越短越好”，而是采用以下目标：

- **领域事实继续分型保存**：冲突、伏笔、线索各有不同状态机，不强行合并成万能实体表。
- **横切关系统一保存**：实体出场、场景角色、版本来源、审计载荷应有统一结构。
- **身份、事实和任务分层**：角色区分靠薄身份和工具权限，故事事实通过共享 Context Chunk 提供。
- **先测量再改变生成行为**：场景级生成只有在数据证明整章 Writer 是主要成本后才灰度启用。
- **所有迁移都可对账、可回滚**：新旧结构先双写、再比对、后切读，最后才删旧结构。

### 最终实施顺序

```text
P0 建立测量基线
  ↓
P1 停止双写与日志膨胀，清理明确废弃结构
  ↓
P2 统一实体出场关系与双账本职责
  ↓
P3 上下文分块、角色薄身化、按需检索
  ↓
P4 有条件灰度场景级生成
```

## 2. 当前架构事实

### 2.1 数据层

`novel-migrations.ts` 当前累计约 53 张表，主要分为：

- 项目/章节：`novel_projects`、`novel_chapters`、`novel_volumes`
- 领域实体：角色、关系、冲突、伏笔、线索、势力、地点、物品、世界元素、信息层
- 版本链：`novel_chapter_versions`、`novel_chapter_content_revisions`、计划版本、场景版本
- 账本与快照：`novel_story_events`、`novel_memory_events`、`novel_memory_snapshots`
- 创作审计：Agent 日志、审稿报告、章节聊天、Discussion Run
- V2 场景结构：Scene、SceneRevision、Focus、Presence、Function

53 张表本身不是问题。问题在于：

- 部分表属于迁移期结构，已出现职责重复；
- 跨实体公共字段被复制到多个主表；
- 日志表把大文本和元数据混在同一行；
- 稳定身份、版本状态和关联角色之间的边界有进一步收敛空间。

### 2.2 工作流生成层

create-flow 主流程：

```text
Director
  → 叙事任务检查点
  → Writer
  → PostWriteGuard
  → Reviewer / 文字盲审
  → 验收检查点与质量门仲裁
  → Reviser（需要时）
  → Memory
  → ChapterFinalizer
```

每次 Agent 调用主要由以下上下文组成：

```text
STATIC system
SEMI shared chapter context
SEMI agent identity
SEMI agent suffix
DYNAMIC task input
```

现有代码已经具备：

- `buildChapterContextShared`：同章角色共享章节事实；
- `promptCacheScope = novel:{projectId}:{chapterNumber}`：同章缓存路由一致；
- shared 前缀 cache breakpoint；
- `semiLayerSharedCache`：运行内避免重复构建字符串；
- `contextMode=editor`：Reviser 不读取全书 shared；
- `contextMode=identity_only`：盲审只读取正文和文字编辑身份。

因此，当前问题并不是“每个角色都按全价重新读取所有上下文”，而是：

1. 首次 shared 依然很大；
2. Provider 缓存并非永久可靠；
3. 实体档案仍以全文注入为主；
4. 工具调用多轮会重复携带会话历史；
5. 下一章需要重建新的 shared；
6. Writer 整章生成在复杂章节中可能存在较高边际成本。

## 3. 设计原则

### 3.1 保留领域分表，不做万能实体表

冲突、伏笔、线索虽然都属于剧情实体，但它们拥有不同字段和状态机：

```text
冲突：intensity / stage / participants / progressionMode
伏笔：category / status / plantMethod / recoverMethod / beats
线索：pointsTo / progress / currentStep / nextStep / isMisleading
```

如果合并为一张大表，将产生大量 NULL 字段、类型分支和运行时校验。因此：

- `novel_conflicts`、`novel_foreshadowing`、`novel_clues` 继续独立；
- 仅抽取跨类型的公共关系，如章节出场、实体关联、审计来源。

### 3.2 稳定身份与版本必须分离

Scene 与 SceneRevision 不应合并：

```text
novel_scenes          = 稳定场景身份
novel_scene_revisions = 某次计划或重写下的场景版本
```

这套分离对“同一场景经过多次重写但身份仍不变”至关重要。

可合并的是角色关联表，而不是 Scene/Revision 本身。

### 3.3 不机械删除冗余标识

`project_id`、`chapter_number` 理论上可通过 `chapter_id` 推导，但在以下情况下保留是合理的：

- 项目隔离查询；
- 日志和事件按章节检索；
- 数据审计与损坏恢复；
- SQLite 下避免高频 join；
- 形成覆盖索引。

是否删除应满足：

```text
没有独立查询用途
且没有隔离/审计用途
且存在一致性约束或可安全推导
且字段漂移风险高于查询收益
```

### 3.4 派生值不是天然冗余

`word_count` 可由正文计算，但读取频率高、正文可能很长。保留缓存值是合理的，前提是：

- 只有一个权威写入点；
- 写正文时同步更新；
- 有一致性检测或修复命令；
- 版本表中的 word_count 用于历史审计时也可保留。

因此最终方案不要求全面删除 `word_count`，而是要求统一计算函数和写入边界。

## 4. 数据结构目标方案

## 4.1 正文版本链收敛

### 现状

同一正文可能存在于：

```text
novel_chapters.content
novel_chapter_versions.content
novel_chapter_content_revisions.content
```

其中 `novel_chapter_versions` 与 `novel_chapter_content_revisions` 职责高度重叠。

### 目标状态

- `novel_chapter_content_revisions`：唯一不可变正文版本链；
- `novel_chapters.current_content_revision_id`：指向当前版本；
- `novel_chapters.content`：保留为当前版本读取缓存或在稳定后改为视图；
- `novel_chapter_versions`：停止新写、只读归档，最终删除。

### 写入模型

```ts
async function saveChapterRevision(input: {
  chapterId: string
  content: string
  source: VersionSource
}): Promise<ContentRevision> {
  return db.transaction(() => {
    const revision = contentRevisionStore.create({
      chapterId: input.chapterId,
      content: input.content,
      wordCount: countNovelWords(input.content),
      phase: input.source.phase,
      agentType: input.source.agentType,
      trigger: input.source.trigger,
    })

    chapterStore.update(input.chapterId, {
      currentContentRevisionId: revision.id,
      content: input.content, // 迁移期保留当前内容缓存
      wordCount: revision.wordCount,
    })

    return revision
  })()
}
```

### 迁移步骤

1. 统计两个版本表各自数据量与最新版本差异；
2. 将页面/API 读取切换到 `content_revisions`；
3. 移除 `novel_chapter_versions` 新写路径；
4. 灰度一版，只读对账；
5. 无差异后归档旧表；
6. 下个大版本删除。

### 验收标准

- 新生成、修订、重写、手工保存都只产生一条 V2 content revision；
- `current_content_revision_id` 指向最新版本；
- `novel_chapters.content` 与当前 revision 内容 hash 一致；
- 旧表新增行数保持为 0。

## 4.2 实体出场关系统一

### 现状

`chapter_spans` 在冲突、伏笔、线索、势力、物品、叙事等多张表中以 JSON 数组重复保存。

### 目标结构

```sql
CREATE TABLE novel_entity_appearances (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  chapter_id      TEXT NOT NULL,
  entity_type     TEXT NOT NULL,
  entity_id       TEXT NOT NULL,
  appearance_role TEXT NOT NULL DEFAULT 'present',
  source          TEXT NOT NULL,
  revision_id     TEXT,
  created_at      INTEGER NOT NULL,
  UNIQUE (chapter_id, entity_type, entity_id, appearance_role, revision_id)
);

CREATE INDEX idx_entity_appearances_chapter
  ON novel_entity_appearances(project_id, chapter_id, entity_type);

CREATE INDEX idx_entity_appearances_entity
  ON novel_entity_appearances(project_id, entity_type, entity_id);
```

字段说明：

| 字段 | 作用 |
|---|---|
| `chapter_id` | 稳定章节关联，避免章节编号调整造成漂移 |
| `project_id` | 项目隔离和覆盖索引，刻意保留 |
| `entity_type/entity_id` | 多态实体引用 |
| `appearance_role` | present / advance / mention / plant / reinforce / recover 等 |
| `source` | ai_arrange / memory_extract / manual / migration |
| `revision_id` | 可选，追踪某个正文/场景版本下的出场关系 |

### 与伏笔 beats 的边界

`appearance` 不替代伏笔 `beats`：

```text
appearance = 这一章与伏笔有关
beat       = 这一章对伏笔做了什么（埋设/强化/转向/回收）
```

两者可以同时存在，beats 仍是伏笔领域事实。

### Store API

```ts
interface EntityAppearanceStore {
  listByChapter(chapterId: string): EntityAppearance[]
  listByEntity(type: EntityType, entityId: string): EntityAppearance[]
  replaceChapterAppearances(input: {
    chapterId: string
    source: AppearanceSource
    revisionId?: string
    appearances: AppearanceDraft[]
  }): void
}
```

### 迁移策略

```text
阶段 A：新增表，旧 chapter_spans 保持权威
阶段 B：createXxx / ai-arrange / syncChapterDimensions 双写
阶段 C：对账任务比较 appearance 与 chapter_spans
阶段 D：prompt-builder 与矩阵读取切到 appearance
阶段 E：停止旧字段写入
阶段 F：删除 chapter_spans
```

### 对账规则

```ts
for (const entity of allEntities) {
  const oldChapters = expandChapterSpans(entity.chapterSpans)
  const newChapters = appearanceStore
    .listByEntity(entity.type, entity.id)
    .map(row => row.chapterId)

  reportDiff(entity, oldChapters, newChapters)
}
```

## 4.3 Scene Cast 关联表合并

### 保留

```text
novel_scenes
novel_scene_revisions
```

### 合并

```text
novel_scene_focus
novel_scene_presence
novel_scene_functions
        ↓
novel_scene_cast
```

### 目标结构

```sql
CREATE TABLE novel_scene_cast (
  scene_revision_id TEXT NOT NULL,
  character_id      TEXT NOT NULL,
  role              TEXT NOT NULL,
  function          TEXT,
  prominence        REAL,
  note              TEXT,
  PRIMARY KEY (scene_revision_id, character_id, role)
);
```

约束：

```sql
CHECK (role IN ('focus', 'present', 'functional'))
CHECK (
  (role = 'functional' AND function IS NOT NULL)
  OR role != 'functional'
)
```

转换逻辑：

```ts
function toSceneCast(scene: ChapterScene): SceneCastDraft[] {
  return [
    ...scene.focusCharacterIds.map(characterId => ({ characterId, role: 'focus' })),
    ...scene.presentCharacterIds.map(characterId => ({ characterId, role: 'present' })),
    ...scene.functionalCast.map(item => ({
      characterId: item.characterId,
      role: 'functional',
      function: item.function,
      prominence: item.prominence,
      note: item.note,
    })),
  ]
}
```

### 验收标准

- ScenePlan 往返序列化前后 focus/present/functionalCast 数量一致；
- 同一角色允许同时 focus + present，但调用侧需明确是否自动去重；
- 旧三表停止新增；
- 计划影子写对账无差异。

## 4.4 StoryEvent 与 MemoryEvent 职责收敛

### 建议职责

```text
novel_story_events  = 故事世界里发生了什么（语义事件账本）
novel_memory_events = 系统如何从正文推导并应用了什么（操作审计）
```

### StoryEvent

保留：

- chapter / scene / order；
- type / title / summary / outcome；
- parent event；
- event-entity relation；
- 事件状态与来源。

用于：

- 因果链；
- 剧情时间线；
- 下一章故事承接；
- 回滚与重建投影。

### MemoryEvent

收敛为：

```ts
interface MemoryOperationEvent {
  id: string
  projectId: string
  chapterId: string
  runId: string
  operation: 'create' | 'update' | 'link' | 'unlink'
  targetEntityType: string
  targetEntityId: string
  beforeJson?: string
  afterJson?: string
  reason?: string
  source: 'memory-agent' | 'sync-dimensions' | 'manual'
  createdAt: number
}
```

用于：

- Memory applyChanges 审计；
- 失败定位；
- 事务回滚或补偿；
- 对账。

### 不建议直接删一张账本

先建立转换和消费清单：

| 消费者 | 应读取 |
|---|---|
| 故事承接 / 因果链 | StoryEvent |
| Memory 调试 / 审计 | MemoryEvent |
| 矩阵投影 | StoryEvent + EntityAppearance |
| 数据修复 | MemoryEvent |

完成消费者切换后，再删除 MemoryEvent 中已经重复的语义字段。

## 4.5 Agent 日志冷热分离

### 现状

`novel_agent_logs` 同时存放：

- 元数据：角色、模型、耗时、token、状态；

### 目标结构

```sql
CREATE TABLE novel_agent_logs (

  user_message_blob  BLOB,

```

### 保留策略

```text
普通成功日志：payload 保留 30 天
失败日志：payload 保留 90 天
用户收藏/审计锁定：长期保留

```

### 写入伪代码

```ts
const payload = shouldPersistPayload(log)
  ? payloadStore.createCompressed({
      systemPrompt,
      chapterContext,
      userMessage,
      result,
      error,
    })
  : undefined

agentLogStore.create({
  ...metadata,
  payloadId: payload?.id,
})
```

### 注意

不要直接删除 `display_agent_name/type`，除非确认 UI 不需要“真实角色”和“展示角色”区分。Reviser 可能由相同底层 Agent 配置展示成不同角色，展示字段可能是有业务意义的副本。

## 5. 上下文架构目标方案

## 5.1 先建立成本测量基线

在改 Prompt 结构前，先记录每个 Context Section 的真实成本。

### 新增观测指标

```ts
interface ContextSectionMetric {
  sectionId: string
  chars: number
  estimatedTokens: number
  sourceHash: string
  mode: 'full' | 'summary' | 'on-demand'
}

interface AgentContextMetric {
  agentType: NovelAgentType
  chapterNumber: number
  systemChars: number
  sharedChars: number
  identityChars: number
  suffixChars: number
  dynamicChars: number
  toolSchemaChars: number
  roundTrips: number
  inputTokens: number
  cacheReadTokens: number
  cacheWriteTokens: number
}
```

### 必须回答的测量问题

1. 每章第一次调用 full-price input 是多少？
2. Director、Writer、Reviewer、Reviser 的成本占比分别是多少？
3. `formatArrangedEntities` 占 shared 的比例是多少？
4. 工具 schema 占输入的比例是多少？
5. 工具调用造成多少次完整历史重发？
6. cache-read / input token 比例是多少？
7. 相邻章节 shared 重复率是多少？
8. 多实体章节和普通章节的成本差异是多少？

### P0 验收标准

至少采集：

- 30 个普通章节；
- 10 个多实体章节；
- 10 个修订/重写章节；
- 至少两个 Provider 或模型。

没有这组基线，不进入场景级生成改造。

## 5.2 Context Chunk 协议

### 目标

把原来的一个大 shared 字符串拆成可度量、可缓存、可降级、可按需加载的块。

```ts
type ChunkMode = 'full' | 'summary' | 'on-demand' | 'disabled'
type ChunkPriority = 'required' | 'recommended' | 'optional'

interface ContextChunk {
  id: string
  versionKey: string
  priority: ChunkPriority
  estimatedTokens: number
  mode: ChunkMode
  content: string
  summary?: string
  entityRefs?: Array<{ type: string; id: string; name: string }>
}
```

### 建议 Chunk 列表

| Chunk | 内容 | 默认策略 |
|---|---|---|
| `chapter-info` | 章节号、章纲、定位、字数预算 | required/full |
| `narrative-task` | Director 批准的场景契约 | required/full |
| `story-ledger` | 上章承接、因果变化 | required/summary |
| `arranged-entities` | 本章出场实体 | required/动态 full/summary |
| `active-conflicts` | 活跃冲突状态 | recommended/summary |
| `pending-foreshadows` | 待推进/回收伏笔 | recommended/summary |
| `active-clues` | 未完成线索 | recommended/summary |
| `info-layers` | 信息差 | Writer/Reviewer required |
| `recent-recaps` | 最近章节摘要 | recommended/summary |
| `hooks` | 待兑现钩子 | required/full |
| `style-profile` | 人工文风目标 | Writer/Reviser required |
| `style-fingerprint` | 前文观测值 | optional/summary |
| `quality-rules` | 质量门阈值 | Writer/Reviewer required |

### Chunk 构建器

```ts
class NovelContextRegistry {
  constructor(private builders: Map<string, ContextChunkBuilder>) {}

  build(request: ContextRequest): ContextChunk[] {
    const policy = ROLE_CONTEXT_POLICIES[request.agentType]
    return policy.map(rule => {
      const chunk = this.builders.get(rule.chunkId)!.build(request)
      return applyMode(chunk, resolveChunkMode(rule, request.budget))
    })
  }
}
```

## 5.3 角色上下文策略

角色区分应由：

```text
薄身份 + 职责 + 输出协议 + 工具权限
```

故事事实应由共享 Chunk 提供。

### 建议策略

```ts
const ROLE_CONTEXT_POLICIES: Record<NovelAgentType, ChunkRule[]> = {
  director: [
    required('chapter-info', 'full'),
    required('story-ledger', 'summary'),
    required('active-conflicts', 'summary'),
    required('pending-foreshadows', 'summary'),
    recommended('recent-recaps', 'summary'),
    required('hooks', 'full'),
  ],

  writer: [
    required('chapter-info', 'full'),
    required('narrative-task', 'full'),
    required('arranged-entities', 'auto'),
    required('info-layers', 'summary'),
    recommended('story-ledger', 'summary'),
    required('style-profile', 'full'),
    optional('style-fingerprint', 'summary'),
  ],

  reviewer: [
    required('narrative-task', 'full'),
    required('arranged-entities', 'summary'),
    required('quality-rules', 'full'),
    recommended('story-ledger', 'summary'),
  ],

  reviser: [
    required('current-draft', 'full'),
    required('failed-items', 'full'),
    required('style-profile', 'summary'),
  ],

  memory: [
    required('chapter-content', 'full'),
    required('story-ledger', 'summary'),
    required('arranged-entities', 'summary'),
    required('hooks', 'full'),
  ],
}
```

### 角色薄身份示例

```text
你是 Writer。
职责：把已批准的 NarrativeTask 写成完整章节正文。
边界：不改变世界事实，不越过 POV 信息边界，不输出解释过程。
输出：只输出正文。
可用工具：novel_ask_story（仅在摘要不足时查询实体事实）。
```

世界规则、文风档案、章节事实不再复制进每个角色 identity，而由 Chunk 按策略注入。

## 5.4 实体详情自动降级

### 决策规则

```ts
function chooseEntityChunkMode(input: {
  entityCount: number
  fullTokens: number
  remainingBudget: number
}): 'full' | 'summary' {
  if (input.entityCount <= 8 && input.fullTokens <= input.remainingBudget * 0.35) {
    return 'full'
  }
  return 'summary'
}
```

### Summary 结构

```ts
interface EntityContextSummary {
  id: string
  type: string
  name: string
  chapterRole: string
  currentState: string
  mustDo?: string
  mustNotKnow?: string
}
```

示例：

```text
[conflict: C17] 顾问团与主角的数据控制权争夺
状态：escalating / 7
本章任务：迫使主角在公开妥协与失去服务器权限之间选择
涉及角色：叶明远、周启航
需要完整 stakes 或历史推进时调用 novel_ask_story({type:"conflict", id:"C17"})
```

### 工具调用限制

按需检索并不是无限调用：

```ts
const ON_DEMAND_LIMITS = {
  director: 4,
  writer: 6,
  reviewer: 4,
  reviser: 2,
  memory: 2,
}
```

超过限制后不再允许拉取，避免工具往返抵消上下文节省。

## 5.5 Token 预算与降级策略

```ts
interface ContextBudget {
  maxInputTokens: number
  reservedForDynamicTask: number
  reservedForToolSchemas: number
  reservedForOutput: number
}

function allocateContextBudget(budget: ContextBudget): number {
  return budget.maxInputTokens
    - budget.reservedForDynamicTask
    - budget.reservedForToolSchemas
    - budget.reservedForOutput
}
```

降级顺序必须稳定：

```text
1. 删除 optional Chunk
2. recommended Chunk 从 full 降 summary
3. arranged-entities 从 full 降 summary
4. recent-recaps 只保留最近 1 章
5. style-fingerprint 降 on-demand
6. 仍超限则阻止生成并展示超限明细
```

不能为了塞进窗口而删除：

```text
NarrativeTask
POV 与信息边界
本章必须出场角色
活跃冲突目标
必须兑现的钩子
用户明确写作指令
```

## 5.6 跨章复用：先测量，再实现增量

不建议直接对整段 Markdown 做 diff。更安全的方式是对 Chunk 做版本哈希：

```ts
interface ContextChunkCacheEntry {
  projectId: string
  chunkId: string
  versionKey: string
  content: string
  contentHash: string
  updatedAt: number
}
```

`versionKey` 由数据版本生成：

```ts
const versionKey = hash({
  projectUpdatedAt,
  entityRevisionIds,
  latestMemoryEventId,
  styleProfileVersion,
})
```

相邻章节可以复用未变化 Chunk：

```ts
const chunks = registry.build(request)
for (const chunk of chunks) {
  const cached = cache.get(projectId, chunk.id, chunk.versionKey, chunk.contentHash)
  if (cached) useCachedChunk(cached)
  else cache.put(chunk)
}
```

失效入口：

- Memory `applyChanges`；
- `syncChapterDimensions`；
- 手工编辑实体；
- 文风档案变更；
- 章节计划/正文版本切换。

## 6. 场景级生成：作为最后阶段灰度

### 为什么暂缓

场景级生成可能降低单次上下文，但会增加：

- LLM 调用次数；
- system/tool 固定开销；
- 场景间衔接问题；
- 合并与织补步骤；
- 全章质量复检复杂度；
- 中断续跑状态管理。

因此它不是 P1/P2 的优化手段，而是 P4 的可选生成策略。

### 启用条件

满足以下任意三项才进入候选：

```text
sceneCount >= 3
arrangedEntityCount >= 8
Writer 初始输入超过 token 预算
整章 Writer 历史平均输入 >= 15k token
已存在批准的 ChapterScenePlan
Provider 缓存命中率低于目标值
```

### 目标流程

```text
ChapterScenePlan
  → Scene 1 Writer
  → Scene 2 Writer（带前场景压缩承接）
  → Scene N Writer
  → Chapter Weaver（只做衔接，不重写剧情）
  → 全章 PostWriteGuard
  → 全章 Reviewer
  → 全章 Reviser
```

### 场景输入

```ts
interface SceneWriterInput {
  chapterContract: string
  scene: ChapterScene
  sceneCast: SceneCast[]
  priorSceneHandoff?: string
  relevantEntities: EntityContextSummary[]
  povInformationBoundary: string
  targetWords: number
}
```

### 场景间承接

不能直接携带上一场全文，使用结构化 handoff：

```ts
interface SceneHandoff {
  physicalState: string[]
  knowledgeChanges: string[]
  relationshipChanges: string[]
  unresolvedPressure: string[]
  lastVisibleAction: string
}
```

### 灰度实验

随机选择满足条件章节：

```text
Control：整章 Writer
Treatment：场景 Writer + Weaver
```

对比指标：

- input/output/cache-read token；
- 总 LLM 调用次数；
- 总耗时；
- PostWriteGuard 重写率；
- Reviewer 评分；
- Reviser patch 数；
- 人工最终采用率；
- 场景衔接问题数。

只有在**成本下降且质量不退化**时扩大灰度。

## 9. 数据迁移安全规范

所有结构迁移遵循：

```text
新增结构
  → 双写
  → 对账
  → 切读
  → 停旧写
  → 观察一个版本
  → 删除旧结构
```

禁止：

- 新表一建好就删旧列；
- 未统计消费者就删除表；
- 未提供 Feature Flag 就切换核心生成路径；
- 将历史数据用不可靠推断批量回填；
- 为了规范化删除日志/事件中的关键审计字段。

每个迁移任务必须提供：

```ts
interface MigrationAcceptance {
  sourceRows: number
  targetRows: number
  mismatchRows: number
  orphanRows: number
  duplicateRows: number
  rollbackVerified: boolean
}
```

## 10. 关键风险与应对

### 风险 1：Context Summary 遗漏事实

应对：

- required facts 永不降级；
- summary 携带实体 ID；
- 提示 Agent 缺细节时调 `novel_ask_story`；
- Reviewer 检查实体执行；
- 对比 full/summary 一致性 fixture。

### 风险 2：按需工具调用抵消 token 收益

应对：

- 每角色工具调用上限；
- 小章节直接 full；
- 高频实体优先 full；
- 记录 round-trip 与工具 schema 成本。

### 风险 3：版本链切换丢历史

应对：

- 旧表只读保留一个版本；
- 按 chapter/version hash 对账；
- 页面先切读，再停写；
- 不立即删除旧表。

### 风险 4：Appearance 多态引用无数据库外键

因为 `entity_type/entity_id` 指向多张表，SQLite 无法建立传统外键。应对：

- Store 写入前校验实体存在；
- 定期 orphan 扫描；
- 删除实体时显式级联 appearance；
- 候选实体转正式实体时迁移关联。

### 风险 5：场景级生成质量下降

应对：

- 最后阶段灰度；
- 保留整章模式；
- 结构化 SceneHandoff；
- 全章 Weaver + 全章质量门；
- 以人工采用率为最终指标。

## 12. 最终决策摘要

### 立即执行

- 建立 token/上下文测量基线；
- 停止正文旧版本表双写；
- Agent 日志大文本冷热分离；
- 合并 Scene Cast 三表；
- 删除明确废弃列；
- 修复提示词协议测试漂移。

### 分阶段执行

- 抽取统一 EntityAppearance；
- StoryEvent 与 MemoryEvent 职责收敛；
- Context Chunk + 角色策略 + 实体摘要；
- 角色薄身化；
- 必要时增加跨章 Chunk 缓存。

### 暂缓

- 直接删除所有 `project_id/chapter_number`；
- 删除 Scene/SceneRevision 分层；
- 合并冲突/伏笔/线索为万能实体表；
- 未测量成本就把默认 Writer 改成场景级生成；
- 未经双写对账就删除 `chapter_spans` 或旧版本表。

最终优先级：

> **先测量、再止双写；先统一横切关系、再做 Prompt 分块；场景级生成最后灰度。**

# 小说创作 Agent：数据结构与生成架构统一方案

> 状态：合并后的最终方案
>
> 本方案已归并早期现状诊断、优化建议、工程实施节奏、迁移安全、验收指标与灰度策略。
>
> 合并原则：**用优化建议找问题，用实施方案定节奏；所有诊断保留，所有高风险改造先测量、再双写、再切读、最后灰度。**

---

## 1. 方案结论

当前系统的主要问题不是“架构方向错了”，而是多轮迁移后留下了三组可治理问题：

1. **数据结构冗余**
   - 正文版本存在双轨写入；
   - `chapter_spans` 在多张实体表重复；
   - Scene 角色关联被拆成三张同构表；
   - Agent 日志把元数据和完整 Prompt 文本混在一张表。

2. **上下文利用不充分**
   - 同章 shared 已有缓存复用，但实体档案仍以全文注入；
   - 不同角色仍通过上下文差异实现区分；
   - 跨章 Chunk 没有复用；
   - Writer 整章长上下文在复杂章节可能成本过高。

3. **技术债迁移边界不清**
   - 新旧版本链并存；
   - StoryEvent 与 MemoryEvent 双账本职责重叠；
   - 部分废弃列仍保留；
   - 若直接删除或切换，容易破坏历史版本和章节时间线。

最终采用的处理顺序：

```text
P0 建立测量基线
  ↓
P1 低风险止血：停双写、日志冷热分离、Scene Cast 合并、废弃列清理
  ↓
P2 统一公共横切面：实体出场关系、双账本职责
  ↓
P3 上下文优化：Context Chunk、角色薄身份、实体摘要、预算降级
  ↓
P4 场景级生成灰度：仅在成本和质量数据成立时启用
```

## 2. 当前架构诊断

### 2.1 数据层诊断

当前数据库约 53 张表。53 张表本身不是错误；真正的问题是重复、双轨和大文本混存。

#### 诊断 A：正文版本双写

同一正文可能同时存在于：

```text
novel_chapters.content
novel_chapter_versions.content
novel_chapter_content_revisions.content
```

其中：

- `novel_chapter_versions` 是旧版本表；
- `novel_chapter_content_revisions` 是 V2 不可变内容版本链；
- `novel_chapters.content` 是当前正文缓存。

这会导致：

- 同一正文至少两份，某些路径下三份；
- 前端版本面板、后端生成流程、历史回滚读取来源不一致；
- 新功能必须同时维护两套版本语义。

#### 诊断 B：`chapter_spans` 多表重复

`chapter_spans` 同时存在于多张实体表：

```text
novel_conflicts
novel_factions
novel_foreshadowing
novel_clues
novel_items
novel_narratives
```

这些表都表示“某个实体在哪些章节出场”，但目前各存一份 JSON 区间。

问题：

- 查询“第 N 章有哪些实体出场”需要 union 多表；
- 每次实体类型新增都可能再复制一次字段；
- 章节重写时同步逻辑分散；
- JSON 区间难以高效索引。

#### 诊断 C：Scene 角色关联三表同构

当前：

```text
novel_scene_focus
novel_scene_presence
novel_scene_functions
```

三张表在 `scene_revision_id + character_id` 上高度同构，仅功能角色多几个字段。

需要保留的是：

```text
novel_scenes
novel_scene_revisions
```

因为 Scene 与 SceneRevision 分别表达稳定身份和版本状态，不应为了减少表数量而合并。

#### 诊断 D：Agent 日志大文本混存

`novel_agent_logs` 同时保存：

- Agent、章节、阶段、耗时、token、状态；
- system prompt；
- chapter context；
- user message；
- task input；
- result；
- error。

日志表因此成为超大行集合。审计查询和页面列表通常只需要元数据，不需要整段 Prompt。

#### 诊断 E：StoryEvent 与 MemoryEvent 双账本

```text
novel_story_events
novel_memory_events
```

两者都在表达“这一章发生了什么”。

合理边界应是：

```text
StoryEvent  = 故事世界里发生了什么
MemoryEvent = 系统如何从正文推导并应用了什么
```

当前两者职责存在重叠，需要收敛，而不是直接删除其中一张。

#### 诊断 F：明确废弃列

部分字段已只用于兼容：

```text
conflicts.first_chapter / last_chapter
factions.first_chapter / last_chapter
```

如果写路径已经不再使用，应在迁移期结束后删除，避免继续误导后续实现。

### 2.2 生成层诊断

工作流：

```text
Director
  → 检查点 1：叙事任务
  → Writer
  → PostWriteGuard
  → Reviewer / 文字盲审
  → 检查点 2：验收
  → Reviser（可选或强制）
  → Memory
  → Finalizer
```

当前每次 Agent 调用上下文分为：

```text
STATIC  system
SEMI    shared chapter context
SEMI    agent identity
SEMI    agent suffix
DYNAMIC task input
```

现有缓存机制：

- `buildChapterContextShared` 同章角色共享；
- `promptCacheScope = novel:{projectId}:{chapterNumber}`；
- shared 前缀 cache breakpoint；
- `semiLayerSharedCache`；
- Reviser `contextMode=editor`；
- 盲审 `contextMode=identity_only`。

所以“每个角色都完全重复全价输入所有上下文”并不准确。prompt cache 已经缓解了跨角色重复。

剩余问题：

1. 首次 shared 仍然很大；
2. Provider 缓存不可靠或失效时会重新全价；
3. `formatArrangedEntities` 把实体档案全文注入；
4. 工具调用多轮会重复携带会话历史；
5. 下一章必须重建 shared；
6. Writer 整章长上下文的边际成本未知。

因此生成层优化不能假设场景级生成必然更优，需要先测量。

## 3. 设计原则

### 3.1 保留领域分表

冲突、伏笔、线索继续独立：

```text
冲突：intensity / stage / participants / progressionMode
伏笔：category / status / plantMethod / recoverMethod / beats
线索：pointsTo / progress / currentStep / nextStep / isMisleading
```

不合并成万能实体表，因为状态机、字段和验收逻辑不同。

### 3.2 统一公共横切面

跨实体公共信息应抽出来：

- 实体章节出场；
- 场景角色关系；
- 正文版本来源；
- Agent 审计载荷；
- 操作审计。

### 3.3 稳定身份与版本分离

```text
novel_scenes          = 稳定场景身份
novel_scene_revisions = 版本状态
```

只合并 Focus/Presence/Function 为 SceneCast，不合并 Scene/SceneRevision。

### 3.4 不机械删除冗余标识

`project_id`、`chapter_number` 如果有以下用途可以保留：

- 项目隔离；
- 日志检索；
- 覆盖索引；
- 审计恢复；
- 减少高频 join。

删除字段的判断：

```text
没有独立查询用途
没有隔离/审计用途
可以安全推导
字段漂移风险高于查询收益
```

### 3.5 派生值有边界地保留

`word_count` 可以保留为缓存值，但必须满足：

- 只有一个权威计算函数；
- 写入正文时同步；
- 可运行一致性修复；
- 版本表中保留是为了审计。

## 4. 数据结构统一方案

## 4.1 正文版本链收敛

### 目标状态

```text
novel_chapter_content_revisions
  = 唯一不可变正文版本链

novel_chapters.current_content_revision_id
  = 当前版本指针

novel_chapters.content
  = 当前版本读取缓存，稳定后可改视图或计算字段

novel_chapter_versions
  = 只读归档，停止新写，最终删除
```

### 写入模型

```ts
async function saveChapterRevision(input: {
  chapterId: string
  content: string
  source: VersionSource
}): Promise<ContentRevision> {
  return db.transaction(() => {
    const revision = contentRevisionStore.create({
      chapterId: input.chapterId,
      content: input.content,
      wordCount: countNovelWords(input.content),
      phase: input.source.phase,
      agentType: input.source.agentType,
      trigger: input.source.trigger,
    })

    chapterStore.update(input.chapterId, {
      currentContentRevisionId: revision.id,
      content: input.content,
      wordCount: revision.wordCount,
    })

    return revision
  })()
}
```

### 迁移步骤

```text
1. 梳理旧版本表全部消费者
2. 前端版本面板和后端 API 切到 content_revisions
3. 停止 novel_chapter_versions 新写
4. 新旧版本按 chapter/content hash 对账
5. 观察一个版本
6. 旧表归档，下个主版本删除
```

### 验收标准

- 新写入不再进入旧版本表；
- 当前章节内容与 current revision hash 一致；
- 修订、重写、手工保存都产生正确 VersionSource；
- 版本面板历史顺序无跳变；
- 可回滚到迁移前读取路径。

## 4.2 实体出场关系统一

### 目标结构

```sql
CREATE TABLE novel_entity_appearances (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  chapter_id      TEXT NOT NULL,
  entity_type     TEXT NOT NULL,
  entity_id       TEXT NOT NULL,
  appearance_role TEXT NOT NULL DEFAULT 'present',
  source          TEXT NOT NULL,
  revision_id     TEXT,
  created_at      INTEGER NOT NULL,
  UNIQUE (chapter_id, entity_type, entity_id, appearance_role, revision_id)
);

CREATE INDEX idx_entity_appearances_chapter
  ON novel_entity_appearances(project_id, chapter_id, entity_type);

CREATE INDEX idx_entity_appearances_entity
  ON novel_entity_appearances(project_id, entity_type, entity_id);
```

### 字段解释

| 字段 | 用途 |
|---|---|
| `project_id` | 项目隔离、覆盖索引、审计恢复 |
| `chapter_id` | 稳定章节引用，不受章节编号调整影响 |
| `entity_type/entity_id` | 多态实体引用 |
| `appearance_role` | present / advance / mention / plant / reinforce / recover |
| `source` | ai_arrange / memory_extract / manual / migration |
| `revision_id` | 可追踪某正文或场景版本 |

### 与伏笔 beats 的关系

```text
appearance = 本章与该伏笔有关
beat       = 本章对伏笔执行了什么动作
```

不互相替代。

### 迁移步骤

```text
1. 新增表
2. ai-arrange 双写
3. Memory applyChanges 双写
4. syncChapterDimensions 双写
5. 手工实体编辑双写
6. 对账 appearance 与 chapter_spans
7. Prompt/矩阵切读
8. 停旧字段写入
9. 观察后删除 chapter_spans
```

### 对账伪代码

```ts
for (const entity of allEntities) {
  const oldChapterIds = expandChapterSpans(entity.chapterSpans)
    .map(chapterNumber => resolveChapterId(chapterNumber))

  const newChapterIds = appearanceStore
    .listByEntity(entity.type, entity.id)
    .map(row => row.chapterId)

  if (!sameSet(oldChapterIds, newChapterIds)) {
    reportMismatch(entity, oldChapterIds, newChapterIds)
  }
}
```

## 4.3 Scene Cast 合并

### 目标结构

```sql
CREATE TABLE novel_scene_cast (
  scene_revision_id TEXT NOT NULL,
  character_id      TEXT NOT NULL,
  role              TEXT NOT NULL,
  function          TEXT,
  prominence        REAL,
  note              TEXT,
  PRIMARY KEY (scene_revision_id, character_id, role),
  CHECK (role IN ('focus', 'present', 'functional')),
  CHECK (
    role != 'functional'
    OR function IS NOT NULL
  )
);
```

### 转换逻辑

```ts
function toSceneCast(scene: ChapterScene): SceneCastDraft[] {
  return [
    ...scene.focusCharacterIds.map(characterId => ({
      characterId,
      role: 'focus' as const,
    })),
    ...scene.presentCharacterIds.map(characterId => ({
      characterId,
      role: 'present' as const,
    })),
    ...scene.functionalCast.map(item => ({
      characterId: item.characterId,
      role: 'functional' as const,
      function: item.function,
      prominence: item.prominence,
      note: item.note,
    })),
  ]
}
```

### 验收标准

- focus/present/functionalCast 往返数量一致；
- 同一角色允许 focus + present，读取侧明确去重规则；
- 功能位不丢失；
- 旧三表停止新增；
- ScenePlan 影子写对账一致。

## 5. 上下文统一方案

## 5.1 P0 成本测量

先不修改 Prompt，先建立指标。

### 指标结构

```ts
interface ContextSectionMetric {
  sectionId: string
  chars: number
  estimatedTokens: number
  sourceHash: string
  mode: 'full' | 'summary' | 'on-demand'
}

interface AgentContextMetric {
  agentType: NovelAgentType
  chapterNumber: number
  systemChars: number
  sharedChars: number
  identityChars: number
  suffixChars: number
  dynamicChars: number
  toolSchemaChars: number
  roundTrips: number
  inputTokens: number
  cacheReadTokens: number
  cacheWriteTokens: number
}
```

### 必须回答

1. 每章首次调用的 full-price input；
2. 每个 Agent 成本占比；
3. `formatArrangedEntities` 占 shared 比例；
4. 工具 schema 占输入比例；
5. 工具调用导致的 round-trip 次数；
6. cache-read / input 比例；
7. 相邻章节 shared 重复率；
8. 多实体章节和普通章节成本差。

### 采样要求

```text
30 个普通章节
10 个多实体章节
10 个修订/重写章节
至少两个 Provider 或模型
```

## 5.2 Context Chunk 协议

把 shared 从一个大字符串拆成独立块：

```ts
type ChunkMode = 'full' | 'summary' | 'on-demand' | 'disabled'
type ChunkPriority = 'required' | 'recommended' | 'optional'

interface ContextChunk {
  id: string
  versionKey: string
  priority: ChunkPriority
  estimatedTokens: number
  mode: ChunkMode
  content: string
  summary?: string
  entityRefs?: Array<{ type: string; id: string; name: string }>
}
```

### 建议 Chunk

| Chunk | 内容 | 策略 |
|---|---|---|
| `chapter-info` | 章节号、章纲、定位、字数 | required/full |
| `narrative-task` | 已批准叙事任务 | required/full |
| `story-ledger` | 上章承接与因果变化 | required/summary |
| `arranged-entities` | 本章出场实体 | required/动态 |
| `active-conflicts` | 活跃冲突 | recommended/summary |
| `pending-foreshadows` | 待推进/回收伏笔 | recommended/summary |
| `active-clues` | 未完成线索 | recommended/summary |
| `info-layers` | 信息差 | Writer/Reviewer required |
| `recent-recaps` | 最近章节摘要 | recommended/summary |
| `hooks` | 待兑现钩子 | required/full |
| `style-profile` | 人工文风目标 | Writer/Reviser required |
| `style-fingerprint` | 前文观测值 | optional/summary |
| `quality-rules` | 质量门规则 | Writer/Reviewer required |

## 5.3 角色上下文策略

角色区分来自：

```text
薄身份 + 职责 + 输出协议 + 工具权限
```

故事事实来自共享 Chunk。

### 策略示例

```ts
const ROLE_CONTEXT_POLICIES = {
  director: [
    required('chapter-info', 'full'),
    required('story-ledger', 'summary'),
    required('active-conflicts', 'summary'),
    required('pending-foreshadows', 'summary'),
    required('hooks', 'full'),
    recommended('recent-recaps', 'summary'),
  ],

  writer: [
    required('chapter-info', 'full'),
    required('narrative-task', 'full'),
    required('arranged-entities', 'auto'),
    required('info-layers', 'summary'),
    required('style-profile', 'full'),
    recommended('story-ledger', 'summary'),
    optional('style-fingerprint', 'summary'),
  ],

  reviewer: [
    required('narrative-task', 'full'),
    required('arranged-entities', 'summary'),
    required('quality-rules', 'full'),
    recommended('story-ledger', 'summary'),
  ],

  reviser: [
    required('current-draft', 'full'),
    required('failed-items', 'full'),
    required('style-profile', 'summary'),
  ],

  memory: [
    required('chapter-content', 'full'),
    required('story-ledger', 'summary'),
    required('arranged-entities', 'summary'),
    required('hooks', 'full'),
  ],
}
```

### 薄身份示例

```text
你是 Writer。
职责：把已批准的 NarrativeTask 写成完整章节正文。
边界：不改变故事事实，不越过 POV 信息边界，不输出解释过程。
输出：只输出正文。
可用工具：novel_ask_story（仅在摘要不足时查询实体事实）。
```

## 5.4 实体详情降级

### 模式选择

```ts
function chooseEntityChunkMode(input: {
  entityCount: number
  fullTokens: number
  remainingBudget: number
}): 'full' | 'summary' {
  if (
    input.entityCount <= 8 &&
    input.fullTokens <= input.remainingBudget * 0.35
  ) {
    return 'full'
  }

  return 'summary'
}
```

### 实体摘要

```ts
interface EntityContextSummary {
  id: string
  type: string
  name: string
  chapterRole: string
  currentState: string
  mustDo?: string
  mustNotKnow?: string
}
```

示例：

```text
[conflict: C17] 顾问团与主角的数据控制权争夺
状态：escalating / 7
本章任务：迫使主角在公开妥协与失去服务器权限之间选择
涉及角色：叶明远、周启航
需要完整 stakes 或历史推进时调用 novel_ask_story({type:"conflict", id:"C17"})
```

### 工具调用上限

```ts
const ON_DEMAND_LIMITS = {
  director: 4,
  writer: 6,
  reviewer: 4,
  reviser: 2,
  memory: 2,
}
```

防止按需查询变成更多轮调用，反而增加总 token。

## 5.5 Token 预算与降级

```ts
interface ContextBudget {
  maxInputTokens: number
  reservedForDynamicTask: number
  reservedForToolSchemas: number
  reservedForOutput: number
}

function allocateContextBudget(budget: ContextBudget): number {
  return budget.maxInputTokens
    - budget.reservedForDynamicTask
    - budget.reservedForToolSchemas
    - budget.reservedForOutput
}
```

降级顺序：

```text
1. 删除 optional Chunk
2. recommended Chunk 从 full 降 summary
3. arranged-entities 从 full 降 summary
4. recent-recaps 只保留最近 1 章
5. style-fingerprint 降 on-demand
6. 仍超限则阻止生成并展示明细
```

不可降级内容：

```text
NarrativeTask
POV 与信息边界
本章必须出场角色
活跃冲突目标
必须兑现的钩子
用户明确写作指令
```

## 5.6 跨章 Chunk 复用

不做 Markdown 全文 diff，改做 Chunk 版本哈希：

```ts
interface ContextChunkCacheEntry {
  projectId: string
  chunkId: string
  versionKey: string
  content: string
  contentHash: string
  updatedAt: number
}
```

```ts
const versionKey = hash({
  projectUpdatedAt,
  entityRevisionIds,
  latestMemoryEventId,
  styleProfileVersion,
})
```

复用逻辑：

```ts
for (const chunk of registry.build(request)) {
  const cached = cache.get(projectId, chunk.id, chunk.versionKey, chunk.contentHash)
  if (cached) useCachedChunk(cached)
  else cache.put(chunk)
}
```

失效入口：

- Memory `applyChanges`；
- `syncChapterDimensions`；
- 手工编辑实体；
- 文风档案变更；
- 正文或计划版本切换。

## 6. 场景级生成作为最后灰度

### 为什么放最后

场景级生成能降低单次上下文，但会增加：

- LLM 调用次数；
- system/tool 固定开销；
- 场景衔接问题；
- Weaver 合并成本；
- 中断恢复复杂度；
- 全章质量门复检复杂度。

因此只有在数据证明 Writer 整章是主要成本后才启用。

### 启用条件

满足任意三项：

```text
sceneCount >= 3
arrangedEntityCount >= 8
Writer 初始输入超过 token 预算
整章 Writer 历史平均输入 >= 15k token
已存在批准的 ChapterScenePlan
Provider 缓存命中率低于目标值
```

### 目标流程

```text
ChapterScenePlan
  → Scene 1 Writer
  → Scene 2 Writer（带前场景压缩承接）
  → Scene N Writer
  → Chapter Weaver（只补衔接，不改剧情）
  → 全章 PostWriteGuard
  → 全章 Reviewer
  → 全章 Reviser
```

### 场景输入

```ts
interface SceneWriterInput {
  chapterContract: string
  scene: ChapterScene
  sceneCast: SceneCast[]
  priorSceneHandoff?: SceneHandoff
  relevantEntities: EntityContextSummary[]
  povInformationBoundary: string
  targetWords: number
}
```

### 场景间承接

```ts
interface SceneHandoff {
  physicalState: string[]
  knowledgeChanges: string[]
  relationshipChanges: string[]
  unresolvedPressure: string[]
  lastVisibleAction: string
}
```

### 灰度对比

| 指标 | 目标 |
|---|---|
| 总 token | 至少下降 20% |
| 总调用次数 | 不失控 |
| Reviewer 评分 | 不下降 |
| PostWriteGuard 重写率 | 不显著上升 |
| Reviser patch 数 | 不显著上升 |
| 人工采用率 | 不下降 |
| 场景衔接缺陷 | 可接受 |

如果不满足，场景级生成保留为高级可选模式，不替代默认工作流。

## 9. 数据迁移安全规范

所有结构迁移遵循：

```text
新增结构
  → 双写
  → 对账
  → 切读
  → 停旧写
  → 观察一个版本
  → 删除旧结构
```

禁止：

- 新表一建好就删旧列；
- 未统计消费者就删表；
- 未提供 Feature Flag 就切换核心生成路径；
- 用不可靠推断批量回填历史数据；
- 为规范化删除关键审计字段。

每个迁移任务提供：

```ts
interface MigrationAcceptance {
  sourceRows: number
  targetRows: number
  mismatchRows: number
  orphanRows: number
  duplicateRows: number
  rollbackVerified: boolean
}
```

## 10. 关键风险与应对

### 风险 1：Context Summary 遗漏事实

应对：

- required facts 永不降级；
- summary 携带实体 ID；
- Agent 可调用 `novel_ask_story`；
- Reviewer 检查实体执行；
- full/summary fixture 对比。

### 风险 2：工具调用抵消 token 收益

应对：

- 每角色工具调用上限；
- 小章节直接 full；
- 高频实体优先 full；
- 记录 round-trip 和工具 schema 成本。

### 风险 3：版本链切换丢历史

应对：

- 旧表只读保留；
- 按 chapter/version hash 对账；
- 页面先切读，再停写；
- 不立即删除旧表。

### 风险 4：Appearance 多态引用无外键

应对：

- Store 写入前校验实体存在；
- 定期 orphan 扫描；
- 删除实体时显式级联；
- 候选实体转正式实体时迁移关联。

### 风险 5：场景级生成质量下降

应对：

- 最后灰度；
- 保留整章模式；
- 结构化 SceneHandoff；
- 全章 Weaver 与全章质量门；
- 以人工采用率为最终指标。

## 12. 最终决策摘要

### 立即执行

- 建立 token/上下文测量基线；
- 停止正文旧版本表双写；
- Agent 日志大文本冷热分离；
- 合并 Scene Cast 三表；
- 清理明确废弃列；
- 修复提示词协议测试漂移。

### 分阶段执行

- 抽取统一 EntityAppearance；
- StoryEvent 与 MemoryEvent 职责收敛；
- Context Chunk + 角色策略 + 实体摘要；
- 角色薄身份；
- 根据测量结果决定是否增加跨章 Chunk 缓存。

### 暂缓

- 直接删除所有 `project_id/chapter_number`；
- 删除 Scene/SceneRevision 分层；
- 合并冲突/伏笔/线索为万能实体表；
- 未测量成本就默认启用场景级生成；
- 未经双写对账就删除 `chapter_spans` 或旧版本表。

最终优先级：

> **先测量、再止双写；先统一横切关系、再做 Prompt 分块；场景级生成最后灰度。**

## 13. 执行配套（让方案真正落地）

前 12 节定义了"做什么、按什么顺序做"。本节补齐执行层面最容易被忽略的四件事：**开关清单、消费者清单、量化指标总表、决策留痕**。没有这些，方案在三个月后执行时会因为"记不清为什么这么定"而再次漂移。

### 13.1 Feature Flag 统一清单

方案的开关散落在各节，这里汇总成一张可执行的表。**所有开关默认关闭，逐项灰度开启**。

| Flag | 默认 | 影响面 | 开启前提 | 关闭方式 |

### 13.4 决策留痕（ADR 建议）

合并方案中"保留 vs 暂缓"的取舍，若不记录，三个月后会被当作"遗漏的优化"重新翻出来做一遍。建议为以下决策各写一条轻量 ADR（每条 5-10 行，含背景、决策、理由、反方观点、日期）：

1. 保留领域分表、不做万能实体表；
2. 保留 `project_id/chapter_number` 等冗余标识（有索引/隔离/审计价值）；
3. 保留 Scene / SceneRevision 分层，仅合并 Cast 三表；
4. 版本链收敛到 `content_revisions`，旧表只读归档；
5. StoryEvent 为语义账本、MemoryEvent 为操作审计；
6. 场景级生成默认不启用，仅在 A/B 达标后灰度。

### 13.5 可观测性补充

## 2. 章节正文编辑器

页面：`chapter-content-editor.tsx`、`detail-forms/chapter-form.tsx`、章节树和矩阵中的章节命令。

| 状态 | 操作 | 接口 | 请求、响应和页面字段 |
| --- | --- | --- | --- |
| 已交付 | 读取章节列表 | `GET /projects/:projectId/chapters` | `id/projectId/volume/volumeId/chapterNumber/title/content/wordCount/status/narrativeTask/outline/acceptanceResult/tension/rhythm/positioning/timeOffset/chapterEndingHook/recap/createdAt/updatedAt` |
| 已交付 | 读取章节 | `GET /chapters/:id` | 同上 |
| 已交付 | 创建章节 | `POST /projects/:projectId/chapters` | `chapterNumber/narrativeTask{description,type,targetEntity?,priority,positioning?}/volumeId?`；卷必须属于项目 |
| 已交付 | 保存章节 | `PATCH /chapters/:id` | `title/content/status/outline/volumeId/tension/positioning/timeOffset/chapterEndingHook/recap`；正文自动重算 `wordCount` 并创建 `manual_patch` revision |
| 已交付 | 完成章节 | `POST /chapters/:id/complete` | `content/title?`；进入 `review` |
| 已交付 | 发布章节 | `POST /chapters/:id/publish` | 无 body；正文非空、状态为 `review`、accept Review 必须绑定当前正文 hash 和 current revision、前序章节全部已发布 |
| 已交付 | 删除未发布章节 | `DELETE /chapters/:id` | 返回 `id/deleted` 并原子重排后续章节引用；`published` 返回 `409` |

用户路径：选择或创建章节 -> 编辑章纲/正文和章节元数据 -> 保存 -> 完成并进入审稿 -> 当前 revision 审稿通过 -> 二次确认发布。已发布章节不能 PATCH 正文/状态、回滚或删除；当前也没有撤回发布命令。

中间章保存响应可附 `derivedState{isMiddleRewrite,staleMarked?,affectedChapters?,message?}`。页面目前只 toast 提示，没有可点击的重建命令，详见 §22。

## 3. 工作流、编排与再修订页面

页面：`novel-conversation-panel.tsx` 的“工作流 / 反推 / 矩阵编排”页签及编排画布。

| 状态 | 操作 | 接口 | 契约 |
| --- | --- | --- | --- |
| 已交付 | 读取本章规范编排 | `GET /projects/:projectId/chapters/:chapterNumber/arranged-entities` | 返回 `projectId/chapterNumber/source/arrangedEntities/alternativeSource/alternative/divergence`；`source` 为 `entity-fields` 或 `ledger` |
| 已交付 | 正式创作 | `POST /projects/:projectId/chapters/:chapterNumber/create-flow` | SSE；`arrangedEntities?`、`modelId?{provider,modelId}`；同章任务互斥 |
| 已交付 | AI 编排 | `POST /projects/:projectId/chapters/:chapterNumber/ai-arrange` | SSE；基于 `outline` 生成并编排实体，不生成正文 |
| 已交付 | 正文反推 | `POST /projects/:projectId/chapters/:chapterNumber/reverse-arrange` | SSE；读取当前正文，只反推实体 |
| 已交付 | 定向再修订 | `POST /projects/:projectId/chapters/:chapterNumber/re-revise` | SSE；`content/arrangedEntities?`；只返回修订稿，不自动落库 |
| 已交付 | 取消同章任务 | `POST /projects/:projectId/chapters/:chapterNumber/cancel-active-flow` | 取消 workflow/discussion/arrange/reverse-arrange/re-revise，返回 `cancelled/kind/startedAt` |
| 已交付 | 检查点决策 | `POST /projects/:projectId/checkpoint/:checkpointId/decision` | `decision/userMessages?`；必须是当前检查点允许的 option |
| 已交付 | 同步兼容入口 | `POST /projects/:projectId/chapters/:chapterNumber/create-team` | `narrativeTask/rhythm?`；内部复用正式 Orchestrator 并自动批准检查点 |

`arrangedEntities` 字段：`characterIds/conflictIds/foreshadowIds/clueIds/factionIds/locationIds/itemIds/characterFunctions[{characterId,function,note?}]`。所有入口复用 `arrangedEntitiesSchema`、项目归属校验、同章任务注册器和 `ChapterFinalizer`。

提交边界：Writer/Reviewer/Reviser 运行在章前 Snapshot 语义上；Finalizer 在事务外调用 LLM 分析 Memory，再在一个短 SQLite 事务内提交正文、content revision、Memory 实体、MemoryEvent、章节维度和 Snapshot。Finalizer 返回的 `content` 与写库的清洗正文一致。

## 4. 群聊共创页面

页面：`novel-conversation-panel.tsx` 的“群聊”页签；群聊全局设置见 §10。

| 状态 | 操作 | 接口 | 契约 |
| --- | --- | --- | --- |
| 已交付 | 启动群聊创作 | `POST /projects/:projectId/chapters/:chapterNumber/create-discussion` | SSE；与工作流共用 `arrangedEntities/modelId`、项目归属和同章锁；成员与 Finalizer 的模型优先级统一为本次模型 > 运行启动时冻结的项目主模型 > Agent 配置/默认模型；Moderator 始终使用独立模型 |
| 已交付 | Writer 断点续跑 | `POST /projects/:projectId/chapters/:chapterNumber/create-discussion/:runId/resume` | 仅 `status=error && failedPhase=chapter_weaving`；恢复 transcript、scenes、arrangedEntities、首次显式成员模型和启动时冻结的项目主模型 |
| 已交付 | 群聊检查点兼容入口 | `POST /projects/:projectId/discussion-checkpoint/:checkpointId/decision` | 与统一检查点状态机共用 pending decision |
| 已交付 | 读取持久历史 | `GET /projects/:projectId/chapters/:chapterNumber/chat` | 工作流与群聊消息依靠 `phase/metadata.flowMode/runId/messageType` 区分 |

用户路径：选择章节和群聊模式 -> 确认编排角色并可选择本次成员模型 -> 启动 -> Moderator 按自身独立模型协调 -> 所有被点名角色发言 -> Reviewer/Reviser -> Finalizer -> 查看正文和审稿结果；Writer 编织失败时从同一 `runId` 继续，并沿用首次显式成员模型与首次冻结的项目主模型。

多角色合并只在认知、可见上下文、system、模型和温度完全相同时启用；缺 `knowledge`、存在章前 `secret` 或任一契约不一致时禁止合并。合并失败、缺段或段落校验失败会逐角色回退；每段仍分别经过格式校验与 Reviewer。`DiscussionRun.scenes` 仅是续跑输入，规范场景身份仍来自 `novel_scenes/novel_scene_revisions`。

## 24. 接口复用合理性检查

1. 工作流、群聊和兼容 create-team 共用 Orchestrator/Finalizer；AI 编排和反推只复用实体生成，不隐式写正文。
2. 工作流、群聊、自由聊天和角色生成的本次模型统一使用 `{provider,modelId}`，Provider 值为配置 ID；不再传可能重名的裸模型 ID。
3. 版本页面可保留 `/versions` 的详情/diff/快照体验，但实现必须委托 `content_revisions`；不能恢复旧表双写。
4. 角色“参与冲突”复用通用 edges 资源，不在角色表增加第二份 participants。
5. 文风档案由 Prompt Builder 按 Agent 编译；Prompt 模板覆盖继续复用 PromptManager，不在页面建立第二套模板解析顺序。
6. 群聊与自由聊天共用角色可见上下文和秘密隔离；调用合并是优化，不得改变成员发言、Reviewer 或审计语义。
7. P3 报告、context-preview、缓存和成本报告共用实际 Prompt 组装与 usage 数据；不能用估算值冒充 Provider usage。
8. 参考阶段 1 共用 source/section/quality/local report；P4-P9 应扩展持久 run/profile/template/binding，而不能把当前项目人物和账本当参考源存储。
9. 参考分析模型列表复用 `/api/providers`；章节生成应扩展现有 create-flow，不新增旁路创作流。
10. 矩阵是只读投影；Storyline/Scene 编辑必须创建 revision，不能直接更新投影结果。

## 25. 模糊项与待确认决策

1. 已发布章节的撤回、进入修订、废弃和删除语义尚未定义；当前统一拒绝正文修改、回滚和删除。
2. `asOfRevision` 是事实指纹校验还是历史投影读取；当前只实现前者。
3. 异步 outbox 投影启用条件、幂等消费、重试和 `projectionLag` 计算方式未固定；当前同步投影恒为 0。
4. 中间章 rebuild job 的影响范围、锁粒度、失败恢复、是否重跑 LLM 及费用确认未定义。
5. Storyline/Scene 人工 revision 的审核角色、状态机和与正文 revision 的绑定方式未定义。
6. Prompt 模板页面是否允许编辑内置模板、如何恢复默认、谁可编辑和项目/全局覆盖冲突提示未定义。
7. 群聊设置是继续全局生效还是改成按项目覆盖；当前是全局。
8. 角色弧光页面是否只读，还是开放一对一 CRUD 和阶段历史编辑；当前只有读取入口。
9. 参考小说 P4-P9 的生成开关默认值、抽样覆盖率、费用二次确认阈值、安全/相似度阈值、模板升级策略和原文删除时机未固定。
10. 参考导入源需求提到 Electron 安全文件桥，但当前实现使用浏览器 File API；是否必须迁移由桌面安全模型决定。
11. 参考解析的 `chapterPattern` 参数已接收但未生效；页面若开放该控件必须先实现解析器语义。
12. 原型图片缺失；未来原型新增字段时需要补接口字段与覆盖矩阵。

## 26. 需求覆盖结论

当前已闭合的核心链路为：

`N-1 Snapshot -> 章前约束/角色可见上下文 -> 工作流或群聊 -> Reviewer/Reviser -> Finalizer 原子提交 -> 当前 revision 审稿绑定 -> 顺序发布`

角色秘密隔离、本次模型选择、群聊成员完整发言、版本单链和发布终态已经进入同一逻辑。尚未闭合的三条产品链路必须单独排期：

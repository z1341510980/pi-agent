## 2. 产品定义

### 2.1 产品目标（一句话）

**在不改变任何生成行为的前提下，先把"钱花在哪、数据冗余在哪"量化清楚，并完成五处低风险止血，让后续 P2/P3/P4 改造建立在可测量、可回滚的基础上。**

### 2.2 三条收益

1. **成本可见**：P0 埋点与报表让每章每个 Agent 的 token 构成（system/shared/identity/suffix/dynamic/tool schema）有量化基线，直接支撑"是否值得做场景级生成/上下文分块"的决策。
2. **数据收敛**：P1 停掉正文旧版本表双写、Agent 日志大文本外置、Scene Cast 三表合并、废弃列清理后，消除 3 份正文共存、超大日志行、三表同构等结构性冗余，降低后续维护与迁移成本。
3. **低风险可回滚**：全部变更由默认关闭的 Feature Flag 控制，迁移遵循双写对账规范，任何一步异常可切回旧路径，不阻塞既有创作流程。

## 4. 需求池

优先级口径：P0 = Must have（本次必须交付）；P1 = Should have（本次必须交付）；未列入项默认 P2+。

### 4.1 P0：成本测量基线

#### P0-1 Context section 成本埋点（对应 T00-1）

- **说明**：在 `runAgentOnce`/`prompt-builder` 的上下文组装处旁路埋点（**不修改 Prompt 内容、不改变生成路径**），按 section 记录字符数与估算 token。
- **范围**：
  - 按 `ContextSectionMetric` 记录：`sectionId`、`chars`、`estimatedTokens`、`sourceHash`、`mode(full/summary/on-demand)`；
  - 覆盖 system / shared / identity / suffix / dynamic / tool schema 六类 section；
  - 复用既有 `novel_agent_logs` 的 token/round-trip 字段（input/output/cache-read/cache-write、llm_round_trips），补充 section 明细（落 payload 表或独立埋点表，由架构师定，默认随 P1-2 payload 表一并落地）。
- **验收标准（量化）**：
  1. 埋点开启后，每个 Agent 调用至少产出 1 条含六类 section 的度量记录；
  2. `sourceHash` 对相同文本稳定、对不同文本可区分；
  3. 埋点不改变既有 prompt 输出（抽样 5 章生成结果与埋点前 diff = 0）；
  4. 埋点性能开销：单次调用额外耗时 < 50ms（纯内存计算，无额外 IO）。

#### P0-2 Agent / 章节成本报表（对应 T00-2）

- **说明**：提供按项目、按章、按 Agent 维度的成本报表，回答"token 花在哪"。
- **范围**：
  - 必答指标（对齐方案 §5.1）：
    1. 每章首次调用 full-price input；
    2. 每个 Agent 成本占比（input + cache-read 口径）；
    3. `formatArrangedEntities`（实体档案）占 shared 比例；
    4. tool schema 占输入比例；
    5. 工具调用 round-trip 次数；
    6. cache-read / input 比例；
  - 展示载体：优先复用 `cache-monitor-panel` 数据源出图；若前端面板不可行，至少提供可导出 JSON/CSV 的报表脚本/接口（见待确认 Q-5）。
- **验收标准（量化）**：
  1. 报表能按 project_id + chapter_number 过滤，输出上述 6 项指标；
  2. 报表数据与 `novel_agent_logs` 埋点原始记录可追溯（每条报表行可下钻到日志）；
  3. 一次采样报告可在 5 分钟内生成（数据量 ≤ 100 章规模）。

#### P0-3 相邻章 shared 重复率统计（对应 T00-3）

- **说明**：统计相邻章节 `buildChapterContextShared` 输出的重复率，为跨章 Chunk 复用（P3）提供决策依据。
- **范围**：
  - 对相邻章 shared 文本做归一化（去空白/换行）后计算重复字符占比；
  - 分别统计"全 shared"与"仅实体档案 section"两个口径。
- **验收标准（量化）**：
  1. 对采样章节输出相邻章重复率（0~100%）分布（p50/p75/max）；
  2. 能输出 top 高频重复 section（如 chapter-info / story-ledger / arranged-entities）；
  3. 统计结果写入基线报告，作为 P3 是否做跨章缓存的输入（方案 §5.6）。

#### P0-4 基线采样与结论模板（对应 T00-4）

- **说明**：执行一次采样，产出结论模板，作为后续灰度的对照基准。
- **范围**：
  - 采样要求（对齐方案 §5.1）：≥ 30 普通章节 + 10 多实体章节 + 10 修订/重写章节，覆盖 ≥ 2 个 Provider/模型；
  - 结论模板固定字段：每 Agent 成本占比、实体档案占比、round-trip 分布、cache-read 占比、相邻章重复率、多实体 vs 普通章成本差、是否值得做场景级生成/跨章缓存（明确 yes/no + 依据）。
- **验收标准（量化）**：
  1. 采样量满足 §13.3：≥30 普通 + 10 多实体 + 10 修订/重写，≥2 Provider；
  2. 结论模板可回答方案 §5.1 全部 8 个问题；
  3. 报告落盘为 docs/novel 下可追溯文件，标注采样时间、Provider、模型与版本。

#### P1-2 Agent 日志冷热分离（对应 T01-4）

- **说明**：`novel_agent_logs` 只留元数据，大文本（system_prompt / chapter_context / user_message / task_input / result / error 等）外置压缩到 payload 表，并加保留策略。
- **范围**：
  - 新增 `novel_agent_log_payloads`（gzip 压缩 BLOB + `content_hash` + `expires_at`）；
  - `graph-store.createAgentLog` 写路径：元数据写主表，大文本写 payload 表（Flag `logPayloadExternalized`）；读取兼容：主表读不到 payload 时兜底旧字段（方案 §13.1 关闭方式）；
  - 保留策略（方案 §4.5）：普通成功 payload 30 天 / 失败 90 天 / 收藏或审计锁定长期 / 日志元数据长期；
  - 保留 `display_agent_type/display_agent_name`（方案 §4.5 明确不立即删，待前端确认）。
- **验收标准（量化）**：
  1. 日志主表平均行体积下降 ≥ 80%（§13.3 指标）；
  2. 审计查询（按 project/chapter/agent 列表）不加载 payload，仅按需读取详情时解压；
  3. payload 读写兼容旧字段：开启 Flag 后，AgentLog 面板详情字段（system/context/user/result/error）显示与迁移前一致；
  4. 保留策略生效：过期 payload 可被清理任务删除，元数据不删；
  5. `content_hash` 可用于去重/校验（同文本不重复存，或至少可校验解压完整性）。

## 5. Feature Flag 设计

对齐方案 §13.1，**所有开关默认关闭**，逐项灰度开启。在既有 `novel-feature-flags.ts`（存储于 `novel_projects.feature_flags` JSON，默认 false、解析失败安全返回 false）基础上**新增 5 个 flag**：

| Flag | 默认 | 影响面 | 开启前提 | 关闭方式 | 本次阶段 |
|---|---|---|---|---|---|
| `versionChainV2Read` | 关 | 前端版本面板、历史回滚 API 读源切到 `content_revisions` | 版本对账差异 = 0（P1-1-5） | 切回旧读 API | P1 |
| `versionChainV2Write` | 关 | 新正文只写 V2 版本链 | 所有消费者已切 V2 读 | 恢复双写 | P1 |
| `logPayloadExternalized` | 关 | Agent 日志大文本写入 payload 表 | payload 读写兼容旧字段（P1-2-3） | 读旧字段兜底 | P1 |
| `sceneCastV2Write` | 关 | Scene 角色只写 `novel_scene_cast` | 三表→cast 转换对账一致（P1-3-1/2/3） | 恢复三表写 | P1 |
| `sceneCastV2Read` | 关 | ScenePlan 往返读取 cast 表 | 影子写对账无差异（P1-3-3） | 读旧三表 | P1 |

补充说明：

- 既有 flag（`scenePlanV2Write` / `scenePlanV2DualWrite` / `memoryProposalV2` / `matrixProjectionV2Read` / `legacyNarrativeWriteDisabled`）保留，`sceneCastV2Write/Read` 与其联动但不互相替代；
- P0 埋点**不引入 flag**（纯旁路记录，不改变行为）；若确需开关，使用独立开关 `contextSectionMetricEnabled`（默认开，随 P0-1 落）；
- 删除列（P1-4）不设 flag（不可逆，靠迁移前引用扫描与观察期控制）；
- 新增 flag 需同步更新 `NOVEL_FEATURE_FLAGS` 常量与 `NovelFeatureFlag` 类型。

## 6. 数据迁移要求

对齐方案 §9，所有结构迁移严格按顺序执行，**禁止跳步**：

```text
新增结构 → 双写 → 对账 → 切读 → 停旧写 → 观察一个版本 → 删除旧结构
```

### 6.1 通用安全规范（禁止项）

1. 禁止新表一建好就删旧列；
2. 禁止未统计消费者就删表（每个迁移第一步必须填消费者清单 §5.2，填不满不允许动结构）；
3. 禁止未提供 Feature Flag 就切换核心生成路径；
4. 禁止用不可靠推断批量回填历史数据；
5. 禁止为规范化删除关键审计字段（本阶段日志元数据、`display_agent_type/name` 均保留）。

### 6.2 每个迁移任务必须提供 MigrationAcceptance

```ts
interface MigrationAcceptance {
  sourceRows: number      // 源表/源字段行数
  targetRows: number      // 目标表/目标字段行数
  mismatchRows: number    // 对账不一致行数（验收要求 = 0）
  orphanRows: number      // 孤儿行数（验收要求 = 0）
  duplicateRows: number   // 重复行数（验收要求 = 0）
  rollbackVerified: boolean // 已演练回滚（验收要求 = true）
}
```

# v0.2 记忆模型重构：冲突/伏笔/钩子/弧光职能边界

**版本**：v0.2.0
**分支**：`feature/v0.2-memory-model`（从 `v0.1.0` tag 切出）
**状态**：设计阶段
**日期**：2026-07-09

## 背景与问题

v0.1 中冲突、伏笔、钩子三类实体职能严重重叠，无法体现各自作用。通过查询项目 `132d4d7d` 的实际数据库数据，发现以下核心问题：

### 证据1：同一事件被多重建模

- **1998年西北脉冲事件**：同时存在于 `novel_conflicts`（`ca602b38`，type=interest）和 `novel_foreshadowing`（`617ed3cb`，status=planted）
- **孙疤尸体被发现风险**：同时存在于 `novel_conflicts`（`004ef73a`）和 `novel_foreshadowing`（`1346457d`）

### 证据2：冲突表混入非冲突内容

- **谜题混入冲突**：`ca602b38`"脉冲同源关系的悬疑"无对抗方，是待解之谜，应归伏笔
- **内心状态混入冲突**：3条 `type=inner` 的记录（`7bea7f5c`/`15ba40e2`/`c5c08174`）是无对抗方的角色心理状态，应归角色弧光
- **章末悬念混入冲突**：`004ef73a`"尸体被发现的风险"本质是第7章的章尾钩子，但第7章 `chapter_ending_hook` 字段为 null

### 证据3：职能字段大面积空置

- `chapter_ending_hook`：7章里5章为 null（钩子散落到冲突/伏笔表）
- `plot_function`：15条冲突里12条为 null
- `plant_method`/`recover_method`：22条伏笔里18条为 null

### 根因

1. Memory Agent 提取边界模糊，`description` 是自由文本，什么都能塞进冲突表
2. 钩子字段没被 Memory Agent 填充，只在 Director 规划时解析
3. 伏笔的 plant/recover method 没被生成
4. 没有跨表去重机制

## 设计目标

1. **界定四实体职能边界**：冲突、伏笔、钩子、角色弧光各自有明确职责
2. **重构 create-flow**：各 Agent 阶段按边界读写实体
3. **新增两张表**：钩子实体、角色弧光实体
4. **数据迁移**：将现有错位数据归位

## 第一节：四实体职能边界

### 1. 伏笔（Foreshadow）— 信息层

**定义**：作者埋下的、读者/角色尚不知道或未理解的信息，有明确的「埋设→回收」周期。

**该装什么**：
- 待解之谜（"1998年脉冲与玉佩信号同源"——读者不知道答案）
- 关键物品的隐藏功能（玉佩可双向通讯、储物法宝的未知限制）
- 身份伏笔（穿越后手背出现的浅疤）
- 事件预兆（蓝星主动发起通讯的能力）

**生命周期**：`planned → planted → reinforced → partially_revealed → recovering → recovered / abandoned`

**不该装什么**：角色内心变化（→弧光）、章末悬念（→钩子）、有对抗方的张力（→冲突）

### 2. 冲突（Conflict）— 张力层

**定义**：有明确对抗方（人vs人 / 人vs环境 / 人vs规则 / 人vs对立价值观）的持续张力。

**该装什么**：
- 生存压力（死亡倒计时——对抗方是监工系统+魔渊妖魔）
- 利益对抗（孙疤抢夺冲击钻——人vs人）
- 调查对抗（赵岩查叶明远——人vs人）
- 认知对抗（蓝星科学框架 vs 超自然证据——人vs认知体系）
- 价值观对立（"忠诚vs生存"——人vs对立价值观，此类 `type=inner` 保留）

**排除规则**：
- ❌ 谜题/悬疑 → 归伏笔
- ❌ 无对抗方的角色心理状态/成长变化 → 归角色弧光
- ❌ 章末悬念（"尸体会被发现吗"）→ 归钩子

**生命周期**：`latent → emerging → escalating → erupting → reversing → resolved / transformed`

**强制约束**：`participants` 必须有至少一方（角色/势力/环境规则/对立价值观），无对抗方的不准入冲突表。Memory Agent 入库时校验。

### 3. 钩子（Hook）— 节奏层（新实体）

**定义**：章末留给读者的悬念驱动，追踪「抛出→兑现」闭环。

**该装什么**：
- 悬念钩子（尸体会被发现吗——suspense）
- 反转钩子（reversal）
- 情感钩子（主角望远方沉思——emotional，不挂钩任何实体）
- 动作钩子（战斗悬而未决——action）

**生命周期**：`thrown → fulfilled / abandoned`
- `thrown`：Director 规划本章时创建
- `fulfilled`：后续章节承接了这个悬念，记录 `fulfilled_at_chapter` + `fulfilled_description`
- `abandoned`：弃用

**关联关系**（由 Memory Agent 建立，不由 Director 建立）：
- `linked_foreshadow_id`：钩子是某伏笔的埋设（时序：Memory Agent 创建伏笔后回填）
- `linked_conflict_id`：钩子是某冲突的升级
- 也可都不挂——纯情绪钩子独立存在

**创建/兑现时机**：
- Director 规划时创建钩子实体（只填描述+类型，不负责关联）
- Writer 写作时承接上一章未兑现钩子 + 在章末抛出本章钩子
- Reviewer 评估时检查"上一章钩子是否兑现、本章钩子是否有效抛出"
- Memory Agent 提取阶段标记钩子 `thrown→fulfilled` + 建立伏笔/冲突关联

### 4. 角色弧光（Character Arc）— 成长层（新实体）

**定义**：角色内心的阶段演进，追踪成长轨迹。

**该装什么**：
- 杀人后的心理冲击与自我消化
- 绝望中因希望燃起求生意志
- 唯物认知被击穿后的认知重构
- 价值观转变、信念动摇

**结构**：阶段演进型，1:1 关联角色（一个角色一条主弧光线）

**弧光类型与阶段模型**：
- `growth`（成长弧）：`denial → resistance → acceptance → transformation`
- `fall`（堕落弧）：`temptation → rationalization → corruption → point_of_no_return`
- `redemption`（救赎弧）：`guilt → atonement → sacrifice → redemption`
- `shift`（转变弧）：`old_framework → disruption → exploration → new_framework`

**字段**：
- `current_stage`：当前阶段
- `stage_history`：JSON 数组，每次阶段转换追加 `{ stage, triggerEvent, description, chapterNumber, changedAt }`
- `description`：弧光整体描述（"从懦弱到坚定"）

**与现有 `character_history` 的关系**：
- `character_history` 保留，记录角色横向状态变更（currentState/goal/pressure）
- `novel_character_arcs` 是纵向成长线追踪，只在**阶段转换**时更新
- `character.arcStage` 字段保留，作为弧光当前阶段的镜像

## 第二节：create-flow 与四实体的交互重构

### 当前 create-flow 的问题

| 阶段 | 现状 | 问题 |
|---|---|---|
| Director | 解析输出填 `chapterEndingHook` 枚举字段；不创建钩子实体；不涉及弧光 | 钩子只是枚举标签，无描述无追踪；弧光完全缺失 |
| Writer | 不读上一章钩子；不兑现钩子 | 衔接对不上的根因——Writer 不知道要兑现什么 |
| Reviewer | 评估钩子但无数据基础（钩子字段常 null） | 无法检查"上一章钩子是否兑现" |
| Reviser | 同 Writer | 同上 |
| Memory | 谜题塞冲突表、内心状态塞冲突表、钩子内容塞冲突表；不填钩子字段；不处理弧光 | 职能混淆的源头 |

### 重构后的实体流转

```
┌─ Director ─────────────────────────────────────────────┐
│ 读：上一章抛出的未兑现钩子（status=thrown）              │
│     当前活跃冲突 + 待回收伏笔 + 角色当前弧光阶段          │
│ 写：创建本章钩子实体（status=thrown，含描述+类型）       │
│     规划本章是否推进某冲突/埋设某伏笔/触发弧光阶段转换    │
│     ⚠️ Director 不负责关联钩子与伏笔/冲突，只创建钩子描述 │
└──────────────────────────────────────────────────────┘
          ↓ 检查点1：用户确认叙事任务
┌─ Writer ───────────────────────────────────────────────┐
│ 读（SEMI 层注入）：上一章未兑现钩子列表（必须承接）       │
│     本章 Director 创建的钩子（必须在章末抛出）           │
│ 执行：正文承接上一章钩子 + 在章末抛出本章钩子            │
└──────────────────────────────────────────────────────┘
┌─ Reviewer ─────────────────────────────────────────────┐
│ 读：上一章钩子（检查是否兑现）+ 本章钩子（检查是否抛出）  │
│ 评估：衔接是否对得上、钩子是否有效                       │
└──────────────────────────────────────────────────────┘
          ↓ 检查点2：用户确认验收
┌─ Reviser ──────────────────────────────────────────────┐
│ 修订时保持钩子兑现/抛出；若改动章末段落由 Memory 重新评估 │
└──────────────────────────────────────────────────────┘
┌─ Memory ───────────────────────────────────────────────┐
│ 输入：章节正文 + 当前实体状态 + 待兑现钩子列表            │
│ 按0.2边界规则分类提取：                                  │
│   - 谜题/线索 → 伏笔（埋设/强化/部分揭示/回收）          │
│   - 有对抗方张力 → 冲突（状态推进）                      │
│   - 章末悬念 → 钩子（标记 thrown→fulfilled，记兑现章号） │
│   - 角色内心变化 → 弧光（阶段转换+触发事件）             │
│   - 建立钩子与伏笔/冲突的关联（回填 linked_*_id）        │
│ 强制约束：冲突必须有 participants；无对抗方不准入冲突表   │
└──────────────────────────────────────────────────────┘
```

### 关键改动点

**1. Director 阶段**
- 新增查询：上一章未兑现钩子注入 Director 上下文
- 新增创建：本章钩子实体（替代只填枚举字段）
- `parseDirectorTask` 从解析枚举 → 创建钩子实体记录

**2. Writer 阶段**
- SEMI 层新增注入：`上一章未兑现钩子列表`（从 `novel_hooks WHERE status='thrown' AND chapter_number < 当前章` 查询）+ `本章规划钩子`
- 这是解决"前后章衔接对不上"的数据基础

**3. Reviewer 阶段**
- 新增检查项：上一章钩子是否兑现、本章钩子是否有效抛出
- `role-reviewer.md` 的"章尾钩子评估"段基于钩子实体数据判断

**4. Memory 阶段（改动最大）**
- LLM 输入增加：待兑现钩子列表
- LLM 输出 schema 重构：
  - `conflictCreates/Updates` 加边界校验：无 participants 的拒绝入库
  - 新增 `hookUpdates`：标记钩子 `thrown→fulfilled` + 兑现描述 + 兑现章号
  - 新增 `arcStageChanges`：角色弧光阶段转换
  - 建立钩子与伏笔/冲突的关联（回填 `linked_*_id`）
- `role-memory-generator.md` 提示词重写：明确四实体边界 + 分类规则 + 排除规则

**5. 章节完成时的 `updateChapter`**
- `chapter_ending_hook` 字段保留作镜像：Director 创建钩子实体后，同步更新为钩子类型
- 矩阵视图现有轨道行不破

## 第三节：数据模型与表结构

### 设计原则
- **复用优先**：现有字段能复用的不新建
- **最小新增**：只新增两张表（钩子、弧光），不重构现有三张表结构
- **边界靠约束**：职能边界通过 Memory Agent 提示词 + 入库校验实现
- **向后兼容**：`chapter.chapter_ending_hook` 字段保留作镜像

### 新增表1：novel_hooks（钩子实体）

```sql
CREATE TABLE novel_hooks (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  chapter_number  INTEGER NOT NULL,
  hook_type       TEXT NOT NULL,              -- suspense/reversal/emotional/action
  description     TEXT NOT NULL,
  status          TEXT NOT NULL DEFAULT 'thrown',  -- thrown/fulfilled/abandoned
  fulfilled_at_chapter INTEGER,
  fulfilled_description TEXT,
  linked_foreshadow_id TEXT,
  linked_conflict_id   TEXT,
  created_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  FOREIGN KEY (project_id) REFERENCES novel_projects(id) ON DELETE CASCADE
);
CREATE INDEX idx_novel_hooks_project ON novel_hooks(project_id);
CREATE INDEX idx_novel_hooks_status ON novel_hooks(status);
CREATE INDEX idx_novel_hooks_chapter ON novel_hooks(chapter_number);
```

**字段说明**：
- `hook_type`：复用现有 `ChapterEndingHookType` 枚举，去掉 `none`（none = 不创建钩子）
- `description`：Director 规划时填
- `status` 流转：`thrown`（Director 创建）→ `fulfilled`（Memory Agent 检测到承接）或 `abandoned`
- `linked_foreshadow_id`/`linked_conflict_id`：由 Memory Agent 建立关联，纯情绪/动作钩子不挂

### 新增表2：novel_character_arcs（角色弧光）

```sql
CREATE TABLE novel_character_arcs (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  character_id    TEXT NOT NULL,
  arc_type        TEXT NOT NULL,              -- growth/fall/redemption/shift
  current_stage   TEXT NOT NULL,
  stage_history   TEXT NOT NULL DEFAULT '[]', -- JSON: [{stage, triggerEvent, description, chapterNumber, changedAt}]
  description     TEXT,
  created_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at      INTEGER NOT NULL DEFAULT (unixepoch()),
  FOREIGN KEY (project_id) REFERENCES novel_projects(id) ON DELETE CASCADE,
  FOREIGN KEY (character_id) REFERENCES novel_characters(id) ON DELETE CASCADE
);
CREATE INDEX idx_novel_arcs_project ON novel_character_arcs(project_id);
CREATE INDEX idx_novel_arcs_character ON novel_character_arcs(character_id);
```

**字段说明**：
- `arc_type`：`growth`（成长）/ `fall`（堕落）/ `redemption`（救赎）/ `shift`（转变）
- `current_stage`：按 arc_type 对应的阶段模型
- `stage_history`：JSON 数组，只在阶段转换时追加
- 1:1 关联角色（一个角色一条主弧光线，多弧光留到 0.3）

### 现有表的改动（最小化）

**novel_conflicts**：不改结构，改入库约束
- Memory Agent 入库时校验：`participants` 不能为空
- 现有 3 条 `type=inner` 无对抗方的数据需数据迁移转为角色弧光

**novel_foreshadowing**：不改结构
- 现有字段足够，问题在 Memory Agent 没正确填充 `plantMethod`/`recoverMethod`
- 0.2 通过提示词约束修复

**novel_chapters**：保留 `chapter_ending_hook` 字段作镜像
- Director 创建钩子实体后，同步更新为钩子类型
- 矩阵视图现有轨道行不破

**novel_node_positions**：`nodeType` 枚举暂不加 `hook`/`arc`
- 0.2 钩子和弧光在矩阵视图用轨道行展示，不进画布节点

### API 层改动

新增 CRUD API（遵循现有 novel-routes.ts 模式）：
- `GET/POST/PUT/DELETE /api/plugins/novel/projects/:projectId/hooks`
- `GET/POST/PUT/DELETE /api/plugins/novel/projects/:projectId/character-arcs`

### 矩阵视图改动

- 现有"章尾钩子轨道行"数据源从 `chapter.chapterEndingHook` → 查询 `novel_hooks`
- 新增"角色弧光轨道行"：显示角色弧光阶段转换
- 钩子兑现状态用不同样式（thrown=虚线、fulfilled=实线）

### 数据迁移策略

```
迁移1：type=inner 且无对抗方的冲突（3条）→ 角色弧光
  - 7bea7f5c "主角燃起求生意志" → growth 弧光
  - 15ba40e2 "唯物认知被击穿" → shift 弧光
  - c5c08174 "首次杀人心理冲击" → growth 弧光
  用代码处理（better-sqlite3 事务），从 participants 提取角色 ID

迁移2：散落到 conflicts 的谜题 → foreshadowing
  启发式识别：participants 为空 + type 为 interest/world_rule
  提供半自动 CLI 工具，用户确认后迁移

迁移3：散落到 conflicts 的章末悬念 → hooks
  如"尸体被发现风险"转成第7章的 hook 记录
  提供半自动 CLI 工具

迁移4：补填 chapter_ending_hook 镜像
  从 novel_hooks 回填，或留 null 由下次重新生成时填充
```

**不自动执行**：提供 CLI 工具，用户确认后执行

### 不做的事（YAGNI）
- ❌ 不重构 `novel_conflicts` 表结构
- ❌ 不删除 `novel_clues` 表（留到 0.3）
- ❌ 不改 `character_history` 结构
- ❌ 不支持多弧光线（留到 0.3）
- ❌ 不自动执行数据迁移

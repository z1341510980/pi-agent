# pi-agent 前端产品 · 用户研究分析与科学的研究计划

> 生成日期：2026-07-28
> 研究员角色：UX Researcher（用户体验研究员）
> 研究范围：pi-agent 桌面前端（通用 Agent 平台 + novel-plugin 作为首个落地场景）
> 研究方法取向：混合方法（定性 + 定量），应团队选择

---

## 0. 执行摘要（关键结论）

- **现状**：工作区内**不存在任何一手用户研究数据**。所有"用户需求 / 痛点"均来自四类二手证据：市场规模估算、竞品评论挖掘、专家启发式评估、设计意图文档。
- **风险预警**：当前产品 / UX 决策建立在"假设驱动设计（assumption-based design）"之上。战略文档中"瑞思（用户研究员）"产出的三类用户与痛点，溯源后实际是**市场规模推算 + 竞品差评挖掘**，并非直接用户接触——属于典型的"需求伪验证"。
- **当前可做的**：基于现有二手证据，做严谨的**二次研究综合（secondary research synthesis）**，逐条标注置信度，产出假设型人物画像与痛点地图。
- **必须补做的**：启动一手混合方法研究，填补"用户是谁、真实痛点频率、任务心智模型"三处断裂的证据缺口（计划见第三部分）。

## 1. 数据资产审计（Evidence Audit）

| 数据源 | 证据类型 | 体量 / 样本 | 能证明什么 | 置信度 | 核心局限 |
|---|---|---|---|---|---|
| `AionUi-借鉴分析报告.md` | 竞品启发式评估（专家视角） | 1 份（对比 8778 vs 5276 节点） | 能力缺口（Team UI 缺失、Gate 割裂等） | 中（专家判断） | 非用户视角，且来自另一产品 |
| `deliverables/product-strategy/prd-*` | 产品策略（含"瑞思用户研究洞察"） | 1 份 PRD | 用户分群、痛点优先级 | **低**（市场推算 + 竞品挖掘） | 自述"链接未逐一核实"，非直接研究 |
| `deliverables/product-strategy/competitive-analysis-*` | 竞品分析 | 7 款产品对比 | 竞品用户槽点（长文崩、人设漂移） | 中（第三方评测引用） | 关于"别家"产品，经分析师转译 |
| `docs/FRONTEND_DESIGN_SYSTEM.md` | 设计系统文档 | 11 章 | 已认知的体验短板、设计三原则 | 中（内部设计意图） | 非用户验证 |
| `apps/.../e2e-test/output/*.log` | 技术日志 | SSE 事件 / 探测日志 | 系统行为轨迹 | 低（自动化测试，非人） | 非用户行为 |

**审计结论**：证据链在三个关键处断裂——
1. **用户是谁**：市场数据告诉我们"有多少人"（职业作者 50–100 万、业余 2000 万+），但没告诉我们"真实用户长什么样、用什么心智模型"。
2. **真实痛点频率**：竞品挖掘告诉我们"别人家用户骂什么"，但没告诉我们"我们产品的用户自己卡在哪、频率多高"。
3. **任务模型**：设计系统描述了"该有什么"，但没有"用户实际怎么走完一次任务"的证据。

## 2. 二次研究综合（Secondary Research Synthesis）

**方法说明**：在缺一手数据下，采用"三角验证 + 置信度标注"的诚实综合。仅当**至少两个独立二手源**指向同一结论时，才提升其置信等级。所有画像与痛点均标注为**假设型（provisional）**，需在第三部分研究中证伪 / 证实。

### 2.1 假设型用户画像（Provisional Personas — 待验证）

> 明确声明：以下画像由"市场规模分群 + 竞品差评模式"推导，**非访谈验证**。它们是研究假设，不是结论。

**画像 A：「保更型职业作者」**（战略称 50–100 万）
- 场景：日更 4000–6000 字签约作者，卡文时依赖 AI 续写且不能崩人设
- 假设性目标：提效保更、人设一致性、润色去 AI 味
- 假设性痛点：长文记忆衰减、OOC 人设漂移（竞品差评高频）
- 与 pi-agent 前端关联：novel-plugin 工作台、小说圣经面板、上下文压缩感知

**画像 B：「低门槛业余作者」**（战略称 2000 万+，主体）
- 场景：零基础套模板出框架、过原创检测
- 假设性目标：快速出框架、低学习成本
- 假设性痛点：学习 / 费用门槛、模板质量
- 与前端关联：首页指令台（GuidPage）、模板入口、引导式 onboarding

**画像 C：「IP 策划编辑」**（数万级，高付费意愿）
- 场景：批量管理角色关系矩阵、生成改编分镜
- 假设性目标：结构梳理、人设矩阵、改编评估
- 与前端关联：矩阵 / 关系图工作区、多标签预览

**画像 D（被完全忽视）：「通用 Agent 平台用户」**（开发者 / 知识工作者）
- 战略文档几乎未覆盖：pi-agent 作为**通用 Agent 平台**，其核心用户是拿来写代码、处理文档、分析数据的人。
- 这批用户的任务模型、痛点（工具编排可见性、权限掌控、多 runtime 区分）在 AionUi 报告里被反复强调为 P0，却**无任何对应用户研究**。
- **这是当前最大的研究盲区**——平台级用户与内容创作用户是两类人，现有证据只覆盖了后者的一部分假设。

### 2.2 痛点地图与置信度（Pain Point Map）

| 痛点 | 证据来源 | 置信度 | 是否 pi-agent 自身缺口 |
|---|---|---|---|
| 长文一致性 / 记忆衰减 | 竞品差评（彩云 / 火山）+ 战略 P0 | 高（跨源印证） | 部分（novel-plugin 在做） |
| 人设漂移 OOC | 竞品差评 + 战略 P0 | 高 | 部分 |
| Agent 编排能力不可见（Team / Subagent 无前端） | AionUi 报告 P0 + 设计系统缺失 | 高（专家评估） | **是（核心缺口）** |
| 工具调用 / 权限决策割裂上下文 | AionUi 报告 + 设计原则"可信" | 高 | **是** |
| 无法区分 runtime / agent 类型 | AionUi 报告 P0 | 中高 | **是** |
| 多任务并行管理弱（session 无拖拽 / 搜索 / 分组） | AionUi 报告 P2 | 中 | **是** |
| 专业主题 / 字号控制缺失（长时间使用疲劳） | AionUi 报告 P2 + 设计系统仅 dark/light | 中 | **是** |
| 通用 Agent 用户任务模型未知 | 无 | **极低（研究盲区）** | 未知 |

**关键发现**：置信度最高的痛点分两类——
- **（1）内容创作侧（长文 / 人设）**：证据来自竞品用户，是"别人家的问题"，对 pi-agent 属间接证据；
- **（2）平台能力侧（Team UI / Gate 内联 / runtime 区分）**：证据来自专家评估 + 自身设计文档，是"我们自己的缺口"，且与设计三原则（**可信 = 状态可见、权限常驻、操作可追溯**）**直接冲突**。

> 研究判断：第二类缺口即便没有用户研究，也应以**高优先级修复**——因为它们违背已确立的设计价值观，属于"已知正确"项（known-correct），不需要等用户来告诉我们"黑盒让人焦虑"。

### 2.3 假设型当前态用户旅程（以"用 pi-agent 完成一次 Agent 任务"为例）

| 阶段 | 理想态 | 假设性断裂点（基于 AionUi 缺口 + 设计系统） |
|---|---|---|
| 启动 | 打开即能下达任务 | 首页为简单入口，无"指令台"（GuidPage 未建） |
| 选择 Agent / runtime | 清楚知道在和"谁"对话 | 只有 model 选择器，**无法区分"Claude Code CLI" vs "GPT-4 API" vs "插件 Agent"** → 心智模型混乱 |
| 下达任务 | 流畅输入、可引用资源 | 已有 slash / @ 引用，基本可用 |
| 观察执行 | 看得见 Agent 在做什么 | **Team / Subagent 在消息流中无可视化** → "黑盒"焦虑，违背"可信" |
| 决策权限 | 在上下文中掌控危险操作 | **权限确认是独立弹窗，打断流式上下文** → 违背"流畅 / 可信" |
| 查看结果 / 预览 | 多格式独立查看 | **无独立 Preview 面板**，文件预览塞在 chat 内 → 多格式查看困难 |
| 管理多任务 | 清晰的任务列表 | **session 列表无拖拽 / 搜索 / 分组** → 任务一多就乱 |

## 3. 科学一手用户研究计划（Primary Research Plan）

**目的**：填补第 1 节断裂的证据链。采用团队选定的混合方法。

### 3.1 研究问题（Research Questions）

- **RQ1（谁）**：pi-agent 前端真实用户由哪几类人构成？各类占比与特征？（验证 / 修正 2.1 画像，**尤其补全画像 D**）
- **RQ2（痛点）**：用户在"下达任务 → 观察执行 → 权限决策 → 结果管理"全流程中的最高频痛点与断裂点是什么？（定性发现 + 定量验证频率）
- **RQ3（心智模型）**：用户对"Agent / Runtime / Team / Subagent / Gate 权限"的心智模型是否清晰？当前 UI 是否匹配？
- **RQ4（优先级）**：在多项待建能力（Team UI、Gate 内联、runtime 选择器、三栏布局、主题 / 字号）中，用户感知价值排序如何？
- **RQ5（满意度基线）**：建立 SUS / NPS / 任务成功率基线，供后续追踪。

### 3.2 方法组合与理由（Mixed Methods）

| 阶段 | 方法 | 回答 | 样本 | 理由 |
|---|---|---|---|---|
| 定性·探索 | 主持式深度访谈（45–60 min） | RQ1 / RQ2 / RQ3 | 每画像 5–8 人，共 20–32 人 | 触及动机 / 痛点 / 心智模型，采用饱和抽样 |
| 定性·验证 | 任务式可用性测试（Think-aloud） | RQ2 / RQ3 / RQ4 | 每画像 5 人，共 15–20 人 | 观察真实操作断裂点，量化任务成功率 / 时长 / 错误 |
| 定量·规模化 | 结构化问卷（含 SUS + 痛点频率矩阵） | RQ1 / RQ4 / RQ5 | n ≥ 200（95% CI ±7%） | 验证画像占比、痛点频率、价值排序、基线分 |
| 定量·行为 | 前端埋点 / 行为分析（若已上线） | RQ2 / RQ5 | 全量（匿名聚合） | 三角验证"自述"与"真实行为"的差异 |

**样本量理由**：
- 定性访谈 5–8 人 / 段通常达到主题饱和（Nielsen 经验法则）。
- 问卷 n = 200 在 50% 比例下 margin of error ≈ 6.9%（95% 置信）。
- 若画像 D（通用 Agent 用户）难招募，至少保证每个已识别段 ≥ 5 人，并对画像 D 单独做一轮补充招募。

### 3.3 招募与筛选（Recruitment & Screener）

- **渠道**：网文作者社区（写手吧 / 番茄作者群 / 豆瓣写作）、开发者社区（掘金 / V2EX / GitHub）、内部种子用户名单、产品等待列表。
- **筛选条件**：近 30 天用过任意 AI 写作 / AI Agent 工具 ≥ 3 次；排除本公司员工；覆盖性别 / 地域 / 设备多样性；每画像配额控制。
- **防偏措施**：避免只招"爱好者"；**必须纳入弃用者（曾用后流失）**以捕获流失原因；给予合理激励（访谈 ¥150–200 / 人，问卷抽奖）。
- **伦理**：签署知情同意、数据匿名化存储、可随时退出。

### 3.4 研究协议（Protocols，节选）

**（1）访谈提纲（节选）**
- 背景：最近一次用 AI 工具完成的任务是什么？卡在哪？
- 心智模型：你理解"Agent / 团队 / 子代理 / 权限"分别是什么吗？
- 痛点回溯：最近一次想砸键盘的时刻？发生了什么？
- 价值排序：若只能先做一个改进，你要哪一个？为什么？

**（2）可用性测试任务（基于当前前端 + 待建能力原型）**
- 任务 1：用 pi-agent 完成"让一个 Team 帮你写并润色一章" → 测 Team UI 缺口
- 任务 2：当 AI 要改你本地文件时，你能理解并掌控这次操作吗？ → 测 Gate / 权限内联
- 任务 3：区分"这是 Claude CLI"还是"这是插件 Agent"并切换 → 测 runtime 选择器
- 指标：任务完成率、时长、错误数、SUS、关键节点情绪（沮丧 / 困惑 / 掌控）

**（3）问卷量表**：SUS（10 题）+ 痛点频率 Likert（5 点）+ 价值排序（MaxDiff 或 pairwise）+ 人口统计。

### 3.5 分析计划（How to Analyze Results）

- **定性分析**：转录 → 开放式编码 → 主题抽取（亲和图）→ 跨画像对比 → 形成饱和主题与验证版 personas（验证 / 推翻 2.1）。
- **定量分析**：描述统计（占比 / 均值）→ 置信区间 → 痛点频率排序（加权）→ MaxDiff 效用值排序 → 与定性三角验证。
- **三角验证矩阵**：同一结论须有"定性访谈 + 定量问卷 +（若有）行为数据"至少两源印证，才升为"高置信"。
- **最终产出**：验证版 personas、优先级排序（用户价值 × 实现成本）、SUS / NPS 基线、改进机会清单。

## 4. 建议与优先级（Recommendations）

### 高优先（立即，不依赖一手研究也可启动）
1. **修复"违背已确立设计原则"的缺口**：Team UI 可视化、Gate 权限内联、runtime 选择器、三栏 + 独立 Preview。这些在 AionUi 报告与自身设计文档中已被专家评估为 P0，且与"可信 / 流畅"原则直接冲突——属"已知正确"项，应立即排期。
2. **启动一手研究（第三部分计划）**：目标在 Q3 内测窗口前完成定性 + 问卷第一轮，为 MVP 验证提供真实证据，**替代当前的"需求伪验证"**。

### 中优先（研究回收后）
3. 依据 RQ4 用户价值排序，对 P1 / P2 项（字号控制、Sider 拖拽搜索、语音输入）排期。
4. **补全画像 D（通用 Agent 用户）的研究**——当前完全盲区，却是平台立身之本。

### 长期
5. 建立持续研究机制：每次大版本前做可用性回归 + 埋点看板，使"用户证据"成为决策默认输入，而非例外。

## 5. 成功度量（Success Metrics）

- **研究采纳率**：80%+ 建议被产品 / 设计采纳
- **用户满意度**：SUS 基线建立后，每版本 +5 分
- **任务成功率**：核心任务（权限决策 / Team 使用）完成率目标 ≥ 80%
- **流失洞察**：弃用者访谈覆盖，流失主因识别率 100%
- **决策依据**：产品评审中"用户研究证据"引用占比从当前 ~0% 提升至 ≥ 60%
